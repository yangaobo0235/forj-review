# 审核流水线、并发与任务生命周期

本文记录浏览器扩展到审核服务的现行执行链路。业务字段和政策规则仍以地区业务文档为准；本文只说明图片如何进入服务、如何调度、何时完成以及何时释放内存。

## 当前执行链路

用户点击“开始审核检查”后执行以下步骤：

1. 扩展通过 `COLLECT_PAGE_MANIFEST` 采集页面字段和 DOM 图片地址，不读取图片正文。
2. 扩展一次调用 `POST /api/review/jobs/urls` 创建任务，只提交页面上下文和图片 URL，不含图片正文字段。
3. 服务端立即把所有图片加入公平模型调度器，自动关闭材料提交阶段；插件无需逐图上传或调用 `/complete`。
4. 模型直接读取原图 URL，在材料提取响应中返回字段和证据区域。URL 模式下的语义重读仍使用原图地址，不下载或裁剪。
5. 待单图识别结束，后端复用 `AgentBatchResult` 完成材料完整性、字段比较和最终建议。二维码官网核验先复用模型返回的 `qr_codes`；模型没有可靠结果时，只对二维码候选图片 URL 读取一次原图到内存，按 ZXing → OpenCV 顺序解码，再执行官网核验。
6. 扩展每秒调用一次 `GET /api/review/jobs/{job_id}` 更新进度，最长等待 120 秒，任务进入终态后展示结果。达到等待上限、重置或切换业务时终止本轮等待并申请取消，丢弃旧任务的迟到响应。

二维码内容优先来自同次 URL 模型提取的 `qr_codes`；模型没有可靠结果时，二维码专用读取器才访问候选原图 URL，在内存中使用 ZXing，失败后用 OpenCV 兜底。该例外不写盘、不上传、不重试图片下载；解码和官网访问分别记录耗时、来源及失败原因，未可靠识别或官网不可用时转人工复核。

## API

| 接口 | 用途 |
| --- | --- |
| `POST /api/review/jobs/urls` | 新插件入口：一次提交 URL，立即识别并自动完成材料提交 |
| `GET /api/review/jobs/{job_id}` | 获取状态、阶段、进度、部分结果或最终结果 |
| `DELETE /api/review/jobs/{job_id}` | 取消排队及运行中的协程；已终结任务保留结果 |
| `POST /api/review/jobs` | 一次提交 URL；内部使用同一公平识别队列 |
| `POST /api/review/assist` | 保留的同步调用接口，不是浏览器插件的正常入口 |

单次任务最多 16 张图片，图片标识和序号分别必须唯一。URL 模式要求可供模型访问的 HTTP(S) 地址；签名 URL 原样保留查询参数。`blob:`、`data:` 和空地址由新插件标记采集错误；接口拒绝未标记错误的非 HTTP(S) 来源。普通图片上传和完成上传入口已移除；二维码只在官网核验的受控候选上执行内存读取。

## 并发参数

| 范围 | 当前值 | 目的 |
| --- | ---: | --- |
| 浏览器图片压缩/上传 | 0 | 新插件只提交 URL |
| 单任务模型识别 | 8 | 单个大任务不能无限占用模型槽位 |
| 全服务模型识别 | 16 | 多任务公平调度 |
| 最终规则汇总 | 2 | 控制 LangGraph、二维码和规则汇总阶段的内存及 CPU 压力 |

后端模型队列按任务轮转。同一任务最多占用 8 个模型槽位；存在其它等待任务时，调度器优先把新空闲槽位交给其它任务。生产值由 `docker-compose.server.yml` 固定，本地可以使用同名环境变量覆盖：

```text
REVIEW_MODEL_JOB_CONCURRENCY=8
REVIEW_MODEL_GLOBAL_CONCURRENCY=16
REVIEW_FINALIZE_CONCURRENCY=2
```

## 状态、阶段与进度

`status` 表示任务是否还能继续，取值为 `RUNNING`、`PARTIAL`、`COMPLETED`、`FAILED`、`CANCELLED`。

`phase` 表示当前所处阶段，取值为 `PREPARING`、`RECOGNIZING`、`FINALIZING`、`COMPLETED`、`FAILED`、`CANCELLED`。`PARTIAL` 是最终结果状态，不是阶段；部分图片失败的任务可以表现为 `status=PARTIAL`、`phase=COMPLETED`。

进度对象包含：

- `total_count`：本次清单图片数。
- `submitted_count`：已提交或失败归档的图片数；提交后即为全部图片数。
- `completed_count`：模型识别成功数。
- `failed_count`：采集或识别失败数。
- `timed_out_count`：识别超时数。

前端轮询等待上限为 120 秒。达到上限时显示已有快照、停止等待并申请取消，不能执行未终结快照中的自动页面动作。创建和查询的单次 HTTP 请求连同 JSON 读取另有 15 秒限制，取消请求也有超时及失败隔离。

## 完成、取消和图片清理

“任务完成”不需要审核页面提供清理按钮。所有单图识别结束且最终汇总执行完毕后，后端自动进入完成阶段。

任务只保存图片 URL 和识别结果，不保存图片正文；二维码解码的短生命周期字节只存在服务内存中，完成后立即释放。清理行为如下：

- 调用取消接口时取消排队和运行中的识别、汇总协程；迟到结果不再写回取消任务。已经完成、部分完成或失败的任务保留原终态和结果。
- 文字结果、状态和进度快照保留约 10 分钟，供前端轮询。

官网核验受能力超时及网页重试策略约束；二维码图片读取有单图大小、超时和候选范围限制，失败后不会进入无限重试。

当前页面没有单独的“取消审核”按钮。创建任务或轮询失败、等待到期、重置、卸载或切换业务时，扩展会申请取消；服务端也支持显式 `DELETE`。取消请求是有界的尽力清理，网络失败时不能保证远端立即停止。

## 常见故障判断

- 页面显示 `Receiving end does not exist`：业务网页没有当前版本的 Content Script。重新加载扩展后，必须刷新业务网页，再重新打开侧边栏。
- 新插件任务长时间处于 `RECOGNIZING`：检查模型是否能访问图片 URL，以及模型服务网络、额度和超时。
- 已提交但识别数不增加：检查模型密钥、模型服务网络和后端日志。
- 进入 `FINALIZING` 后较慢：检查二维码官网访问、规则能力超时和最终汇总并发。
- `status=PARTIAL`：查看失败数和超时数；这表示流程已经结束但部分材料未成功，不是任务仍在运行。

## 2026-10-13 迁移与回滚

影响范围：审核接口只接收图片 URL；模型同次提取字段与 qr_codes。普通图片上传、压缩和裁图接口已删除；二维码官网核验保留受控的内存读取，使用 ZXing 优先、OpenCV 兜底。进度使用 submitted_count。

发布时配套更新后端与扩展。旧上传插件和存储本地图片文件的工作台任务不再支持，需重新采集图片地址。当前合成测试覆盖两种本地解码器，真实 URL 可访问性、二维码真实原图解码率和耗时仍需在实际审核页验收。
