# 审核配置开发

## 选择正确入口

| 变化 | 入口 |
| --- | --- |
| 已支持的字段、材料、路径、别名、版本、规则组合 | 工作台或声明式页面 JSON |
| 需要新的业务算法、外部查询或复杂材料策略 | Python 原生声明和注册能力 |
| 页面控件不在通用采集/写回范围内 | 浏览器平台适配器 |
| 审核生命周期本身变化 | 通用流程，需同步架构和协议验证 |

工作台操作见[审核配置使用](审核配置使用.md)，业务依据见[业务规则](业务/)。不要为普通字段变化复制主图，或在前端重新实现审核规则。

## 离线编辑与运行配置的区别

`examples/page-config` 是脱敏、可运行示例，不会自动启用。实际服务从 PostgreSQL 页面快照加载。离线文件用于编写、校验、差异和回放；验证后通过工作台保存，或按[部署运维](部署运维.md)向目标空间发布。

编辑已有配置时先导出目标空间的完整快照，再复制为工作目录；保留历史和事务回执文件。不要把只有单个示例的目录直接发布覆盖已有生产配置。

```powershell
uv run python scripts/dev/page_tools.py export --schema public --directory .tmp/pages-before
Copy-Item .tmp/pages-before .tmp/pages-work -Recurse
uv run forj-review-service --page-schema
```

调整时使用新版本，不改写已记录版本的内容。以下 Schema、编译、独立回放和原生能力均使用同一审核内核。

## 配置契约与能力发现

- `uv run forj-review-service --page-schema`：输出当前 JSON Schema。
- `GET /api/review/configuration/schema`：同一份机器可读契约。
- `GET /api/review/configuration/rules`：可引用的内置规则、必要字段、检查项和执行阶段。
- `GET /api/review/page-catalog`：当前服务快照中的活动页面。

Schema 拒绝未知属性，布尔开关必须使用 JSON 的 `true`/`false`。配置不接受 Python 导入路径、JavaScript 或执行脚本。普通字段比较支持当前引擎的证据模式、已列出的归一化器、权威链和日期时效；它不是任意表达式规则语言。新增算法仍需开发后端处理器并登记到 `businesses/rules/catalog.py`。

## 新增页面

完整示例见 `examples/page-config/permit.json`。关键部分：

```json
{
  "key": "permit.vin",
  "label": "车辆识别代号",
  "aliases": ["车辆识别代号", "车架号"],
  "normalizer": "vin",
  "evidence": [{"material": "permit", "field": "license.vin"}]
}
```

这一条会同时生成页面采集定义、材料提取白名单、材料字段路由和后端字段策略。多来源时在 `evidence` 中增加条目，`mode` 缺省推导为 `PARALLEL`。`evidence` 是此字段的完整来源列表，显式修改它时会替换此字段原有路由。

- `key` 是稳定领域标识；中文改名只改 `label`、`aliases` 等页面绑定。
- 需要页面取值的字段必须声明 `aliases`；`locator_id`/`locator_name` 只是附加定位条件。材料内部字段可设置 `page_evidence_required=false`，规则内部输入不要求页面别名。
- `evidence.field` 是材料模型提取的字段名，允许与领域 `key` 不同。
- 一个材料分区时 `evidence.scope` 可省略；多个分区时必须明确指定。
- `sections` 描述页面字段区块；`page_groups` 描述图片区域，二者不混用。
- 新材料在 `materials` 声明名称、关键词、读取指引即可，无需更新前端材料类型表。
- 材料 `required=true` 表示必传；相同 `alternative_group` 表示组内任一材料满足即可。
- 显式修改材料必传状态、数量或替代组时，证据完整性要求与上传清单同步更新；删除材料也会移除其上传要求。只修改字段配置不改变继承的上传要求，身份证正反面等组合仍按原声明保留。材料改为可选不会停用仍依赖该材料的业务规则或字段比对。
- `required_pages` 会自动加入页码提取；页码字段使用现有识别协议的 `registration.covered_pages`，不要求材料一定是登记证。
- `extra_fields` 仅补充供专用处理器读取的材料字段；普通审核字段无需重复填写。
- `remove_extra_fields` 删除显式补充的提取字段；普通字段来源和页码要求变更后，其自动提取项会重新计算。
- `remove_materials` 删除继承材料及其必传要求，但必须显式更新仍引用该材料的字段、权威链或证据要求。
- 配置不控制模型任意生成审核结论；模型提取原始信息，后端按声明执行比对。

新配置默认不启用页面写回。确有需要时，声明已支持的 `page_actions`、`writable_control_kinds`（`text`、`textarea`、`number`、`select`、`date`）、逐字段 `writable`、`identity_anchors` 和独立 `record_identity_fields`。浏览器仍执行记录身份、控件和回读检查；仅声明 writable 不会绕过这些检查。

`page_actions` 支持 `fill_review_fields`（人工字段回填）、`verify_invoice`（自动发票验真）和 `set_affiliation`（自动挂靠设置）。规则提出的动作只有已注册、且被当前配置启用时才下发；动作目录要求确认时，规则不能将其降为免确认。挂靠动作还要求两个目标字段都声明为可写。只启用专用动作不会开放通用字段回填按钮。关闭全部动作时，设置 `page_actions: []` 并将继承的可写字段显式改为 `writable: false`。

报废置换支持显式配置 `emission_standard`、`fuel_type_exact`、`jiefang_flag` 归一化器，分别用于排放标准、保留 LNG/CNG 区别的燃料类型、以及登记证品牌到“是否解放牌”的转换。

2026-10-19 动作权限修复迁移：内置报废置换配置显式启用上述三项动作，保留原有默认行为。有意自动验真或设置挂靠的自定义配置，应在新版本的 `page_actions` 中显式列出对应动作；仅启用 `fill_review_fields` 的配置只允许人工回填。此次清理移除了无业务消费者的 `old_vehicle.brand` 内部目标，品牌仍用于 `old_vehicle.is_jiefang`。已有模板指纹或历史快照保持不变，模板更新导致指纹校验不一致时须创建并验证新配置版本，不能覆盖历史记录。

控件类型表示逻辑类型：Ant Design 单日期选择器内部即使是只读文本输入，也按 `date` 采集和回填，通过日历提交日期。下拉框按页面选项文本精确匹配。控件适配属于扩展的浏览器平台层，业务配置只声明允许回填的字段和类型。日期范围、时间选择及未适配的自定义控件交人工处理，详见[页面控件回填排查](部署运维.md)。

## 激活页签识别

页面顶层可声明可选的 `review_tab`，如 `"review_tab": "许可证审核"`。名称必须与审核表单中激活页签的完整文案一致。浏览器先按路径取候选，再读取可见表单内唯一的激活页签，检查 `aria-controls`、`aria-labelledby`、面板角色与可见性；DOM 选择和校验只在前端执行，后端只保存步骤名称。

车源、过户、一致性审核按各自激活页签及关联可见面板区分；一致性仍为未配置审核入口。页签模式缺失、歧义、面板未就绪时停止采集，不能用整页关键词或人工选择绕过。字段与身份锚点限定在当前面板，离开步骤后旧采集永久失效，切回也必须重新采集。

未继承模板且省略 `review_tab` 的普通配置保留原路径/特征识别。继承时省略该字段保留模板值，显式 `null` 清除继承值（仅用于确实没有审核页签的自定义页面），字符串替换为新名称。青岛、长春报废置换继续按原路径识别。

这是页面目录 `1.0` 的可选增量字段，既有 `ReviewRequest`、Profile ID、规则和主图不变。后端与扩展需配套更新：重启后端、重新加载构建的扩展、刷新业务页面并重新采集。回退时同时恢复上一版后端和扩展并重采；旧版识别不支持新版页面流程，回退后应先验证当前页面是否仍适用。

## 修改已有业务

以 `permit.json` 中的独立示例配置为模板，使用精确身份：

```json
"extends": {"page_id": "example_permit", "version": "1.0"},
"fields": [{"key": "permit.vin", "label": "新版车辆识别代号"}]
```

继承应选择当前已配置业务的精确页面身份和版本，不能使用已清除的历史声明或未配置业务作为模板。

继承时，未填写的属性保留原值。示例仅改变字段名称，原字段别名、材料来源、写回边界及其他字段均保留。材料也支持局部修改名称、关键词或必传属性。模板可以是内置业务，也可以是同目录另一个配置版本；加载器按依赖顺序编译，不依赖文件名先后。

新增字段：在 `fields` 增加带 `label` 和 `evidence` 的条目。删除字段：使用 `remove_fields`。删除时清理该字段的路由和展示绑定；如果仍被身份锚点、组合字段、材料证据要求或业务规则引用，则明确报错。应更新相关配置或显式停用依赖规则，不能因删除一个字段就默认停用整项审核。

`enable_rules`/`disable_rules` 只控制已注册的业务规则。对继承后的全部字段检查绑定校验生产者，停用规则后需显式清理或替换相关 `checks`；必审字段不能仅剩一个失效绑定。地区政策随模板继承，并与新配置版本对齐；不支持通过单独停用政策能力绕过政策声明。特殊主体类型和挂靠任务由字段的受限 `task_projector` 选择后端实现，不向前端下发审核算法。

## 版本、生效与回退

配置身份是 `page_id + version`，不能覆盖同身份版本。同一快照内拒绝重复身份；使用 `--snapshot-pages` 建立本地历史后，也拒绝跨重启覆盖已记录版本的源内容或有效配置，`active` 切换不受此限制。同一 `page_id` 的业务和地区不能跨版本改变；接入另一业务或地区应使用新页面身份。修改内置 `1.0` 配置时使用新版本，例如 `2.0`。同一个 `page_id` 只允许一个外部配置版本标记 `active=true`；旧版本可设为 `active=false` 并继续作为模板或历史请求的解析目标。

活动版本用于页面识别目录，采集清单和审核请求携带精确页面与版本。服务运行期间整个注册表保持不变，采集配置不可用时，插件阻止已配置页面进入审核，避免用旧内置规则继续执行。多页面查询不明确时接口返回 409，不取列表末尾猜一个。

回退：将旧配置改为活动版本、新配置改为非活动版本，校验后重启；回退到内置业务时，可移除该页面的外部活动版本。重启不保留内存中的审核作业，应先等待当前作业结束。

## 支持范围

页面必须能由现有浏览器采集器读取。普通表单、区域和图片分组可以通过元数据配置；特殊 iframe、自定义绘制控件等需要开发人员扩展浏览器通用采集能力。审核配置工作台已经提供页面采集、澄清、草稿编辑与受控保存；向生产空间发布是独立操作。


## 审核判定边界

配置 Agent 通过能力目录的 `decision_policy` 读取统一红橙绿语义，具体见[字段与判定规则](审核执行原理.md)。`uncertain_requires_review` 必须为 `true`；配置不能将不确定材料直接判通过或冲突。既有政策人工例外仍交人工确认。新配置验证、离线回放与实际审核使用同一内核。

回放样例可增加 `expect.comparison_reasons`、`expect.check_reasons`，例如 `"comparison_reasons": {"permit.vin": ["RECOGNITION_UNCERTAIN"]}`，用于区别识别不确定和缺少材料。未填写这两项的既有回放样例仍兼容。

## 普通业务改哪里

普通页面在 `.tmp/pages-work/` 维护 JSON。页面取值字段同时声明 `aliases` 和 `evidence`；标签、来源、时效、必传材料等优先修改声明，不需要修改前端或复制主图。

- 页面字段必须有别名。`locator_id`、`locator_name` 是缩小定位范围的条件，不能代替别名；材料内部字段可显式设置 `page_evidence_required=false`。
- 材料内部字段无需页面值也可完成材料核验，结果会保留在工作台中；同一页面上其他要求页面取值的字段仍按各自配置校验。
- `evidence` 是字段的完整来源列表。修改后只从当前有效路由生成提取字段，连续继承不会累积旧来源。
- `remove_fields` 删除字段及其路由和检查绑定；仍被身份、组合字段或规则引用时拒绝通过。
- `remove_materials` 删除继承的材料和必传要求；仍有字段、权威链、证据路由或材料证据要求引用时必须先修改引用。
- `materials[].extra_fields` 增加处理器专用提取输入，`remove_extra_fields` 删除此前显式保留的输入；普通字段的提取项始终由路由生成。
- 停用规则后，继承的检查绑定也必须有生产者。可以显式清空相关字段的 `checks`，或改绑已启用的规则；必审字段还必须保留有效审核依据。

停用规则时，必须清理其投影字段的 `checks`，为仍需审核的字段提供其他有效证据来源。若要删除字段，应使用 `remove_fields`；清空检查绑定不代表取消必审要求。以当前有效声明和精确模板版本为准，不使用历史清理前的模板。

## 校验与查看实际结果

在仓库根目录执行：

```powershell
uv run forj-review-service --check-pages .tmp/pages-work
uv run forj-review-service --check-pages .tmp/pages-work --json
uv run forj-review-service --inspect-pages .tmp/pages-work
```

校验同时装配运行时能力，检查未知规则、无效依赖及不合法的证据阶段。`--json` 将失败输出为含 `ok=false`、`errors` 的 JSON，退出码为 2。

`--inspect-pages` 输出继承展开后的字段、材料提取清单、路由、检查绑定、能力、页面元数据和配置 SHA-256。输出同时包含内置页面与外部配置，并标记活动版本。它只读取配置，不写文件、不调用模型、不访问审核页面。

比较两个独立目录中的活动页面：

```powershell
uv run forj-review-service --compare-pages .tmp/pages-before .tmp/pages-after
```

按稳定 `page_id` 对齐，即使版本从 `1.0` 变成 `2.0`，仍能看到具体字段、材料、检查和能力的新增、删除和变化。非活动版本的完整内容仍可分别通过 `--inspect-pages` 检查。

## 离线回放

回放文件放在页面配置目录的子目录或独立测试目录，不要与根目录的页面 `.json` 混放。公开示例只使用虚构值和 `example.test` 图片地址：

```powershell
uv run forj-review-service --replay-pages examples/page-config --cases examples/page-config/回放样例/permit-cases.json
```

示例覆盖一致、冲突、缺失材料和不确定证据。回放使用真实主图，必须提供固定 `batch`，不会调用模型、读取图片 URL 或执行官网核验；外部核验只能消费 `external_results` 固定样例，没有样例时生成证据不足结果。

每项用例包含：

| 属性 | 用途 |
| --- | --- |
| `name` | 不重复的样例名称 |
| `request` | 固定页面身份、版本及脱敏页面采集结果 |
| `batch` | 固定材料识别、字段观察及不确定标记 |
| `external_results` | 按能力 ID 提供固定 `checks`、`qr_checks`、`evidence`，可省略 |
| `expect.recommendation` | 必填整单预期 |
| `expect.comparisons` / `expect.checks` | 指定字段或检查的预期状态 |
| `expect.capabilities` | 核对能力执行、跳过、阻塞或失败状态 |
| `expect.comparison_fields` | 精确核对比较字段集合，防止少审核一项 |
| `expect.manifest_fields` | 精确核对浏览器应采集的字段集合 |
| `expect.task_fields` / `expect.writable_fields` | 精确核对任务目标及允许写回的字段集合 |

回放通过退出码为 0，预期不符为 1，文件或配置无效为 2。报告只列标识、状态、摘要和预期差异，不回显页面值或材料原文。DOM 控件是否真实存在仍由浏览器采集验证；固定 batch 回放不能代替真实页面验收。

## 本地快照、版本保护与回退

完成检查与回放后，可为当前本地配置建立基线：

```powershell
uv run forj-review-service --snapshot-pages .tmp/pages-work
```

命令在 `.tmp/pages-work/.history/` 写入内容寻址的配置快照和 `versions.json` 索引。源文件与继承展开结果都记录摘要。后续离线校验、检查会拒绝同一 `page_id + version` 的内容或模板发生改变，要求使用新版本。即使文件被删除后重新建立，索引仍保留已记录版本的约束。

这是显式建立的本地基线；尚未保存快照的草稿允许修改。目录整体复制时应保留 `.history/`。快照不保存真实页面数据、图片或审核结果，不负责恢复内存中的审核作业。

`active` 属于本地版本选择，不计入不可变源配置摘要。新增版本时把旧版本设为 `active=false`，新版本设为 `active=true`，保留精确模板文件；验证并发布到目标数据库空间后，重启对应审核服务并重新采集。需要回退时交换活动标记，校验、发布到目标数据库空间并重启后生效。若工作文件丢失，可从快照的 `files` 对象恢复原文件；不要手工篡改历史摘要。

快照写入使用独占写锁和原子替换索引。若本地进程异常退出留下 `.history/write.lock`，先确认没有其他快照命令运行，再清理该锁文件。读取检查不会创建或改写历史。


## 原生业务声明

结构定义见 `src/forj_review_service/businesses/packs/model.py`，完整示例见
`src/forj_review_service/businesses/packs/scrap_replacement.py`。声明由五部分组成：

### 1. 字段（`FieldDeclaration`）

每个字段声明：稳定键、中文标签、页面别名、页面区域、证据来源、比较方式、权威链。

```python
FieldDeclaration(
    key="old_vehicle.vin",              # 稳定键，只增不改
    label="报废车辆车架号",              # 面向审核员的名称
    section=OLD_SECTION,                # 后端分区
    aliases=("报废车辆车架号", "旧车车架号", "车架号"),   # 页面上的写法
    page_section=OLD_SECTION,           # 页面 DOM 区域
    section_required=True,              # 必须落在该区域，否则判歧义
    mode="PARALLEL",                    # 证据模式
    sources=("vehicle_license", "registration_certificate"),
    normalizer="vin",
    authority=(...),                    # 权威链，见下
    required=True,                      # 是否进入必审清单
)
```

**权威链**用于"某个来源说了算"的字段。链首是唯一比较基准，其余来源各按自己的
`match` 窗口与基准比对；链首缺失时转人工复核，不让位给下一条来源：

```python
authority=(
    AuthorityRule("qr_page", "二维码官网"),                    # 链首＝权威
    AuthorityRule("page", "申请页面", required=True),          # 页面缺失即人工复核
    AuthorityRule("image", "行驶证或登记证",
                  ("vehicle_license", "registration_certificate"), "suffix8"),
)
```

不需要权威关系的字段不要写 `authority`，走通用的多源比对。

### 2. 材料（`MaterialDeclaration`）

每类材料声明：材料类型、显示名、可读字段、读取指引、页面分组提示、允许出现的分区。

```python
MaterialDeclaration(
    document_type="registration_certificate",
    display_name="机动车登记证书",
    fields=("vehicle.owner", "vehicle.vin", "registration.covered_pages"),
    guidance="读取注册登记信息栏中的车辆类型、车辆识别代号……",
    hints=("登记证书", "机动车登记证"),          # 页面分组文字
    allowed_scopes=(OLD_SECTION,),               # 只出现在旧车资料区
    scoped_vehicle_fields=(),                    # 车辆字段如何跟随页面分区
)
```

`scoped_vehicle_fields` 表示"材料上的 `vehicle.X` 落到 `{当前分区}.X`"。**不在这里
声明、又没有显式路由规则的字段会被丢弃**——这是防止材料上的无关字段冒充领域字段。

### 3. 材料字段路由（`RouteDeclaration`）

材料上的字段名与领域字段名不一致时逐条声明；`{scope}` 按当前页面分区替换，一条规则
可以映射到多个领域字段：

```python
RouteDeclaration("invoice", "vehicle.owner",
                 ("new_vehicle.owner", "application.customer_name"),
                 scope=NEW_SECTION),
```

### 4. 地区（`RegionDeclaration`）

同一业务的各地区共用字段和材料，只有政策与页面地址不同：

```python
RegionDeclaration(
    Region.QINGDAO,
    replacement_policy=QINGDAO_REPLACEMENT_POLICY,   # 也可为 None
    admin_paths=("/scrap-replace-qingdao",),
    # 报废置换保持路径识别，不声明 review_tab。
),
```

地区政策能力 ID 由地区推导（`{region}_replacement_policy`），不用单独声明。
**加一个新地区 = 加一个 `RegionDeclaration`。**

**业务不分地区时不要按地区拆声明。** 页面地址不同、规则完全一样时，用一条
`Region.DEFAULT` 声明可把多个地址列在同一业务配置中（如一致性审核
是一条声明两个地址，见审核执行原理中的步骤识别说明）。按地址拆成多个地区声明会让同一套规则出现
多份 Profile，改一处漏一处会静默地只对某个地址生效。

`page_anchors` 是未声明 `review_tab` 的普通页面的特征文案：用于共享地址或未知路径时唯一匹配，要求全部命中。声明 `review_tab` 的审核页面只认激活页签及对应面板，不使用特征词兜底，步骤识别见[审核执行原理](审核执行原理.md)。

### 5. 能力与页面动作

```python
capability_specs=( CapabilitySpec("material_completeness", kind="MATERIAL", ...), ... ),
binding_declarations=( CapabilityBinding("material_completeness"), ... ),
page_action_ids=("fill_review_fields",),
page_interaction=True,
# 规则结论投影成页面字段的核验条目：(check_id, field)。
field_check_bindings=(("VEHICLE-MODEL-POWER", "vehicle.model"), ...),
# 审核字段就是声明的字段，页面上其他控件不进审核目录。
review_declared_fields_only=True,
material_policy=SCRAP_REPLACEMENT_MATERIAL_POLICY,
```

**每个能力都必须有对应的绑定**，否则服务启动时校验失败。

字段级回填还需要四处声明，缺一不可：`page_action_ids` 启用 `fill_review_fields`、要允许写回的字段上标 `writable=True`、`writable_control_kinds` 声明已验证过的控件类型、以及 `identity_anchors` 声明页面指纹锚点和独立记录身份字段。

- **没声明过控件类型的业务不限制**，这是给历史业务留的口径；新业务一律显式声明，只放开验证过的类型。
- **兼容旧清单时，页面指纹锚点必须包含一个强锚点**（`*.vin` 或 `application.id`）。锚点一个都匹配不上时指纹是空串，页面写回和原图定位会在客户端被静默拒绝——报错信息不会指出是锚点写错了，只会表现为"点了没反应"。新业务接入时先确认锚点字段在该页面上存在。

两个可选声明的用途：

- `field_check_bindings`：规则结论默认作为独立任务出现在“页面外核验”里；希望审核员在字段视图里也能看到时，把结论绑到对应页面字段上。**绑定之后该检查不再出独立任务**，结论并进那一行——审核员在字段下面就能看到，不必切视图。合并由后端 `prepare_display_tasks` 按这张表做，前端不持有第二份。
  **字段既有页面值又有材料值时同样适用**（日期类规则就是这种：字段本身要核页面和材料，规则还要判时效），不是只在字段没有比对时才生效。——同一句话在两个地方各说一遍只会让审核员在「待处理」里把它处理两次；字段控件不在页面上时条目出不来，独立任务保留。多条检查绑到同一字段时按最坏状态合并理由，结论本身仍各自保留，每条检查自己的理由还会写进它的候选值（`CheckResultValue.check_reason`），工作台放进对应的候选框里。结论多、理由长的字段尤其需要，否则审核员得在框和字段理由之间来回对照。
- `review_declared_fields_only`：默认 `False`——页面上未配置核验来源的控件会生成一条“请人工核对”条目，避免被静默忽略。新业务的审核范围就是声明字段时设为 `True`，否则工作台会被页面上大量无关控件淹没。

## 原生业务登记与引用校验

在 `src/forj_review_service/businesses/packs/__init__.py` 的 `BUSINESS_PACKS` 里加一行：

```python
BUSINESS_PACKS: dict[BusinessType, BusinessExtensionPack] = {
    BusinessType.SCRAP_REPLACEMENT: SCRAP_REPLACEMENT_PACK,
    BusinessType.VEHICLE_SOURCE: VEHICLE_SOURCE_PACK,      # 新增
}
```

登记之后自动生效的部分：字段清单与标签、证据策略、材料白名单与读取指引、
材料字段路由、页面地址白名单、Profile、能力绑定、以及下发给前端的采集清单。

Profile 由声明生成（见 `src/forj_review_service/businesses/profiles.py` 的 `build_profile`；
`build_scrap_profile` 是它的报废置换包装）。未声明扩展包的业务走
`rules_configured=False` 的降级路径，返回"规则尚未配置，请人工复核"。

分区归属由 `__init__.py` 的 `_validate_scope_ownership` 在启动期校验：
**同一业务分区不能出现在两个业务里**，否则按分区反查声明（`pack_for_scope`）
就会变成看声明顺序。字段路由只有业务分区可用，这一层保证它总能选对声明。

同一处还有一道 `_validate_all_pack_references`，校验声明内部的**每一个字段键引用**
是否都指向本业务已声明的字段（`src/forj_review_service/businesses/packs/model.py` 的
`validate_pack_references`）：路由目标（含 `{scope}` 展开后的每一个分区）、
组合字段的三个键、`field_check_bindings`、`identity_anchors`、`derived_field`、
`invoice_verification_field`、`material_field`，以及字段键与材料类型是否重复声明。
一次报出全部问题，不用改一处、启动一次。

**这道校验存在的理由**：这些引用写错时后果是静默的——那条观察值在
`field_policy()` 处被丢掉，审核员看到的是「该字段没有材料证据」，而不是
「配置写错了」。两种情况的处理方式完全不同。启动期直接失败并指出是哪个声明的
哪一处，比带着一个静默错误去审单子好。

两条因此必须知道的写法：

- **`{scope}` 会按分区展开，所以每个分区展开后的键都要存在。** 只在某一个分区存在的
  字段，必须在 `RouteDeclaration` 上写 `scope=` 限定，否则另一侧会展开出一个不存在的
  键。报废置换的注册日期、车辆类型、燃料类型都是这种。
- **只被规则读取、不进审核目录的字段同样要声明**（`mode=None`、`required=False`、
  `reviewable=False`、不加别名）。青岛政策的 `new_vehicle.origin` 就是这样：它没有页面
  控件、不参与字段比对，但字段键必须存在，否则产地判定会因为「没有证据」而静默失效。
  适用于供规则读取、不参与常规比较的上下文字段。

## 什么时候扩展代码

只有三种情况：

1. **需要新的判断能力**：在 `src/forj_review_service/businesses/rules/<业务>.py` 写一个同步 Handler
   （返回 `RuleExecutionResult`），在 `src/forj_review_service/businesses/rules/catalog.py` 的 `RULE_DEFINITIONS`
   里注册，并在声明里绑定 `CapabilitySpec` + `CapabilityBinding`。三处缺一不可：
   **没有注册表条目，`BusinessRuleRegistry.validate` 会在启动期抛 `UnknownBusinessRule`**。
   超时、重试和失败策略由 `CapabilitySpec` 声明，不需要写在 Handler 里。
2. **页面 DOM 结构完全不同**：现有采集器按中文别名 + 页面区域匹配，多数页面
   只需要在声明里补别名。结构差异大时才需要前端适配器。
3. **需要新的展示形态**：在 `apps/review-extension/src/features/review/ui/workbench-renderers.ts`
   注册新的 Renderer。通用任务用默认渲染器即可。

如果新业务要改动引擎侧的投影表（`field_policies`、`fields`、`materials`、
`completeness` 的中文标签、`service` 的槽位表），先确认它们是否已经按
`BUSINESS_PACKS` 合成——合成之后新增业务不需要再碰这些文件。

**主图（`src/forj_review_service/runtime/workflow/graph.py`）不按业务复制。** 只有生命周期本身变化时才改主图。

## 接入与交付检查

- 明确页面路径、激活步骤、记录身份、字段分区、材料、来源和可写边界。
- 登记字段、材料、路由、地区、能力及动作；检查引用，不能静默丢字段。
- `record_identity_fields` 声明可靠的记录身份字段；确认真实页面存在锚点和唯一目标。
- 为一致、可靠冲突、缺材料、不确定、外部失败和步骤变化准备独立样例。
- 更新对应业务规则文档，使用[业务文档模板](业务/业务文档模板.md)。
- 配置检查、回放、相关自动化用例和真实控件验收通过后，明确发布与回退方式。

内置页面识别目录变更后，使用 `uv run python scripts/dev/export_page_catalog.py` 同步扩展内置目录及 fixture。服务下发的精确采集清单仍是已配置页面的正常来源；清单不可用时不能用旧规则继续执行。

能力目录接口和配置 Schema 是当前支持范围的依据。禁止生成任意 Python、恢复历史停用声明、绕过不确定保护、把未配置业务判为通过，或让普通业务变更落进 HTTP、调度器和通用控件分支。
