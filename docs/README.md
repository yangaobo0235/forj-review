## 推荐阅读顺序

- 日常审核：审核辅助使用 → 对应业务文档。
- 修改已有页面：审核配置使用 → 业务字段核对矩阵；需要 CLI 或理解限制再读审核配置开发。
- 开发或 AI 改代码：开发规范 → 项目结构 → 对应业务 → 涉及的开发/数据主题。
- 部署与排障：部署运维 → 相关数据文档。

## 正式文档怎么维护

1. **按职责更新。** 字段和政策改业务文档；共同执行机制改审核执行原理；类型/索引改字典；命令改对应开发或运维主题。其他位置通过链接引用，避免第二份规则。
2. **描述现状。** 正式文档写已实现能力和已确认口径。待办、尝试、一次性清理和未确认设计放本机计划；不堆开发流水、历史截图或完成报告。
3. **保持稳定。** 已有主题能容纳的直接补章节。确有独立长期主题、新业务或能力失效时允许增删，同时更新本页和引用；不按每次需求新建方案、计划、总结。
4. **保持可验证。** 示例脱敏，仓库链接用相对路径，命令与入口一致。运行配置以目标数据库活动发布为准，文档不是运行默认值。
5. **业务表完整。** 区分页面审核、系统输入、辅助材料、查询范围和动作目标；逐字段写来源、比较及回填限制，不能只在文末增加变更记录。

## 本机开发计划

本机入口为 `docs/开发计划/README.md`，整个 `docs/开发计划/` 由根 `.gitignore` 排除，不纳入提交。入口内有计划模板；此处说明路径，不建立依赖本机文件的正式链接。

新克隆仓库不会包含该目录，需要时在此位置创建。计划记录目标、待确认问题、范围、验证和进度；完成后将长期结论写回上述固定文档，不把计划复制进正式目录。
