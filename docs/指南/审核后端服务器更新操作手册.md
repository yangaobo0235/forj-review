# 审核后端服务器更新操作手册

核对日期：2026-10-16。此次范围：审核后端部署到 Ubuntu；浏览器扩展安装在使用者电脑；聊天配置后端和配置 Web 保持本机运行，不上传也不开放 8011/5174。

以下公网地址取自当前代码预设 `http://175.178.6.214:18110`。如果服务器已经更换，先替换地址，并核对扩展 `public/manifest.json` 的 `host_permissions` 是否包含新地址。本流程不会自动连接或修改服务器。

## 1. 两个服务器目录各放什么

| 位置 | 用途 | 更新时操作 |
| --- | --- | --- |
| `/home/ubuntu/review-agent-deploy/` | 一个后端压缩包，以及固定的 Compose、启动/停止/回滚脚本 | 首次上传工具，日常只换后端包 |
| `/opt/review-assistant/` | 正式运行 Compose、服务器 `.env`、部署锁和回滚记录 | `.env` 手动维护，其余由脚本管理 |
| `/home/ubuntu/review-agent-deploy/logs/` | 持久化审核应用日志 | 保留，不用本地日志覆盖 |

`start-review.sh`、`stop-review.sh`、`rollback-review.sh`、`review-common.sh` 和 Compose 首次更新一次，日常保留。启动脚本自动解包并校验，无需每次单独上传发布信息或校验清单。

## 2. 本地构建后端

准备 Docker Desktop（Linux 容器引擎）、Git、Node.js 22.18+。在 Windows PowerShell：

```powershell
cd D:\fjkj\software\workspace\forj-review-assistant
docker info
.\package-server.cmd
if ($LASTEXITCODE -ne 0) { throw '后端打包失败，不要上传旧产物' }
```

后端按 `uv.lock` 在 Docker 中构建 Linux amd64 镜像，打包当前工作区源码，包含未提交改动；不是只打包最近一次 Git 提交。`release.json` 会标记 dirty。确认服务器是 x86_64/amd64，ARM 服务器不能直接使用这份镜像。

日常只需上传这一个文件，不用手动解压：

```text
.tmp/server-release/forj-review-server.tar.gz
```

首次上传一次的固定工具位于 `.tmp/server-deploy/`：

```text
docker-compose.server.yml
start-review.sh
stop-review.sh
rollback-review.sh
review-common.sh
recover-legacy-compose.py
DEPLOY.md
```

压缩包内部包含镜像 TAR、`release.json` 和 `SHA256SUMS`，不用分别处理。只有本次命令成功后才使用这些产物；失败可能留下上次成功的包。旧版打包留下的散落 TAR 和清单不再使用。不要上传本机 `.env`、`.venv`、整个 `.tmp`、真实会话库或整个源码仓库。

## 3. 本地打包连接服务器的扩展

注意：本次核对发现 `apps/extension/.env` 配置了 `http://127.0.0.1:8010`。显式环境配置优先于构建模式，所以直接运行公网打包也可能继续连接本机。

建议在同目录维护仅用于公网模式的 `apps/extension/.env.public.local`，内容只有：

```dotenv
VITE_AGENT_BASE_URL=http://175.178.6.214:18110
```

该文件不包含模型密钥，不修改 `.env` 中的本地地址；Vite 的 public 模式会优先读取它。若 PowerShell 或 IDEA 进程本身设置了同名环境变量，其优先级更高，也要核对。另一种一次性构建方式如下，不需要创建文件：

```powershell
$previousReviewEndpoint = $env:VITE_AGENT_BASE_URL
try {
    $env:VITE_AGENT_BASE_URL = 'http://175.178.6.214:18110'
    .\package-extension.cmd
    if ($LASTEXITCODE -ne 0) { throw '扩展打包失败' }
} finally {
    $env:VITE_AGENT_BASE_URL = $previousReviewEndpoint
}
```

得到 `.tmp/forj-review-extension-public.zip` 和校验文件。这份 ZIP 给使用者电脑安装，**不用放进后端 Docker 容器**。

`package-extension.cmd` 会执行 `npm ci` 和构建；如果本机后来还要审核本地服务，执行 `.\package-extension.cmd -Local`，并确保没有进程变量或 `.env.development.local` 覆盖本地地址。两种构建都会更新 `apps/extension/dist`；区分本地版和公网版的解压目录，避免 Chrome 加载错目录。

## 4. 服务器检查、备份和环境配置

先 SSH 登录服务器。部署用户须能运行 Docker，服务器需已有 Docker Engine、Compose v2、curl、flock 和 sha256sum。

```bash
uname -m
docker info >/dev/null
docker compose version
docker ps --filter name=review-agent-service
```

已有安装升级前，备份运行目录，不需要先停旧服务：

```bash
umask 077
backup_dir="$HOME/review-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
cp -a /opt/review-assistant "$backup_dir/runtime"
```

如果是首次安装，先准备目录，再创建服务器配置；已有安装不要覆盖原来的密钥：

```bash
sudo install -d -o ubuntu -g ubuntu -m 0750 /opt/review-assistant
install -d -m 0750 /home/ubuntu/review-agent-deploy
nano /opt/review-assistant/.env
chmod 600 /opt/review-assistant/.env
```

适用于当前现有内置业务的服务器配置示例：

```dotenv
DASHSCOPE_API_KEY=在服务器编辑器中填写实际密钥
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
DASHSCOPE_MODEL=qwen3.8-flash

REVIEW_MODEL_GLOBAL_CONCURRENCY=16
REVIEW_MODEL_JOB_CONCURRENCY=8
REVIEW_FINALIZE_CONCURRENCY=2

REVIEW_LOG_LEVEL=INFO
REVIEW_LOG_MAX_MB=10
REVIEW_LOG_BACKUP_COUNT=30
REVIEW_IMAGE_PRIVATE_HOSTS=
```

模型名应采用账号实际支持、已验证的名称；保留现有可用配置也可以。Compose 已固定容器日志目录 `/logs` 和文件日志必需模式，无需把本地 `REVIEW_LOG_DIR=../../logs` 复制过去。`REVIEW_IMAGE_PRIVATE_HOSTS` 仅在二维码原图确实来自明确授权的内网主机时填写精确主机名/IP，否则保持空。

**本次不设置 `REVIEW_PAGES_DIR`。** 当前本地 `review-pages/` 尚无页面 JSON，现有业务来自镜像内置声明。不要照搬本地的 `../../review-pages`，也不要擅自改为宿主机路径：当前 Compose 没有外部配置卷，配置加载又需要可写的相邻锁文件，不能在只读镜像中简单指定目录就解决。已有服务器若设置了此变量，必须先核对其挂载和用途；不能为了本流程直接删除原有业务配置。

本地聊天配置 Agent 保存的新页面不会自动同步到服务器。这次先更新现有审核业务；后续启用本地新配置到服务器，需要单独安排校验、发布和版本回滚流程。

## 5. 首次上传固定脚本

用 WinSCP/SFTP 将本地 `.tmp/server-deploy/` **里面的文件**上传到 `/home/ubuntu/review-agent-deploy/`，覆盖同名文件，不要再套一层 `server-deploy/`。这一步只需做一次，之后工具没有改变就不用再传。打包会从根目录 `deploy/` 的四个 Shell 脚本和根目录 Compose 汇总生成此目录，Shell 文件已规范为 LF 无 BOM，传输时不要转换换行符。

上传后在服务器执行一次：

```bash
cd /home/ubuntu/review-agent-deploy
chmod +x start-review.sh stop-review.sh rollback-review.sh
```

以后手动更新的内容按下面区分：

| 情况 | 上传什么 |
| --- | --- |
| 首次安装，或从旧版脚本迁移到本版 | 固定工具目录中的文件，以及一个后端压缩包 |
| 只修改后端业务代码/依赖 | 只上传 `forj-review-server.tar.gz` |
| 部署脚本或 Compose 有变化 | 额外上传变化的工具文件 |
| 只修改模型密钥、模型名、并发、日志参数 | 直接编辑服务器 `/opt/review-assistant/.env`，无需本地打包上传 |

## 6. 日常更新：停止 → 手动换包 → 启动

本地两个打包命令成功后，在服务器停止审核后端：

```bash
cd /home/ubuntu/review-agent-deploy
./stop-review.sh
```

接着用 WinSCP 手动把本地 `.tmp/server-release/forj-review-server.tar.gz` 上传到 `/home/ubuntu/review-agent-deploy/`，覆盖同名文件，不用解压。上传完成后启动：

```bash
cd /home/ubuntu/review-agent-deploy
./start-review.sh
```

启动脚本自动解包并验证包内文件、校验值及镜像 ID，校验 Compose，保留旧健康镜像及匹配的 Compose，准备日志权限，重建容器并等待健康响应。服务器 `.env`、日志和回滚记录保留。停止到启动期间服务不可用，内存审核任务会中断，应选择无人审核时更新。首次安装没有运行服务时跳过停止。

只有脚本成功退出后再继续验收。首次迁移若旧容器存在但原 Compose 已缺失，脚本通过同目录的 `recover-legacy-compose.py` 从实际容器参数恢复受保护的运行快照，校验通过后才加载新镜像。快照含旧环境变量，权限为 0600，不要分享；回滚到该快照使用旧容器的实际环境参数，服务器 `.env` 本身不变。没有旧容器可供恢复，或参数无法准确重建时会停止升级，需恢复原备份；不能通过删回滚标记绕过检查。

## 7. 验证和更新浏览器扩展

服务器：

```bash
curl --fail http://127.0.0.1:18110/health
docker ps --filter name=review-agent-service
docker logs --tail=50 review-agent-service
tail -n 50 /home/ubuntu/review-agent-deploy/logs/review-agent.log
```

健康接口预期 `{"status":"ok"}`。`review service started` 应出现本次发布 ID；启动脚本已验证包内记录的镜像 ID 与实际加载的镜像一致。容器服务名为 `review-agent`，容器名为 `review-agent-service`，端口映射为服务器 18110 到容器 8010。

使用者 Windows 电脑：

```powershell
curl.exe --fail http://175.178.6.214:18110/health
```

若服务器本机能访问、使用者电脑不能，检查云安全组、服务器防火墙与实际 IP/端口。当前审核 API 没有用户登录鉴权，18110 的来源应限制为实际使用者的出口 IP；不要为此开放本地配置服务的 8011/5174。

解压公网扩展 ZIP 到固定目录，打开 `chrome://extensions/`，开启开发者模式，选择“加载已解压的扩展程序”，选含 `manifest.json` 的目录。已有同一目录安装时覆盖文件后点击重新加载。随后刷新实际审核网页，确认请求目标为服务器 18110，再用测试样例完成一次材料识别、字段核对、二维码核验与字段回填。

`/health` 正常只代表服务进程可响应，不代表模型密钥、配额、材料地址、官网核验或页面回填全部正常。原图 URL 还必须可被模型服务读取；仅浏览器登录后可见的图片不代表服务器或模型能访问。

## 8. 日志在哪里、记录什么

| 日志 | 实际位置 | 内容与保留 |
| --- | --- | --- |
| 应用日志 | `/home/ubuntu/review-agent-deploy/logs/review-agent.log` | 容器 `/logs` 持久化映射；午夜或 10 MiB 轮转，最多 30 份归档加当前文件 |
| 部署日志 | `/home/ubuntu/review-agent-deploy/deploy.log` | 启停、校验、镜像加载、回滚与健康等待输出；下次操作发现超过 5 MiB 时转为 `.1` |
| Docker 控制台 | `docker logs review-agent-service` | 应用控制台、启动失败等；最多 3 个 10 MB 文件，由 Docker 管理 |
| 浏览器诊断 | 审核网页/扩展侧栏的 Console | DOM 采集、定位、回填和回读；不会自动上传服务器 |

“保留 30 份”不是“保留 30 天”，高流量时一天可能轮转多次。应用日志时间为 `Asia/Shanghai`；重建/停止容器不删除挂载日志，容器控制台历史应优先以应用文件日志补充。

后端记录：发布版本和实际配置摘要；请求路由模板/状态/耗时；任务创建及终态；图片数与采集失败数；分类/提取调用、耗时、token 与限流；重试原因和结果；二维码解码来源、官网域名、TLS/HTTP 与失败码；图节点和能力状态；证据质量、字段冲突/待复核状态及原因；排队耗时、执行耗时和进程峰值内存。

用 `request_id`、`job_id`、`trace_id`、图片标识、业务/地区/配置版本串联；不写姓名、身份证/VIN/车牌、字段原值、完整材料/二维码 URL 与签名、Cookie、密钥、完整提示词或模型原始响应。成功轮询和健康检查不逐条刷日志。

```bash
# 实时查看
tail -f /home/ubuntu/review-agent-deploy/logs/review-agent.log
# 部署失败
tail -n 100 /home/ubuntu/review-agent-deploy/deploy.log
docker logs --tail=100 review-agent-service
# 按某次任务查询，包括归档
grep -F 'job_id=替换任务ID' /home/ubuntu/review-agent-deploy/logs/review-agent.log*
grep -F 'trace_id=替换追踪ID' /home/ubuntu/review-agent-deploy/logs/review-agent.log*
```

后端成功不能证明浏览器写回成功；回填问题要结合浏览器 `[ReviewAgent] write.*` 诊断。日志是排障记录，不是完整证据档案或已完成审核记录。详细字段见[日志与排查](../参考/日志与排查.md)。聊天配置仍在本机，其日志不在上述服务器路径。

## 9. 失败恢复与日常重启

更新失败或出现回归时：

```bash
cd /home/ubuntu/review-agent-deploy
./rollback-review.sh
curl --fail http://127.0.0.1:18110/health
```

回滚恢复上一健康镜像及匹配 Compose，不恢复你手工修改的服务器 `.env`；若故障来自 `.env`，需结合第 4 节备份恢复相应配置。没有旧镜像和匹配 Compose 的首次安装不能回滚。健康失败不会自动回滚，不能只看到容器存在就当作更新成功。

临时重启既有容器（不应用 `.env` 的新值）：

```bash
cd /opt/review-assistant
docker compose --env-file .env -f docker-compose.server.yml restart review-agent
```

修改服务器 `.env` 后，按停止、启动流程应用配置，无需重新打包。保留 `forj-review-server.tar.gz` 和固定服务器工具；不要在新版本验收前清理历史 Docker 镜像或回滚记录。
