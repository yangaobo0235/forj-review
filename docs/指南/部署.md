# FORJ Review Assistant 修改代码后重新部署完整流程

本文只记录从本地打包开始，到腾讯云更新完成的操作。没有测试、lint 和 Git 检查步骤。

## 固定部署信息

```text
腾讯云 IP：175.178.6.214
后端端口：18110
容器名称：review-agent-service
镜像名称：forj-review-api:main
服务器目录：/opt/review-assistant
上传目录：/home/ubuntu/review-agent-deploy
日志目录：/home/ubuntu/review-agent-deploy/logs
```

日志目录和发布包放在一起，排查时 `cd` 一次就够。容器内挂在 `/logs`，由
`start-review.sh` 每次部署时创建并放开写权限（容器用户和 ubuntu 不是同一个 uid，
不放开的话应用只会记一条 `Review log file disabled` 告警，服务照常但没有文件）。
文件按天轮转，最多保留 30 份：`review-agent.log` 是当天的，
`review-agent.log.2026-09-22` 是前一天的。

**时区**：容器默认 UTC，日志时间戳会比北京时间慢 8 小时，轮转切点也会变成早上
8 点。`docker-compose.server.yml` 里已设 `TZ: "Asia/Shanghai"`，镜像里装了
`tzdata` 提供时区数据文件——两者缺一不可，只有环境变量没有数据文件时 C 库仍
回落 UTC。部署后验证：

```bash
docker exec review-agent-service date
```

输出应是北京时间（CST），不是 UTC。

当前 2 核、1 GB 容器使用以下审核流水线参数，它们已经写在
`docker-compose.server.yml` 中，服务器 `.env` 仍只需要保存模型密钥：

```text
浏览器图片压缩/上传：不执行，只提交 DOM 图片 URL
二维码内存读取与解码并发：2
单个审核任务模型并发：8
全服务器模型并发：16（按任务公平轮转）
最终规则汇总并发：2
```

新插件使用 `/api/review/jobs/urls`，无需调整浏览器压缩或上传并发；汇总保持 2，
控制 LangGraph 12 节点与规则核验的 CPU 开销。

模型侧上限的真正约束是 DashScope 账号额度，不是这台 2 核 1 GB。后端日志出现
`rate_limited=true` 就是撞额度了，先降 `REVIEW_MODEL_GLOBAL_CONCURRENCY`：限流
超过一次重试会直接变成"识别失败转人工"，比慢更糟。

新插件一次提交所有图片 URL 后立即开始识别。普通文字字段由模型直接读取 URL；二维码字段优先使用同次模型返回的 `qr_codes`，模型没有可靠结果时，后端只对二维码候选图片 URL 在内存中执行一次 ZXing 优先、OpenCV 兜底的本地解码，再执行官网域名白名单核验。该读取不写盘、不上传、不进入普通图片链路。升级后重启服务并重新加载扩展。
后端与扩展需配套更新。图片上传接口已移除；`/api/review/jobs` 与 `/api/review/jobs/urls` 均只使用 HTTP(S) 图片地址。

项目不是 Java 项目，没有 JAR。对应的后端发布文件是：

```text
forj-review-api-main.tar
```

插件发布文件是：

```text
forj-review-extension-public.zip
```

## 推荐：日常一键打包和更新

每次修改代码后，在项目根目录执行：

```powershell
cd D:\fjkj\software\workspace\forj-review-assistant
.\scripts/release/package-server.cmd
.\scripts/release/package-extension.cmd
```

两个脚本会覆盖生成以下文件：

```text
.tmp/forj-review-api-main.tar
.tmp/docker-compose.server.yml
.tmp/forj-review-extension-public.zip
```

使用 Xftp 把 TAR 和 Compose 文件覆盖上传到：

```text
/home/ubuntu/review-agent-deploy/
```

本次升级需将下面两个脚本同步上传，之后脚本未变化时无需重复上传：

```text
deploy/start-review.sh
deploy/stop-review.sh
```

然后在 Xshell 执行一次：

```bash
cd /home/ubuntu/review-agent-deploy
chmod +x start-review.sh stop-review.sh
./start-review.sh
```

日常更新不要求先运行 `stop-review.sh`。`start-review.sh` 使用 Compose 的
`--force-recreate` 自动替换旧容器，并按顺序完成：保存当前镜像为
`rollback`、加载新 TAR、复制 Compose、重建容器和等待健康检查。

同一个发布包只执行一次 `start-review.sh`。连续执行两次通常不会产生两个容器，
但第二次会用当前 `main` 再生成 `rollback`，可能失去真正的上一版本回滚镜像。

只有需要明确进入维护停机状态时才执行：

```bash
cd /home/ubuntu/review-agent-deploy
./stop-review.sh
```

启动过程中偶尔先出现 `curl: (56) Connection reset by peer`，随后又显示
`Review Assistant started successfully.`，表示脚本第一次探测时应用尚未就绪，
后续已经成功，不需要再次运行启动脚本。刚启动时 `docker compose ps` 短暂显示
`health: starting` 也正常，Docker 自己的健康检查稍后才会更新。

下面“一至八”保留为脚本发生问题时的完整手动备用流程。

## 一、本地重新打包

打开 PowerShell，进入项目：

```powershell
cd D:\fjkj\software\workspace\forj-review-assistant
```

删除本地上次生成的发布文件，再创建输出目录：

```powershell
Remove-Item -LiteralPath .\.tmp\forj-review-api-main.tar -Force -ErrorAction SilentlyContinue
Remove-Item -LiteralPath .\.tmp\forj-review-extension-public.zip -Force -ErrorAction SilentlyContinue
Remove-Item -LiteralPath .\.tmp\docker-compose.server.yml -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force .\.tmp
```

### 1. 打包后端 Docker 镜像

先启动 Docker Desktop，确认左下角显示 `Engine running`。

执行：

```powershell
docker build --platform linux/amd64 `
  -t forj-review-api:main `
  -f .\deploy\Dockerfile .
```

导出镜像 TAR：

```powershell
docker save `
  --output .\.tmp\forj-review-api-main.tar `
  forj-review-api:main
```

### 2. 打包公网插件

必须使用 `build:public`，这样插件才会连接腾讯云：

```powershell
npm --prefix apps/extension run build:public
```

压缩插件：

```powershell
Compress-Archive `
  -Path .\apps\extension\dist\* `
  -DestinationPath .\.tmp\forj-review-extension-public.zip `
  -Force
```

复制服务器 Compose 文件：

```powershell
Copy-Item `
  -LiteralPath .\docker-compose.server.yml `
  -Destination .\.tmp\docker-compose.server.yml `
  -Force
```

查看生成结果：

```powershell
Get-Item `
  .\.tmp\forj-review-api-main.tar, `
  .\.tmp\forj-review-extension-public.zip, `
  .\.tmp\docker-compose.server.yml |
  Select-Object FullName, Length, LastWriteTime
```

最终得到：

```text
D:\fjkj\software\workspace\forj-review-assistant\.tmp\forj-review-api-main.tar
D:\fjkj\software\workspace\forj-review-assistant\.tmp\forj-review-extension-public.zip
D:\fjkj\software\workspace\forj-review-assistant\.tmp\docker-compose.server.yml
```

## 二、上传到腾讯云

在 Xshell 登录服务器后执行：

```bash
mkdir -p /home/ubuntu/review-agent-deploy
```

使用 Xftp 把下面两个文件上传到 `/home/ubuntu/review-agent-deploy/`，选择覆盖服务器上的同名旧文件：

```text
.tmp/forj-review-api-main.tar
.tmp/docker-compose.server.yml
```

插件 ZIP 不需要上传服务器，它用于发给朋友。

上传完成后检查：

```bash
ls -lh /home/ubuntu/review-agent-deploy
```

确认 TAR 不再增长后再继续。当前 TAR 通常约 250 MB。

## 三、替换服务器后端

以下命令都在 Xshell 中执行。

进入服务器部署目录：

```bash
cd /opt/review-assistant
```

确认服务器正式密钥文件存在：

```bash
test -s .env && echo '.env exists' || echo 'ERROR: .env missing'
```

必须显示：

```text
.env exists
```

首次从旧目录升级且根目录 `.env` 不存在时，先将原 `review-agent-service/.env` 复制到 `/opt/review-assistant/.env`，保留旧文件。此后更新不要上传、覆盖或删除正式 `.env`。

### 1. 删除更早的回滚镜像

服务器只保留一个回滚版本。先删除上一次遗留的 `rollback` 标签：

```bash
docker image rm forj-review-api:rollback 2>/dev/null || true
```

这条命令只处理本项目的 `forj-review-api:rollback`，不会删除其他项目镜像。

### 2. 保存当前线上版本用于回滚

```bash
if docker image inspect forj-review-api:main >/dev/null 2>&1; then
  docker tag forj-review-api:main forj-review-api:rollback
elif docker image inspect review-agent-service:main >/dev/null 2>&1; then
  docker tag review-agent-service:main forj-review-api:rollback
fi
```

### 3. 安装新 Compose 文件

```bash
cp /home/ubuntu/review-agent-deploy/docker-compose.server.yml \
  /opt/review-assistant/docker-compose.server.yml
```

### 4. 加载新后端镜像

```bash
docker load -i \
  /home/ubuntu/review-agent-deploy/forj-review-api-main.tar
```

查看镜像：

```bash
docker image ls forj-review-api
```

正常情况下会看到：

```text
forj-review-api   main
forj-review-api   rollback
```

### 5. 用新镜像重建容器

```bash
docker compose -f docker-compose.server.yml \
  up -d --no-build --force-recreate review-agent
```

旧容器会被 Compose 自动替换，不需要手工删除旧容器。

## 五、发布新插件

需要发给朋友的文件：

```text
D:\fjkj\software\workspace\forj-review-assistant\.tmp\forj-review-extension-public.zip
```

朋友首次安装：

1. 把 ZIP 解压到固定目录。
2. Edge 打开 `edge://extensions/`，Chrome 打开 `chrome://extensions/`。
3. 开启开发人员模式。
4. 点击“加载解压缩的扩展程序”。
5. 选择包含 `manifest.json` 的目录。

朋友更新：

1. 用新 ZIP 内容覆盖之前的插件目录。
2. 打开浏览器扩展管理页。
3. 点击插件的“重新加载”。
4. 回到已经打开的业务审核页，按 `Ctrl+F5` 刷新页面。
5. 关闭并重新打开侧边栏。

如果只重新加载插件、不刷新已经打开的业务页面，点击审核可能出现：

```text
Could not establish connection. Receiving end does not exist.
```

这表示当前业务页还没有注入新版本 Content Script，不表示腾讯云后端故障。

## 六、部署成功后删除旧发布文件

确认后端和插件均正常后，删除服务器上传的 TAR：

```bash
rm -f /home/ubuntu/review-agent-deploy/forj-review-api-main.tar
```

TAR 已经通过 `docker load` 进入 Docker，删除上传文件不会影响正在运行的容器。

如果上传目录存在密钥中转文件，也删除：

```bash
rm -f /home/ubuntu/review-agent-deploy/review-agent.env
```

正式密钥文件必须保留：

```text
/opt/review-assistant/.env
```

清理无标签的旧镜像层：

```bash
docker image prune -f
```

服务器最终只需要保留：

```text
forj-review-api:main
forj-review-api:rollback
```

检查：

```bash
docker image ls forj-review-api
```

不要删除 `interview-guide-*`、`refund-*` 等其他项目的容器和镜像。

## 七、出现问题时回滚

如果新后端上线后无法使用，把保留的回滚镜像重新设为 `main`：

```bash
docker tag forj-review-api:rollback forj-review-api:main
```

重新创建容器：

```bash
cd /opt/review-assistant
docker compose -f docker-compose.server.yml \
  up -d --no-build --force-recreate review-agent
```

检查：

```bash
curl http://127.0.0.1:18110/health
docker compose -f docker-compose.server.yml logs --tail=200 review-agent
```

如果只是新插件有问题，不需要动服务器。重新使用上一次的插件 ZIP，并在扩展管理页点击“重新加载”即可。

## 九、部署后快速排障

先在服务器确认后端，不要看到插件报错就反复执行启动脚本：

```bash
curl http://127.0.0.1:18110/health
docker compose -f /opt/review-assistant/docker-compose.server.yml ps
docker compose -f /opt/review-assistant/docker-compose.server.yml logs --tail=200 review-agent
```

判断顺序：

1. `curl` 返回 `{"status":"ok"}`：后端已可用，继续检查插件和业务页刷新。
2. 容器为 `Up (health: starting)`：等待 Docker 健康状态更新；只要 `curl` 已成功即可使用。
3. 容器反复重启或 `curl` 一直失败：查看日志，不要再次覆盖 `rollback`。
4. 插件显示 `Receiving end does not exist`：重新加载插件并刷新业务页面。
5. 插件显示 HTTP、上传或任务失败：确认公网健康接口，再按任务阶段排查。任务阶段说明见[审核流水线文档](../概念/审核流水线.md)。

## 十、取性能数据

每完成一单，日志里会留下一行四段耗时分解：

```bash
grep "review job timing" /home/ubuntu/review-agent-deploy/logs/review-agent.log
```

```text
review job timing job_id=... status=COMPLETED images=16
  recognize_ms=23440 finalize_ms=1830 total_ms=25270 peak_rss_mb=712
```

| 字段 | 怎么用 |
| --- | --- |
| `recognize_ms` / `finalize_ms` | 分别定位识别与汇总耗时；并发受模型额度和 CPU/内存约束 |
| 重试 | 从模型调用日志和结果中的 `retry_summary` 查看；任务计时行不再输出重试次数 |
| `peak_rss_mb` | 进程历史峰值内存；偏高时检查二维码原图尺寸与活动任务量，旧上传并发参数已不存在 |
| `rate_limited=true`（在 `review qwen call completed` 行里） | 撞 DashScope 额度了，先降 `REVIEW_MODEL_GLOBAL_CONCURRENCY` |

单张图的材料类型判定看 `Agent image completed` 行：`category_hint`（前端从页面
文案判的）和 `type`（后端实际采用的政策）不一致，就是类型串到了别的业务。
