# 新增审核业务与页面手册

普通页面、材料和审核字段调整，优先使用[声明式页面配置](声明式页面配置.md)。它支持一份 JSON 接入新页面或继承现有版本，自动生成采集、提取和字段路由。以下内容说明底层 Python 扩展包，主要用于维护原生业务或开发新的特殊能力。

本手册说明如何接入一个新的审核业务或一个新的审核页面。核心结论：

> **一个业务的全部配置是一份声明，位于 `src/forj_review_assistant/businesses/packs/<业务>.py`。**
> 新增业务 = 写这份声明 + 登记。前端零改动。

`docs/业务/` 下的地区业务文档解释**当前判断是什么**；本手册解释**如何新增**。

---

## 一、先判断属于哪一种

| 需求 | 要写什么 | 要动前端吗 |
| --- | --- | --- |
| **新业务**（如车源审核） | 一份声明 + 注册 | 不用 |
| **新页面**（已有业务的新地区/新页面） | 在声明里加一个地区或补字段别名 | 不用 |
| **与已有业务共用地址的新业务**（如过户审核） | 声明中填写地址和页面特征，目录自动汇总 | 不用 |
| **新能力**（需要新的判断逻辑） | 声明里绑定 + 写一个 Handler | 不用 |
| **新页面结构完全不同**（DOM 差异大） | 声明 + 前端适配器 | 要 |

绝大多数情况是前两种，**只写声明**。共用地址的情况见第八节——它是唯一一种
「地址一样但业务不同」的场景，靠页面特征文案区分。

---

## 二、声明里写什么

结构定义见 `src/forj_review_assistant/businesses/packs/model.py`，完整示例见
`src/forj_review_assistant/businesses/packs/scrap_replacement.py`。声明由五部分组成：

### 1. 字段（`FieldDeclaration`）

每个字段声明：稳定键、中文标签、页面别名、页面区域、证据来源、比较方式、权威链。

```python
FieldDeclaration(
    key="old_vehicle.vin",              # 稳定键，只增不改
    label="报废车辆车架号",              # 面向审核员的名称
    section=OLD_SECTION,                # 后端分区
    aliases=("报废车辆车架号", "旧车车架号", "车架号"),   # 页面上的写法
    page_section=OLD_SECTION,           # 页面 DOM 区域
    section_required=True,              # 必须落在该区域，否则判歧义
    mode="PARALLEL",                    # 证据模式
    sources=("vehicle_license", "registration_certificate"),
    normalizer="vin",
    authority=(...),                    # 权威链，见下
    required=True,                      # 是否进入必审清单
)
```

**权威链**用于"某个来源说了算"的字段。链首是唯一比较基准，其余来源各按自己的
`match` 窗口与基准比对；链首缺失时转人工复核，不让位给下一条来源：

```python
authority=(
    AuthorityRule("qr_page", "二维码官网"),                    # 链首＝权威
    AuthorityRule("page", "申请页面", required=True),          # 页面缺失即人工复核
    AuthorityRule("image", "行驶证或登记证",
                  ("vehicle_license", "registration_certificate"), "suffix8"),
)
```

不需要权威关系的字段不要写 `authority`，走通用的多源比对。

### 2. 材料（`MaterialDeclaration`）

每类材料声明：材料类型、显示名、可读字段、读取指引、页面分组提示、允许出现的分区。

```python
MaterialDeclaration(
    document_type="registration_certificate",
    display_name="机动车登记证书",
    fields=("vehicle.owner", "vehicle.vin", "registration.covered_pages"),
    guidance="读取注册登记信息栏中的车辆类型、车辆识别代号……",
    hints=("登记证书", "机动车登记证"),          # 页面分组文字
    allowed_scopes=(OLD_SECTION,),               # 只出现在旧车资料区
    scoped_vehicle_fields=(),                    # 车辆字段如何跟随页面分区
)
```

`scoped_vehicle_fields` 表示"材料上的 `vehicle.X` 落到 `{当前分区}.X`"。**不在这里
声明、又没有显式路由规则的字段会被丢弃**——这是防止材料上的无关字段冒充领域字段。

### 3. 材料字段路由（`RouteDeclaration`）

材料上的字段名与领域字段名不一致时逐条声明；`{scope}` 按当前页面分区替换，一条规则
可以映射到多个领域字段：

```python
RouteDeclaration("invoice", "vehicle.owner",
                 ("new_vehicle.owner", "application.customer_name"),
                 scope=NEW_SECTION),
```

### 4. 地区（`RegionDeclaration`）

同一业务的各地区共用字段和材料，只有政策与页面地址不同：

```python
RegionDeclaration(
    Region.QINGDAO,
    replacement_policy=QINGDAO_REPLACEMENT_POLICY,   # 也可为 None
    admin_paths=("/scrap-replace-qingdao",),
    # 地址认不出来时的兜底（页面改版换了路径）。
    page_anchors=("车源审核", "行驶证信息"),
),
```

地区政策能力 ID 由地区推导（`{region}_replacement_policy`），不用单独声明。
**加一个新地区 = 加一个 `RegionDeclaration`。**

**业务不分地区时不要按地区拆声明。** 页面地址不同、规则完全一样时，用一条
`Region.DEFAULT` 声明把多个地址都列进去（车源审核是一个地址，一致性与过户
是一条声明两个地址，见第八节）。按地址拆成多个地区声明会让同一套规则出现
多份 Profile，改一处漏一处会静默地只对某个地址生效。

`page_anchors` 是**页面特征文案**，只在两种情况下起作用：地址改了版认不出来，
或者这个地址被多个业务共用（第八节）。地址唯一的业务不必声明——按内容判定
反而会被共享的侧边栏和跨业务公共区块带偏。声明了就要**全部命中**才算数。

### 5. 能力与页面动作

```python
capability_specs=( CapabilitySpec("material_completeness", kind="MATERIAL", ...), ... ),
binding_declarations=( CapabilityBinding("material_completeness"), ... ),
page_action_ids=("fill_affiliation_fields",),
page_interaction=True,
# 规则结论投影成页面字段的核验条目：(check_id, field)。
field_check_bindings=(("VEHICLE-MODEL-POWER", "vehicle.model"), ...),
# 审核字段就是声明的字段，页面上其他控件不进审核目录。
review_declared_fields_only=True,
material_policy=SCRAP_REPLACEMENT_MATERIAL_POLICY,
```

**每个能力都必须有对应的绑定**，否则服务启动时校验失败。

字段级回填还需要四处声明，缺一不可（详见 `docs/业务/车源审核.md` §9）：`page_action_ids` 里有一个已注册的页面写回动作、要允许写回的字段上标 `writable=True`、`writable_control_kinds` 声明已验证过的控件类型、以及 `identity_anchors` 声明页面指纹锚点。

- **没声明过控件类型的业务不限制**，这是给历史业务留的口径；新业务一律显式声明，只放开验证过的类型。
- **页面指纹锚点必须包含一个强锚点**（`*.vin` 或 `application.id`）。锚点一个都匹配不上时指纹是空串，页面写回和原图定位会在客户端被静默拒绝——报错信息不会指出是锚点写错了，只会表现为"点了没反应"。新业务接入时先确认锚点字段在该页面上存在。

两个可选声明的用途：

- `field_check_bindings`：规则结论默认作为独立任务出现在“页面外核验”里；希望审核员在字段视图里也能看到时，把结论绑到对应页面字段上。**绑定之后该检查不再出独立任务**，结论并进那一行——审核员在字段下面就能看到，不必切视图。合并由后端 `prepare_display_tasks` 按这张表做，前端不持有第二份。
  **字段既有页面值又有材料值时同样适用**（日期类规则就是这种：字段本身要核页面和材料，规则还要判时效），不是只在字段没有比对时才生效。——同一句话在两个地方各说一遍只会让审核员在「待处理」里把它处理两次；字段控件不在页面上时条目出不来，独立任务保留。多条检查绑到同一字段时按最坏状态合并理由，结论本身仍各自保留，每条检查自己的理由还会写进它的候选值（`CheckResultValue.check_reason`），工作台放进对应的候选框里。结论多、理由长的字段（车源的车型）尤其需要，否则审核员得在框和字段理由之间来回对照。
- `review_declared_fields_only`：默认 `False`——页面上未配置核验来源的控件会生成一条“请人工核对”条目，避免被静默忽略。新业务的审核范围就是声明字段时设为 `True`，否则工作台会被页面上大量无关控件淹没。

## 三、登记

在 `src/forj_review_assistant/businesses/packs/__init__.py` 的 `BUSINESS_PACKS` 里加一行：

```python
BUSINESS_PACKS: dict[BusinessType, BusinessExtensionPack] = {
    BusinessType.SCRAP_REPLACEMENT: SCRAP_REPLACEMENT_PACK,
    BusinessType.VEHICLE_SOURCE: VEHICLE_SOURCE_PACK,      # 新增
}
```

登记之后自动生效的部分：字段清单与标签、证据策略、材料白名单与读取指引、
材料字段路由、页面地址白名单、Profile、能力绑定、以及下发给前端的采集清单。

Profile 由声明生成（见 `src/forj_review_assistant/businesses/profiles.py` 的 `build_profile`；
`build_scrap_profile` 是它的报废置换包装）。未声明扩展包的业务走
`rules_configured=False` 的降级路径，返回"规则尚未配置，请人工复核"。

分区归属由 `__init__.py` 的 `_validate_scope_ownership` 在启动期校验：
**同一业务分区不能出现在两个业务里**，否则按分区反查声明（`pack_for_scope`）
就会变成看声明顺序。字段路由只有业务分区可用，这一层保证它总能选对声明。

同一处还有一道 `_validate_all_pack_references`，校验声明内部的**每一个字段键引用**
是否都指向本业务已声明的字段（`src/forj_review_assistant/businesses/packs/model.py` 的
`validate_pack_references`）：路由目标（含 `{scope}` 展开后的每一个分区）、
组合字段的三个键、`field_check_bindings`、`identity_anchors`、`derived_field`、
`invoice_verification_field`、`material_field`，以及字段键与材料类型是否重复声明。
一次报出全部问题，不用改一处、启动一次。

**这道校验存在的理由**：这些引用写错时后果是静默的——那条观察值在
`field_policy()` 处被丢掉，审核员看到的是「该字段没有材料证据」，而不是
「配置写错了」。两种情况的处理方式完全不同。启动期直接失败并指出是哪个声明的
哪一处，比带着一个静默错误去审单子好。

两条因此必须知道的写法：

- **`{scope}` 会按分区展开，所以每个分区展开后的键都要存在。** 只在某一个分区存在的
  字段，必须在 `RouteDeclaration` 上写 `scope=` 限定，否则另一侧会展开出一个不存在的
  键。报废置换的注册日期、车辆类型、燃料类型都是这种。
- **只被规则读取、不进审核目录的字段同样要声明**（`mode=None`、`required=False`、
  `reviewable=False`、不加别名）。青岛政策的 `new_vehicle.origin` 就是这样：它没有页面
  控件、不参与字段比对，但字段键必须存在，否则产地判定会因为「没有证据」而静默失效。
  口径同过户审核的 `application.source_published_at`。

## 四、什么时候才需要写代码

只有三种情况：

1. **需要新的判断能力**：在 `src/forj_review_assistant/businesses/rules/<业务>.py` 写一个同步 Handler
   （返回 `RuleExecutionResult`），在 `src/forj_review_assistant/businesses/rules/catalog.py` 的 `RULE_DEFINITIONS`
   里注册，并在声明里绑定 `CapabilitySpec` + `CapabilityBinding`。三处缺一不可：
   **没有注册表条目，`BusinessRuleRegistry.validate` 会在启动期抛 `UnknownBusinessRule`**。
   超时、重试和失败策略由 `CapabilitySpec` 声明，不需要写在 Handler 里。
2. **页面 DOM 结构完全不同**：现有采集器按中文别名 + 页面区域匹配，多数页面
   只需要在声明里补别名。结构差异大时才需要前端适配器。
3. **需要新的展示形态**：在 `apps/extension/src/features/review/ui/workbench-renderers.ts`
   注册新的 Renderer。通用任务用默认渲染器即可。

如果新业务要改动引擎侧的投影表（`field_policies`、`fields`、`materials`、
`completeness` 的中文标签、`service` 的槽位表），先确认它们是否已经按
`BUSINESS_PACKS` 合成——合成之后新增业务不需要再碰这些文件。

**主图（`src/forj_review_assistant/runtime/workflow/graph.py`）不按业务复制。** 只有生命周期本身变化时才改主图。

## 七、前端采集清单

后端通过 `GET /api/review/collect-manifest?business_type=...` 下发字段别名、
页面分组标题、材料分组关键词、上传槽位，以及**展示用的中文名**
（`fields[].label` / `materials[].label`）。前端在采集前拉取并应用；
已配置页面必须取得精确页面与版本的清单；拉取失败时阻止进入审核，提示重新连接与采集。

侧边栏和 Content Script 是两个独立的 JS 运行时，各自应用同一份清单：采集判定
（别名匹配、分区、图片筛选）发生在 Content Script，展示用的中文名（字段名、
材料名）发生在侧边栏。所以新增业务时**后端声明一次就够了**，前端不需要再各改
一份中文名表。

尚未声明扩展包的业务返回 404，浏览器可使用历史内置表进行识别与展示，后端保持未配置业务的人工复核处理。

清单与前端内置表的一致性由 `apps/extension/tests/collect-manifest.test.mjs`
锁定：它用后端生成的 fixture 走前端的真实查找路径，逐条比对结果。

## 八、页面识别：地址不够用时

### 问题

后台是**列表页不卸载、详情叠上去**的结构，同一个菜单下的详情页可能共用地址：

| 业务 | 地址 | 怎么进到页面 |
| --- | --- | --- |
| 一致性审核 | `/consistency-qingdao?showPageModel=1`<br>`/consistency-changchun` | 列表筛选「待一致性审核」，点操作列的「一致性审核」 |
| 过户审核 | 同上，两个地址完全一样 | 列表筛选「待过户审核」，点操作列的「过户审核」 |

两边的 URL 一模一样，`document.body.innerText` 里还混着侧边栏菜单、列表页和
底部版权——**光看地址和「页面上有没有某个词」都判不出来**。

这两个业务还**不分地区**：青岛和长春两套页面用的是同一套规则，所以它们和车源
审核一样取 `Region.DEFAULT`，两个地址挂在同一条声明上。地区维度只在报废置换里
有意义（两地政策不同）。

### 配置在哪

页面识别声明由 `src/forj_review_assistant/businesses/page_catalog.py` 汇总，随
`GET /api/review/page-catalog` 下发给浏览器。**有扩展包的业务不用在这里写**：
地址和特征声明在 `RegionDeclaration` 里，`active_identities()` 会从活动 Profile 自动汇总：

```python
# src/forj_review_assistant/businesses/packs/transfer.py —— 过户审核
RegionDeclaration(
    Region.DEFAULT,                                    # 不分地区
    admin_paths=("/consistency-qingdao", "/consistency-changchun"),   # 与一致性审核共用
    page_anchors=("审核过户凭证", "过户发票买家名称", "转入地车管所"),
),
```

**还没有扩展包的业务**（当前只有一致性审核）在 `page_catalog.py` 的
`_DECLARED_IDENTITIES` 里显式声明一条 `PageIdentity`，字段一样。等它有了包，
把这一条删掉，改在声明里写。

两个业务的地址完全重合时，`identities_for_path()` 会返回**多条**候选——这正是
本模块存在的理由，`context_validation.py` 校验请求的业务/地区在候选集合里；请求
携带 `page_id` 时还必须匹配该路径的页面身份，不要求共用地址只有一个候选。

接口**必须独立于采集清单**：识别发生在「按业务类型取采集清单」之前，识别不出
来就不知道该取哪份清单。所以它一次下发全部业务，不按业务类型查。

### 判定顺序

1. **先地址**。命中的声明只有一条 → 就是它。地址唯一的业务（报废置换、车源）
   到此结束，不看内容——按内容判定反而会被共享的侧边栏带偏。
2. **地址撞在一起时看特征**。在共用该地址的声明里筛「特征全部命中」的，
   恰好一条才算识别成功。
3. **地址一条都不命中**（页面改版换了路径）→ 全表按特征兜底，同样只认唯一解。
4. **给不出唯一答案就不猜**：返回「无法识别当前审核业务，请人工选择」。

「先地址后特征」是有意的顺序——反过来的话，一致性审核页上的「过户详情」页签
会让过户审核的声明也命中，两边同时成立。

### 特征怎么选

只能取**详情区**的区块标题和独有字段标签，并且要求全部命中。踩过的三个坑：

| 坑 | 说明 |
| --- | --- |
| **侧边栏菜单** | 「青岛一致性审核」这几个字在每张页面上都有（菜单项 + 页签标题），拿来当特征必然误判 |
| **方向相反的词** | 「过户」两个字只在**一致性审核页**上出现（有个页签叫「过户详情」），过户审核页反而没有 |
| **跨业务共用的区块** | 开票日期、发票代码、发票号码、开票金额、识别车架号、经销商在两个页面上**一模一样**；审核操作区（审核处理 / 通过 / 驳回 / 取消 / 立即提交）和底部版权也是 |

`tests/unit/businesses/test_page_catalog.py` 把这几条锁住了：共用地址的每条声明都必须有特征、
特征之间不得重叠、特征里不得出现后台公共文字。

### 浏览器侧

- 识别只认下发的清单（`apps/extension/src/platform/browser/catalog/page-catalog.ts`），浏览器不再维护地址表。
  清单不可用时退回内置表，而内置表**对共用地址只返回「认不出来」**——退回
  一个只有地址的表等于把「不猜」作废，它必然给出一个错误答案。
- **人工选择在自动识别认不出来时生效**（`apps/extension/src/platform/browser/identity/business-detector.ts`）。
  自动识别唯一且与人工矛盾时才拒绝——共用地址的两个业务自动识别本来就给不出
  答案，此时若还按「页面说了算」拒绝人工，审核员就永远选不进去。
- 侧边栏的业务下拉里，共用地址的两个业务都要列出来（`reviewPanelConfig.ts`），
  否则特征不全时没有退路。
- 加了新业务记得把 fixtures 重新生成一遍（`apps/extension/tests/fixtures/page-catalog.json`），
  它由 `page_catalog()` 产出，前端测试直接读它。
