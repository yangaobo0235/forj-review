# AI 与开发者改动准则

修改前先阅读 `概念/系统定位.md`、`概念/规则主图与能力.md` 和本文件，并检索现有调用链、注册表和测试。需求必须落到拥有该职责的目录。

| 需求 | 修改位置 |
| --- | --- |
| 后端协议 | `src/forj_review_assistant/contracts`、`src/forj_review_assistant/contracts` |
| LangGraph 生命周期 | `src/forj_review_assistant/runtime/workflow` |
| 业务配置 | `src/forj_review_assistant/businesses`、`src/forj_review_assistant/businesses/packs` |
| 审核能力 | `src/forj_review_assistant/capabilities` |
| 证据比较与聚合 | `src/forj_review_assistant/evidence/comparison` |
| 任务展示与建议 | `src/forj_review_assistant/presentation` |
| 页面采集 | `apps/extension/src/platform/browser`、`apps/extension/src/platform/browser/adapters` |
| 页面写回 | `apps/extension/src/platform/extension` |
| 工作台展示 | `apps/extension/src/features/review/ui` |

必须保持的约束：后端规则不下沉前端；DOM 细节不上移后端；主图不按业务复制；新增能力必须注册；普通新页面优先使用 JSON 和动态目录，仅新浏览器能力需要扩展 Adapter/Action；停用业务不能偷偷激活；页面写回必须身份校验、白名单、唯一性检查、回读和回滚；协议变更必须提供兼容转换和迁移测试。

主图、状态字段、公开协议和注册表 ID 属于架构面变更。修改前补充影响说明，修改后更新文档、契约测试和发布说明。完成定义包括实现、测试、lint/build、文档和可回滚路径。

## 修改步骤

1. 明确需求属于页面、协议、能力、规则还是基础设施，并定位唯一归属目录。
2. 搜索同类实现、注册表和测试，优先扩展已有抽象。
3. 先更新类型和注册契约，再实现逻辑，避免字符串拼接形成隐式协议。
4. 为成功、缺失、冲突、超时和权限拒绝补充测试。
5. 运行后端与前端完整检查，检查 `git diff --check`，同步更新相关文档。

## 评审问题

- 是否把业务判断放到了后端规则层？
- 是否新增了注册表条目和稳定 ID？
- 是否保持主图生命周期和响应形状不变？
- 是否为降级、人工复核和回滚提供可见结果？
- 是否扩大了页面权限、外部调用或敏感数据暴露？

涉及审核业务时，还必须检查 `docs/业务/` 下是否已有对应地区文档。若已有，修改代码必须同步更新该文档；若没有，先从 `docs/业务/业务文档模板.md` 创建独立文档，并在 `docs/概念/字段与判定规则.md` 和 `docs/索引.md` 中登记。业务规则文档必须同时记录后端判断和前端展示/写回行为，不能只记录其中一侧。

如果修改 Profile、注册表、能力绑定、子图、页面适配器、页面动作或 Renderer，必须在对应业务文档的“实现清单”中同步更新。文档应明确区分“当前运行时已经使用的实现”和“为未来拆分保留的扩展边界”，不能把尚未接入主流程的子图写成已经生效的生产能力。

## 常见需求的正确落点

“增加普通页面或修改字段”优先修改页面 JSON，并使用本地配置工具校验、查看差异及回放；新政策算法增加后端处理器和规则登记；“增加一个新的二维码服务”扩展 External Check Registry；“页面换了字段位置”优先修改采集绑定，超出现有 DOM 能力才扩展浏览器平台；“工作台要展示新的任务细节”优先使用任务协议和已注册的后端任务投影。只有出现新的通用生命周期阶段时，才讨论主图节点。

## 不允许的快捷做法

- 为了快速通过测试，把协议字段改成 `dict[str, Any]` 或忽略未知状态。
- 为了兼容旧客户端，在每个节点同时维护两套业务逻辑；兼容只能集中在 `contracts` 边界。
- 为了“用户体验”在前端把 `INSUFFICIENT` 改成通过，或隐藏降级原因。
- 为了修复页面写入失败，删除身份校验、回读或唯一性检查。
- 为了临时调试提交真实材料、浏览器 Cookie、接口响应或本地缓存。

## AI 生成代码的额外要求

AI 修改前必须先列出将触碰的目录、现有注册表和相关测试；生成后逐项核对职责边界。AI 不得自行创建新的顶层抽象、重命名公开协议、删除失败分支或恢复已删除的旧实现。无法确认业务含义时，应保留人工复核状态并在代码或文档中留下待确认点，而不是猜测一个默认通过规则。

## 测试与发布

### 测试分层

后端模型和协议测试验证字段与兼容转换；规则测试验证 `MATCH`（一致）、`CONFLICT`（冲突）、`INSUFFICIENT`（证据不足）和 `REVIEW_REQUIRED`（需要人工复核）；能力测试验证注册、超时和降级；工作流测试验证主图节点顺序、分支和最终任务；API（应用程序接口）测试验证 HTTP（超文本传输协议）契约。前端测试覆盖 Adapter（适配器）、Action（动作）、Renderer（渲染器）和工作流 wiring（连接编排）。

### 标准验证

```powershell
# 在仓库根目录执行
uv run ruff check src tests scripts
uv run python -m compileall -q src
uv run pytest tests -q
npm --prefix apps/extension test
npm --prefix apps/extension run lint
npm --prefix apps/extension run build
npm --prefix apps/extension run build:public
git diff --check
```

修改图片链路必须覆盖：仅 URL 输入、签名参数保留、同次模型提取字段及 qr_codes、无可靠二维码和非官网链接的人工复核、独立官网核验、公平调度、取消及工作台材料身份。确认旧上传、通用本地裁剪和 data URL 解码接口不存在；二维码官网核验允许且只允许使用受控的 URL 内存读取器（ZXing → OpenCV），不得把它扩展成普通图片处理分支或重新引入已退役上传链路。

停用业务和旧协议的测试**直接删除**，不要保留再跳过。按测试名静默跳过的机制会掩盖真实失败——本次重构就曾让一个防护测试（名字里含 `transfer`）从未真正运行过。需要临时停用某个测试时，用显式的 `pytest.mark.skip(reason=...)` 写在测试本身。

### 发布要求

提交必须通过测试、lint、构建和文档检查；版本变更记录协议、Profile、注册表和页面动作变化。发布前保存可回滚版本，确认停用能力仍为停用，确认 manifest 权限和外部服务配置未扩大。线上发现错误时优先回滚 Profile 或能力版本，再修复代码。

### 失败诊断

测试收集失败时先修复导入和协议迁移问题，再运行具体测试；不要通过删除测试或放宽断言来“修复”收集。出现单个 Profile 失败时，使用能力级 fixture 隔离问题，确认其他 Profile 和通用主图仍可运行。构建失败要区分依赖、类型、lint 和打包路径，记录可复现命令。

### 变更记录

每次发布记录版本、提交 SHA、启用的 Profile、能力注册表版本、协议兼容范围、数据库或配置迁移、已知限制和回滚命令。重大协议变更保留至少一个兼容窗口，并在窗口结束后删除转换代码和对应文档。

### 测试数据要求

测试 fixture 必须脱敏并标注来源类型。每个新增能力至少包含：最小成功样本、关键字段缺失样本、字段冲突样本、低质量材料样本、外部服务超时样本和重复请求样本。组合字段必须覆盖页面双值一致/冲突、材料冲突和双字段回填；旧车 VIN 必须覆盖二维码权威、后 8 位和二维码缺失/多值。涉及页面写回时，再增加页面身份不匹配、目标控件不唯一、回读不一致和回滚样本。

### CI 与本地差异

本地命令应与 CI 使用相同的锁文件和 Python/Node 版本。若 Windows、Linux 或浏览器环境产生差异，应在测试中固定时区、编码、排序和换行，而不是在代码中添加平台特判。构建产物和缓存不应进入提交；CI 失败日志只保留脱敏后的请求 ID 和错误类别。

### 发布闸门

以下任一项不满足时不得发布：公开协议没有兼容说明；Profile 引用了停用或不存在的能力；主图拓扑测试失败；页面动作缺少身份校验或回读；任何关键路径只有自动通过而没有人工复核降级；安全扫描发现凭据或扩大权限；文档链接指向已删除的旧计划。

业务规则发布还必须逐项对照对应地区文档：Profile ID 和版本、日期边界、产地匹配方式、材料清单、能力绑定、前端标签、任务 ID、页面动作和失败状态都要能在代码与测试中找到对应实现。文档中没有记录的规则不应直接上线。
