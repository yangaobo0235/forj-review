# 审核配置开发

## 维护边界

新页面由开发者接入；已有页面的普通字段及已开放的业务选项由手动工作台、CLI 或助手维护。三个入口共用完整配置编译、字段权限检查、候选预览、原始试采集事实检查、固定证据回放和版本发布逻辑。

正式配置位于本机 `forj_review.local` 的关系表：页面、版本、字段、材料、发布批次、发布明细和当前发布指针。JSONB 只保存有类型约束的嵌套声明，不保存文件名到文本的映射。线上 `public` 保持原样，两者不自动同步。详见[数据库设计](../数据/数据库设计.md)。

`businesses/packs/model.py` 只保留通用不可变运行模型。生产目录不再保存页面 JSON、旧业务全局策略或模板默认值；运行时必须显式使用数据库页面。`rules/`、`capabilities/`、`evidence/` 保留算法和执行能力。

## 完整配置 2.0

可运行示例：[完整 permit 页面](../../examples/page-config/permit.json)。当前只支持完整 2.0 页面，不再提供增量模板配置。独立测试夹具与目录说明见[测试组织](../../tests/README.md)。

| 配置部分 | 内容 | 日常字段维护 |
| --- | --- | --- |
| 页面身份、路径、分区、图片组 | `page_id`、业务、地区、版本、paths、sections、page_groups | 只创建新版本，不更换页面身份或布局 |
| fields | 字段键、名称、别名、定位、比较、证据路由和开发属性 | 普通字段可增删改；开发属性锁定 |
| materials | 材料名称、指引、分区和处理器输入 | 可组合已有识别能力；新处理器仍开发 |
| settings | 上传策略、地区政策、规则能力、组合字段、二维码和展示 | 优先用 set_material_policy / set_policy_dates / set_presentation；其余 set_page_options 仍受最终差异检查，算法元数据不能改 |
| 页面动作、身份锚点、可写控件 | 浏览器写回契约 | 仅登记动作、来源属性、转换器和控件；新字段默认不可写，授权须显式提出 |

2.0 不使用 `extends`、remove_fields/remove_materials 或增量规则开关。完整配置独立编译，不读取当前 Python 模板补齐字段或材料。未知嵌套属性会报错，布尔值必须是真正的 JSON 布尔值。

字段 `evidence` 的每条来源声明 material、材料 field、scope 和可选 group_order；它生成材料提取项及证据路由。新字段须有明确证据、有效比较方式和页面别名，多分区须指定 scope。

`SYSTEM` 表示当前只检查页面输入，不代表该字段永远由开发锁定。对于可审核、没有材料来源、权威链、派生引用或身份/规则/动作等专用依赖的普通输入，维护契约返回 `comparison_configurable=true`，可用显式 `set_field_comparison` 设置已有普通比较模式、非空材料来源与规范化方式。普通 `upsert_field` 不得隐式完成此转换；命令不改变 required/writable/reviewable 等权限。其余专用字段仍按实际依赖保护。`phone` 规范化只消除空白、括号、横线及显式 +86/0086 前缀，保留区号、分机与真实号码差异。

这类无专用依赖的普通输入也允许通过 `remove_field` 从审核配置删除；维护契约返回 `removable=true`。删除后不再进入审核采集清单、任务或回填目标，但不操作业务页面的真实输入框。带身份、规则、派生或其他实现依赖的字段仍禁止删除，不能仅凭 `SYSTEM` 模式判断可删或不可删。

材料 `guidance` 与 `details.scoped_guidance` 是可维护的读取和映射指引；修改分区指引须保留其他处理属性。派生关系等实现属性仍由开发维护；历史槽位属性仅保留版本兼容，不再用于猜测材料类型。识别提示词由固定协议与当前配置自动组合，模型只生成一份事实，由后端投影为原文 `raw_fields` 与用于比较的标准 `fields`，见[审核执行原理](审核执行原理.md)。

材料 `extra_fields` 与 `details.scoped_extra_fields` 仅保留处理器显式输入。普通字段的提取项从其路由生成，删除最后一个消费者才会消失。`evidence[].comparison=false` 表示只给专用规则提供输入，保留历史“路由存在但不直接比较”的语义，属于开发配置，日常编辑不能新增这种映射。

上传要求集中在 `settings.material_policy`，不会同时读取 `materials[].required` 等旧版简写。地区政策、比较权威链和不确定性保护继续由内核执行。

配置助手的调查工具保留完整原始结果，同时向模型提供字段、材料、页面选项和 Schema 定义目录。目录展示字段实际可编辑属性及依赖；`get_configuration.field_keys/material_types` 一次读取指定目标的正式声明、相关材料说明和维护限制，`read_draft.field_keys` 读取待改草稿字段，`read_tool_result` 按原始结果 ID 和 JSON Pointer 补查相关子树，只有子树仍过大时才分页。无需顺序读取源配置、可编辑配置、生效配置三份视图或全部 Schema。

模型上下文按完整工具调用组裁剪，重复且内容相同的配置调查只保留一份目录，较早的大段分页保留原始结果引用和游标；近期分页内容可直接读取。模型可见本轮剩余预算与连续调查计数，连续查阅而未形成修改、澄清或路线结论时提示先收口。完整事件与证据不随上下文裁剪删除，旧任务的目录从持久化原始结果重建。

`assess_route(CONFIG)` 必须提供具体 `operations`，复用实际编辑内核进行无写入预检；通用 Schema 支持某属性不代表目标字段允许修改。预检不改变草稿，也不代替业务口径、编译回放或发布验证。工具结果显式提供本次 `evidence_id` 供引用；分页结果的 `tool_result_id` 仍表示原始来源，不能混用供应商最初生成的调用编号。明确的普通属性修改可以直接通过受控编辑生成草稿，无需为了判路先调用预检。`LOCAL_CODE` 仍须引用目标配置和部署能力调查，不能因预算耗尽或一次失败作出该判断。

判路依据是目标配置的真实依赖、已有算法能否组合及操作预检，不是业务名称白名单。普通材料字段比较不要求存在同名专项规则。能力目录的 `code_execution=false` 只表示配置服务没有代码工具，不能据此认定配置无法表达需求；`rule_parameters=false` 和 Schema 禁止未知属性也不是所有修改必须转代码的依据。业务来源不明确时先调查或澄清，不能擅自将票面“电话”改成“购买方电话”或按页面值挑选候选。

本轮相同参数、草稿修订、需求修订与证据修订的成功只读调查复用原结果，保留原始来源和复用记录；任何相应修订变化后重新执行。两次连续复用或临近调用上限时，后续模型只获得编辑、澄清、决策、验证等收口工具；总预算不少于 8 次时预留最后 4 次用于收口。模型继续请求已收起的调查工具，或同一操作重复确定性失败三次，明确以 `EXECUTION_STALLED` 停止，保留依据，不转换为代码或复杂需求结论。

执行事实仍保存在 `cfg_task_run/cfg_task_event`。应用层为操作生成动作、实际结果与下一步摘要，界面按轮次和调用编号配对开始/完成；不展示原始推理，不为进展摘要额外调用模型。`GET /tasks/{sid}/events` 返回时间和轮次，支持 `after_seq` 增量、`before_seq` 历史分页及 `limit`（1—200）；`before_seq=0` 从最新记录向前读取，各页按时间顺序返回。处理记录请求 `include_messages=false`，避免将大段工具协议正文重复传给进展列表。原始旧记录没有业务摘要时明确标注，不能补造发现。任务视图的 `execution_summary` 投影本轮结果及已取得的依据。

消息的执行轮次来自事件表的 `run_id`。新一轮保留用户消息、业务回复、当前草稿、需求与证据引用，重新调查和决策，不继续模仿上一轮的工具翻页过程。提问或中断工具在新一轮得到结果时，其完整调用组仍一并保留，不能产生孤立工具回复。调用预算耗尽时区分“尚未生成修改”和“已有修改已保留”，恢复不等于已完成验证。

## 新增页面

1. 以完整示例建立新 `page_id` 和未使用的版本，编写字段、材料、布局与能力引用。
2. 若通用能力已经覆盖，只需配置；新算法、查询或控件才修改对应代码和能力目录。页面数据写入数据库，不再建立代码级页面注册常量。
3. 在脱敏固定证据上回放，实际页面检查识别、采集和必要的写回行为；更新业务说明。
4. 导出目标状态，在 `configuration.json` 的 `definitions` 添加新页面的完整声明，并在 `active` 指定初始版本，保留已有版本和页面选择，再执行开发 `import`。
5. 等待自动加载并核对实际版本。配置服务不提供新建页面入口。

## 检查、差异与固定回放

```powershell
uv run forj-review-service --page-schema
uv run forj-review-service --check-pages examples/page-config --json
uv run forj-review-service --inspect-pages .tmp/pages-work
uv run forj-review-service --compare-pages .tmp/pages-before .tmp/pages-after
uv run forj-review-service --replay-pages examples/page-config --cases examples/page-config/回放样例/permit-cases.json
```

`ReplaySuite` 要求固定 request、batch、expect；外部核验通过 external_results 固定输入，不发请求。expect 可核对 recommendation、comparisons、checks、capabilities、comparison_fields、manifest_fields、task_fields 和 writable_fields。样例预期由人工确定，助手不能修改。回放文件放子目录或独立目录，避免被当成根目录页面配置。

## 数据库结构迁移与隔离

本机两个后端均设置 Schema 为 `local`。线上 Compose 默认 `public`，不会随着本机配置自动变更。四张原业务表在 local 内有完整副本；查询不跨 Schema、不回退 public。

显式迁移入口保留已有关系结构版本 3 → 4 的转换：先备份自有表，再迁移页面历史、发布和参考导入台账；四张 forj_ 表及 ref_vehicle_model_key 既有源外键原地保留。更早的线上快照库不适用此命令。

```powershell
uv run python -m forj_review_service.interfaces.database_tools migrate --schema local --backup-dir .review-config/backups/local-to-v7 --apply
uv run python -m forj_review_service.interfaces.database_tools check --schema local
```

目标 Schema 必须已存在。版本 3 使用专用转换，版本 4 及以后按迁移注册顺序执行尚未应用的增量；已是最新版时拒绝重复执行。当前目标结构为 7，v4/v5/v6 环境须按顺序应用剩余迁移（005_configuration_tasks.sql、006_capture_evidence.sql、007_configuration_workspace.sql）后再运行新版后端；迁移不修改活动发布或补写历史验证。public 升级额外要求 `--allow-public`，本地流程不使用该参数。服务启动只验证结构与迁移摘要，不执行建表、数据转换或默认值播种。

### 追加结构版本与恢复

`forj_review_database/schema.sql` 是已发布的 v4 基线，摘要在 `schema.py` 中固定。即使只改注释，也不能重写基线或修改数据库摘要来消除不兼容；文档说明可以直接维护。CRLF 与 LF 统一计算。`schema.BASELINE_VERSION` 表示基线版本，当前目标版本由 `migrations.migration_history()` 最后一项决定。

后续需要结构变化时，在 `src/forj_review_database/` 下的 `migration_sql/` 增加编号 SQL（如 `005_add_column.sql`），并向 `migrations.py` 的 `UPGRADES` 追加 `Migration(5, 名称, 文件路径, 固定 SHA256)`。编号从 5 连续递增，路径相对模块目录，摘要按 UTF-8 内容和 LF 换行计算；已发布文件及注册项不可修改。SQL 只操作获准的自有表，不能自行 COMMIT、修改迁移台账、切换 Schema 或访问 public。同步更新 ORM、字段字典及受影响消费者，验证旧结构升级、新库初始化、失败回滚和源表保护。

服务启动检查所有受管理的 v4 及以后记录是否构成完整且摘要一致的历史；不会只看最大版本。v3 转换后保留的旧台账属于历史记录，当前代码不声称验证其旧脚本摘要。迁移工具先校验历史和文件，再备份、自有表升级、写台账并比较受保护数据与触发器；整个升级在同一事务中完成。新结构的显式初始化同样从 v4 顺序应用增量，普通启动不初始化。

升级前停止两个后端，先做目标库或 Schema 的完整 PostgreSQL 备份并验证可恢复，再执行 migrate 和 check。工具产生的 COPY/JSON 备份用于数据核对，不能代替包含结构、约束、序列和函数的完整备份。事务内失败会整体回滚，不需要手工修改台账。提交后需要撤销结构时，优先追加经过测试的修正迁移；需要恢复备份时停止写入，在独立数据库恢复并验证后切换到匹配代码版本，不直接清空当前 Schema 或改动受保护表。镜像回滚和页面配置回滚都不会自动降级表结构。

旧快照跨 Schema 初始化器已移除；新运行链路不依赖 `.history/`、`.receipts/` 或迁移标记文件。数据库发布历史由关系表管理。

## 现场证据与历史复用

新任务和继续聊天需要已保存的真实采集目录。采集契约2.0保存字段原值、图片HTTP(S)地址及原始分区/标签/定位；结构摘要排除原值与URL，内容摘要只表示目录，不是图片内容摘要。`blob:`/`data:`无HTTP来源时保存空URL和unsupported类型，不能提交二进制或账户凭据URL。

扩展只提交一次目录，不下载、上传或补存图片；浏览器预览按需请求原URL，材料分析直接向现有模型集成传URL。局部诊断不阻断调查，相关证据失败需补采/澄清，不误转人工设计。观察和失败尝试以事件记录capture、sample、URL摘要、时间与证据修订，不能把浏览器可见当作模型可访问。

`cfg_task_capture`保留任务的历史采集和语义映射。补采按标签、分区和定位给出唯一对应或歧义线索，不跨采集复用field_3/sample_3，也不自动继承旧图观察。实时试采集分别核对实例、URL、结构和记录身份；无法提取独立记录身份时保守核对原字段值。目录可在标签页关闭后用于调查，发布仍要求当前浏览器证明。

## 无模型 CLI 字段维护

先导出结构化配置，导出目录中的 `configuration.json` 是离线交换文件，不是数据库中的文件实体：

```powershell
uv run python scripts/dev/page_tools.py export --schema local --directory .tmp/pages-before
uv run python scripts/dev/page_tools.py prepare --directory .tmp/pages-before --output-directory .tmp/pages-edit --page-id vehicle_source:default --version manual.20261020.1 --operations operations.json
```

operations.json 是受限字段操作数组，例如：

```json
[{"op":"upsert_field","value":{"key":"vehicle.engine_no","label":"发动机号码"}}]
```

prepare 不写数据库，输出预览和 `plan.json`。页面身份与能力实现不能更换。普通字段命令保持保守权限；set_page_options、upsert_material/remove_material、set_field_permissions 仅允许已有契约内的明确操作，最终编译检查依赖和写回安全。RuleBinding.inputs/parameters 当前必须为空，不会接受后忽略。

在工作台导出候选和原始试采集事实，使用其中同一个候选版本进行准备与验证。`--candidate` 接收完整候选对象；工作台导出的包装对象需要取其中 `candidate`。

```powershell
uv run python scripts/dev/page_tools.py verify --directory .tmp/pages-edit --trial-json candidate.json --cases accepted-cases.json
uv run python scripts/dev/page_tools.py publish --schema local --directory .tmp/pages-edit --expected-revision 1 --backup-dir .tmp/pages-pre-save --trial-json candidate.json --cases accepted-cases.json --operation-id manualsave1
```

expected-revision 使用 export 返回的实际值。发布前复核页面现场、候选摘要、证明有效期、映射和固定回放；数据库基线改变则拒绝提交。模型调用与回放不持有数据库发布锁。成功回执在发布记录中保存；同一操作 ID 不能用于另一候选。

`import` 是开发接入入口，读取结构化导出目录，可新增页面与能力声明，但不能覆盖历史版本。普通字段维护使用 `publish`。CLI 不启动配置服务，也不调用模型。

## 历史回退与程序恢复

单页回退：工作台选择历史版本，或 `prepare --page-id PAGE --rollback-version VERSION`，再完成试采集、回放、验证和 publish。仅改变版本选择，不覆盖历史内容。

整批回退创建新的发布记录，引用历史批次的完整页面版本清单：

```powershell
uv run python scripts/dev/page_tools.py restore --schema local --release-id 1 --expected-revision 2 --backup-dir .tmp/pages-pre-rollback --operation-id rollback1 --trial-json rollback-evidence.json --cases rollback-cases.json
```

rollback-evidence.json 为 `{ "PAGE_ID": { ...原始 evidence... } }`，每个实际变更页面都须提供当前候选的试采集事实；回放集须覆盖这些页面的目标历史版本。发布命令代表人工明确执行，不由 AI 自动代确认。

版本、发布记录和旧字段不删除，当前 revision 继续递增。代码/镜像回滚不自动执行数据库降级。服务器旧代码仍读取旧 public 表；其更早结构的转换不在当前 3 → 4 迁移器范围内，未来上线须先独立安排迁移，不能把本地 Schema 名随包发布到线上。

保存后审核服务约每 2 秒检查新发布，编译完成后自动加载；编译失败保留旧快照，已启动任务使用原快照。数据库当前选择的发布不等于进程已加载；核对发布 ID、页面版本、有效摘要、内核版本和配置来源一致，才显示已生效。

## 服务接口与代码入口

- `businesses/page_config/schema.py`、compiler.py、state.py、maintenance.py：完整声明与字段权限。
- `runtime/configuration/publication.py`、verification.py、offline.py：共享预览与验证；`integrations/storage/` 管理关系仓储和结构版本；`interfaces/database_tools.py` 是显式数据库迁移入口。
- 配置服务通过 `integrations/review_kernel` 适配，审核核心不依赖配置服务会话或模型。
- HTTP：`/tasks/{sid}/draft`、mappings、trial、replay、validate、confirm；export 提供候选及原始证明。
- 正式保存返回 PUBLISHED，实际加载状态单独核对；`/api/review/configuration/loaded` 返回审核服务实际加载页面、版本、摘要、来源与兼容标识。


## 扩展与发布

浏览器的页面目录、字段定义、分区、材料关键词、显示名称和回填权限从审核服务活动配置下发，不再维护随包业务兜底表。服务或清单不可用时提示重新连接和读取；已清空的配置不能恢复历史字段或权限。配置试运行与正式采集使用相同解释器。

打包不导入或覆盖配置，服务启动从目标数据库读取。结构版本与表字段见[数据库设计](../数据/数据库设计.md)及[数据库字段字典](../数据/数据库字段字典.md)。框架或扩展代码更新后部署相应服务和扩展；只修改已支持的页面配置时发布后自动加载，重新读取业务页面即可。

## 聊天任务与执行边界

一个任务绑定已有页面及创建时的目标页面版本/内核指纹；不支持新增页面。创建必须关联保存目录，内联snapshot入口会先持久化。历史采集供调查，发布仍需当前现场、试采集和固定回放。其他页面发布不改变调查基线；最终提交在最新head上编译完整组合，生成匹配验证并执行全局CAS，同页冲突明确拒绝。

`revision`只跟踪草稿内容，`intent_revision`跟踪有效目标，`evidence_revision`跟踪现场/映射，`row_version`是每次保存递增的并发号。前端静止状态命令携带expected_row_version，执行中更正按需求版本核对，不能混用四种版本。`manage_requirements` 明确新增、更正、撤回和查询；被替代/撤回的目标保留历史，不参与当前验收。交互、路线、决策、验证及人工确认按版本核对；补充问题答案也进入需求资料。缺现场、澄清、环境失败和预算中断不等于无法实现。

消息与目标分开：一条真实消息可拆多项目标，查询不新增目标。局部更正/撤回只使相关目标及依赖判断失效，独立目标继续按属性预期核对；对象存在、删除和JSON指针值都可客观检查。新报告保存目标到属性前后值的检查结果；RESOLVED不能独立证明验收，审核语义继续要求冻结业务回放。能力说明从实际模型、编辑限制和内核注册生成，不存第二份能力数据库或自然语言白名单。

`assess_route` 必须引用实际目标配置和当前能力结果。配置可表达时组合语义操作，失败按原因有限修正；配置缺口记录为 LOCAL_CODE，线上不提供 HUMAN_HANDOFF 或代码执行工具。混合要求不能静默只发布其中一部分，全部有效目标都须有当前决策和独立验证。

模型上下文保留完整有效需求和有界消息，原生调用/结果成组选择；有效需求超出预算时明确停止，不截掉条件。大结果按原始调用 ID 分页读取，引用保留实际能力、操作与身份摘要，分页结果不再次折叠成引用。字段读取按 field_keys 聚焦，编辑/预览返回实际变更，COMPILED 只表示编译和依赖通过。数据库增量追加消息，以事件为模型工具结果的事实来源，避免每次写入比较整个历史。超过消息上限的工具结果在同一事务内写为 TOOL_RESULT_CHUNK，消息保留摘要引用；按分片序号、数量与完整摘要核对后读取，缺失明确报错。保留单条消息和载荷原有上限，工具工件另限 4 MB，不通过放宽约束容纳大结果。归档使用 CLOSED 并保留已存现场证据，恢复保留草稿，发布前重新验证；已确认保存先对账。

新验证保存实际起止时间、有效需求摘要、版本化验证上下文及 15 分钟发布期限。验证上下文限制为 64 KiB，超限明确提示拆分需求。新报告的 kernel_version 是契约版本，kernel_fingerprint 是精确源码标识；legacy 保留旧语义，发布始终核对精确指纹。expires_at 只负责新报告清理，不延长旧证明。

### 工作台交互契约

`CreateTask.initial_message`与任务创建原子保存，服务核对真实采集与页面归属；`detected_page_id` 只表示扩展按当前服务目录唯一识别的页面，不能代替最终只读采集身份检查。界面先选择采集目录，再描述修改要求，无需逐项勾选字段或材料。

- `reference_fields/reference_samples`只表示调查引用，与业务目标、审核字段和验收覆盖分开；新任务不接受旧selected别名或required_samples选择意图。必传要求必须是独立目标并反映在material_policy；旧版离线正式证据仍按其契约校验，不改写历史。
- `messages` 携带草稿修订及可选 `expected_intent_revision`。运行中更正会先取消并等待旧执行结束，再核对需求版本、补齐取消的工具结果、清旧检查点并保存新消息；已确认发布冻结更正。只有解释为目标变化才递增需求版本，纯查询不销毁已有报告；尚未解释的消息仍阻止旧报告确认。
- `references` 只添加来自当前快照的引用，不直接修改配置。自动试采集须等待当前轮次停在浏览器交互，失败保留人工重试入口。
- `task_view` 是详情与历史列表共用的应用层投影，任务详情及候选导出也由该模块组装。`task` 和 `chat_messages` 是详情响应的必需字段，前端读取时校验，直接呈现后端阶段、需求覆盖、发布许可与业务对话，不回退原始消息或另算结论。仓储只提供持久化事实。发布面板绑定当前修订、需求与报告，变化后关闭旧确认。
- `activation` 将审核服务的实际加载事实持久化；`adoption` 将15分钟的指定浏览器任务绑定页实例、URL、页面、版本和有效摘要。扩展独立重新读取审核服务目录与清单，执行只读采集；后端再次核对身份、期限、加载状态与字段唯一性。新现场不替换已发布版本的原验证证据。
- `rebase` 先GET三方比较，再POST当前基线摘要与逐项冲突选择。字段按稳定key合并，嵌套对象按键比较，其余列表作为整体冲突。确认后创建关联任务，保留目标与非冲突候选，原任务不可变基线保持不变；保留已存现场作为调查依据，旧验证与发布确认不复用。
- `split` 只接受明确选出的部分有效需求及独立验收理由。原任务保留全部目标，新关联任务从当前活动配置重新准备，不复制原候选或发布证明。拆分本身不认定需求已满足，也不跳过发布校验。

任务、需求、执行轮次、交互分别保存至cfg_task/cfg_task_requirement/cfg_task_run/cfg_task_interaction。消息和工具结果增量写cfg_task_event，本地交付为版本化事件；task.context只保存小型工作上下文。每次新输入、恢复和发布有独立轮次；澄清/浏览器等待续用原轮次和预算。交互绑定需求、草稿、证据版本及候选/验证，原始确认只能来自可信HTTP操作。

数据库007迁移替换旧聊天表并删除图片二进制链路；005/006及历史摘要保持不变。正式配置、发布、长期验证和受保护目录不清理。迁移遇到已确认待对账发布时拒绝；先完整备份并隔离恢复/试迁移，再显式执行local升级。审核就绪仅依赖正式配置主干，配置服务另外检查聊天表，双方仍校验完整迁移历史。

`baseline_version`通过原始页面版本外键读取；preview可重建，不是发布证明。双栏工作台由后端投影阶段、覆盖和发布许可；前端只管理资料页签、局部滚动、输入引用与焦点。引用先进入当前任务的未发送输入，各任务隔离保存；发布面板绑定当前草稿、需求、证据及报告。
工作台“业务验收预期”优先直接回放已登记样例，读取固定输入并展示字段/规则预期；新预期须人工明确冻结为新ID。内核重绑定时只复制目标页面样例、修改执行版本，保留源输入与expect；回执同时记录不可变源摘要与实际执行摘要，不能靠改预期通过。复杂新输入仍由开发人员准备，非通用图像标注平台。

## 开发本地代码接续

在线上完成能力调查后，通过 `GET /api/review-config/tasks/{sid}/handoff` 或工作台按钮导出任务包。包包含需求、目标页面、配置候选/基线、能力缺口、验收和摘要，不包含原始现场、图片或模型载荷。包摘要用于核对内容，不授予任何执行权限。

开发人员先确定独立检查，准备依赖镜像，然后显式启动本地入口：

```powershell
# 镜像准备可以访问依赖源；后续候选检查没有网络和生产环境变量
 docker build --target local-validation -t forj-review-local-checks:dev -f deploy/Dockerfile .

uv run forj-review-config-develop --package task.json --repo . --output .review-config/local-tasks/change-1 --checks checks.json --image forj-review-local-checks:dev

# 中断后恢复；未知工具副作用须先核对，再显式 --reconcile
uv run forj-review-config-develop --output .review-config/local-tasks/change-1 --resume
```

`checks.json` 为开发人员冻结的非空数组，例如：

```json
[{"id":"normalization","argv":["python","-m","pytest","-q","tests/unit/evidence/test_field_normalization_cases.py"],"timeout":120}]
```

检查必须覆盖本次新增需求及相邻边界，不能只运行已有回归。代码 Agent 不能改写检查命令、已有测试或验证器。命令只按登记的 argv 在独立容器执行，镜像固定到本地 ID；容器无网络、无 Docker socket、无宿主环境变量继承，以非 root 用户和只读源码挂载运行，限制进程、内存、CPU 和临时空间。首版支持只读源码的 Python 检查；需要额外可写构建目录、数据库或外部接口的检查会显示待环境/未验证，需开发人员准备专用离线检查，不能把缺环境转为过于复杂。

任务使用独立副本带入实际工作区快照，包括受支持的未跟踪源码，排除忽略文件、私密配置和符号链接；记录原 HEAD、工作区摘要和文件清单，不修改原目录的暂存区、提交或未提交内容。工具限定源码、前端、契约及业务说明，用文件摘要和唯一原文执行修改；补丁相对任务快照生成。

产物为 `changes.patch`、`report.json`、可恢复的 `state.json` 和副本。`LOCAL_CHECKS_PASSED` 仅表示当前补丁的登记离线检查通过，仍需开发人员审查需求覆盖、实际页面/接口联调及部署。模型不调用 finish 时，执行器也会按当前候选与独立检查收口，记录停止原因；预算结束且已生成补丁时仍完成登记检查并保留结果，不伪称业务验收通过。

每次检查只登记一份带实际工具结果 ID 的证据；同一候选的检查回执在收口时复用，源码摘要变化后重新检查。检查通过不能覆盖显式的 NEEDS_INPUT 或 HUMAN_HANDOFF。容器清理须确认删除或不存在，失败时保留所有权标记并要求显式对账，不能覆盖遗留容器标记继续执行。

本地报告区分 NEEDS_INPUT、WAITING_ENVIRONMENT、BUDGET_EXHAUSTED、INTERRUPTED、UNVERIFIED_PATCH 与 HUMAN_HANDOFF。人工接续须引用实际调查并列出具体实现/验收障碍和决策项。恢复遇到未知工具结果停止重放；开发者核对副本后使用 `--resume --reconcile`，终止任务拥有的容器、登记未知结果，再重新调查。不要将本地任务目录或业务数据加入 Git。代码部署后重新读取目标能力、验证配置，才可回到配置发布路径。

开发本地任务结束后，在原LOCAL_CODE任务上传 `report.json`，`POST /tasks/{sid}/local-report` 核对实际导出包摘要与当前需求，按契约保留交付、文件、补丁摘要和调查/检查依据。格式不符、包过期或C缺少具体障碍与不同调查证据时拒绝。LOCAL_CHECKS_PASSED展示待评审补丁，环境/预算/中断保持等待；HUMAN_HANDOFF只表示人工接续材料已交付，需求尚未实现。导入不自动发布、应用补丁或部署；目标变化后重新调查与判路。
