# 页面漂移体检与修复提案 · 改造计划

> 状态：待评审。评审通过后按期次执行，每期独立可交付、可回滚。
> 范围：`review-agent-service` + `review-extension`。不改主图生命周期，不改审核判定口径。

---

## 一、要解决的问题

审核规则已经是声明式的（一份扩展包 = 全部配置），但**页面一变就要人工改 Python**。
具体三类：

| 变更 | 现在的表现 | 后果 |
| --- | --- | --- |
| 字段改名 / 标签换文案 | 该字段采集不到，表现为"没有材料证据"或"请人工核对" | 审核员以为数据缺失，实际是配置失效 |
| 字段新增 | 默认口径下生成一条"请人工核对"；**但过户、车源设了 `review_declared_fields_only=True`，会静默不采** | 审核范围静默缩小，无人报警 |
| 材料图换顺序 | 位置敏感的槽位推断（`分区:第几张图`）会静默判成另一种材料 | 材料类型判错，结论跟着错 |

**痛点不是"改起来累"，是"坏了不响"。**

## 二、现有地基（已核实，本计划复用它，不重造）

| 已有能力 | 位置 | 本计划怎么用 |
| --- | --- | --- |
| 声明 → 前端采集清单下发 | `packs/model.py:466` `build_collect_manifest`，经 `GET /api/review/collect-manifest`（`main.py:128`） | 体检的"声明侧"输入直接取它，不新建第二份 |
| 声明内部引用的启动期校验 | `validate_pack_references`，`packs/__init__.py` `_validate_all_pack_references` | 修复提案的**静态校验层**复用它，不另写一套 |
| 清单与前端内置表的等价测试 | `review-extension/tests/collect-manifest.test.mjs` + 各业务 manifest 测试 | 漂移夹具沿用同一 fixture 机制 |
| 页面识别的锚点兜底 | `businesses/page_catalog.py`，地址改版时按 `page_anchors` 兜底，给不出唯一解就不猜 | 体检的"走错页面"判定复用它 |
| 采集器的噪音过滤 | `page-field-collector.ts:538` `reviewFieldInventory`，已过滤搜索筛选/系统控件/忽略名单 | "未认领控件"候选集因此本身就是相对干净的 |
| 未配置控件的人工核对条目 | `presentation/routing.py:251,280` | 体检与它共用判据，不产生第二套口径 |

**结论：地基比预想的好。缺的不是校验器，是"漂移"这个概念本身。**

## 三、还缺什么（本计划的实际工作量所在）

1. 没有**漂移报告**：异常今天零散地体现在单次审核结果里（"没证据""认不出页面"），从来没有人把"这份声明 vs 这个页面"聚合成一张**精确到声明条目、告诉你该改哪一条**的报告。
2. 没有**候选建议**：别名匹配不上时，没有任何东西说"页面同区域出现了『车辆识别代号』，疑似该字段改名"。人还是得自己翻代码。
3. 没有**数据化修复通道**：所有修复都是改 Python，没有可审阅、可回滚、不需要发版的数据层。
4. 没有**漂移检测的评测集**：改对了没有，今天靠感觉。

## 四、设计原则（这一版和上次失败的尝试的根本区别）

### 1. 判卷人不交给模型

模型的任何产出都必须被一个**不依赖模型自身感知**的程序判定。这里有两层，都已存在或本次新建：

- **静态**：`validate_pack_references` + 漂移体检器（提案合入后重跑，残差必须归零）。
- **实证**：对真实案例跑一次**现有的**材料提取，看这份材料里到底有没有那个值、和页面对不对得上。复用 `workflow/service.py` 的提取链路，不新写视觉代码。

上次失败是因为"猜配置"和"验配置"看的是同一份模糊页面快照，每轮不产生新信息。这次证据来自一次真实提取，是**新信息**。

### 2. 拆成两个子问题，自动化程度不同

| 子问题 | 主导 | 模型的角色 |
| --- | --- | --- |
| **认领**：这个控件是不是那个字段 | 确定性打分（同节点文案变更 > 标签相似度 > 同区域同位置 > 控件类型一致） | 只在分数咬平时二选一，或回答"都不是" |
| **配规则**：这个字段核哪份材料的哪一栏 | **模型自由提案**，不受候选列表限制 | 提案 + 说明理由；由静态校验和实证校验判它对不对 |

模型不输出标签字符串本身——它只回候选编号，程序按编号把页面原文逐字回填。所以不存在"AI 把字段名写错"这类问题。

### 3. 证据能证明"对得上"，证明不了"该核它"

新旧车都有车架号、行驶证和登记证都有所有人——值都对得上，选哪个是业务口径。
所以终态是**模型提案 + 附证据 + 人确认语义**，模型无权拍板。

### 4. 权限是运行时强制，不是提示词恳求

模型的工具面里**不存在"写配置"这个动作**，只有"提交提案"。生效由人触发，落盘由程序执行。

### 5. 位置依赖要消灭，不是检测

字段认领靠标签不靠位置，所以字段换序天然免疫。真正危险的是材料图的隐式位置语义。
方向是**把位置依赖改成显式声明**（材料靠标题/标签认领），消灭问题而不是监控问题；消灭不掉的少数真位置依赖，只报不猜。

## 五、目标架构

```
审核员点「配置体检」（只读采集，不审核、不写回、不提交）
        ↓  页面快照（控件标签/区域/文档顺序/必填标记 + 材料图顺序）
┌────────────────────────────────────────────────────────┐
│ L1 漂移体检器  纯确定性，无模型，可单测                 │
│   renamed     声明别名失效 + 同区未认领候选（带打分依据）│
│   removed     声明别名失效且无可信候选                   │
│   appeared    页面出现审核区必填控件、无声明覆盖（分级）  │
│   moved       位置敏感声明的相对顺序变化（只报不猜）      │
│   unidentifiable  页面锚点丢失 → 走错页面                │
│   insufficient    区域未展开/截断/未加载 → 证据不足       │
│ 输出：精确到声明条目的报告 + 每条的证据与置信            │
└────────────────────────────────────────────────────────┘
        ↓
┌────────────────────────────────────────────────────────┐
│ L2 变异夹具评测集（判卷人，进 CI，不需要模型凭证）       │
│   真实脱敏快照 + 程序注入变更 → 断言报告恰好命中、不多报  │
└────────────────────────────────────────────────────────┘
        ↓  L1 报出的漂移 + 有限候选 + 现有声明上下文
┌────────────────────────────────────────────────────────┐
│ L3 修复提案 Agent（薄循环）                             │
│   工具：read_declaration / propose_patch / verify_evidence│
│         ask_user（≤4 选项 + 自由文本）                  │
│   无「写配置」工具；提案必须过静态校验 + 实证校验        │
│   预算：≤6 次模型调用、≤2 轮修复，超限输出三清单         │
└────────────────────────────────────────────────────────┘
        ↓
   人审 → 写入 override（进 git）→ 清单自动下发 → L1 复检归零
```

## 六、数据层：override 进 git

新增 `app/businesses/packs/overrides/<业务>.json`，在 pack 加载时合并，随
`build_collect_manifest` 自动下发到前端——**不需要改前端任何一张表**。

### 允许 override 什么（只做加法，不做口径）

- 给已有字段**追加别名**（改名自愈的主路径）
- 给已有字段改 `page_section` / `section_required`
- 给已有材料**追加 `hints`**（分组标题换文案）
- 新增"未认领控件 → 已声明字段"的认领关系
- 忽略清单：确认"这个控件不审核"，避免每次重复报

### 禁止 override 什么（必须走 Python + 评审）

删除字段、改字段 `key`、改 `normalizer` / `mode` / `sources` / `authority`、
改 `required`、改材料白名单、改地区政策与规则绑定。

理由：这些是**业务口径**，改错会造成错审而不是漏审。数据层只承担"页面适配"，
不承担"规则变更"。这条边界是本计划最重要的约束，防止 override 文件长成一个没有
测试的第二配置系统。

### 合并与校验

- 优先级：override > pack 声明；同 key 追加语义（别名、hints）为并集，不做替换。
- 合并结果**必须过 `validate_pack_references`**，引用不合法启动即失败，与现有口径一致。
- override 文件带 `source`（哪次体检、哪个人确认）和 `added_at`，可追溯到决策人。
- 回滚 = 删一条 JSON，不需要回滚代码。

## 七、期次计划

### P0 · 前置：一致性审核补扩展包

一致性审核目前**没有扩展包**（`page_catalog.py` 的 `_DECLARED_IDENTITIES` 手写一条顶着）。
没有声明就没有体检基准，也没有 override 可挂。

- 交付：`packs/consistency.py` + 登记 `BUSINESS_PACKS` + 删掉 `_DECLARED_IDENTITIES` 里的手写条目 + 按 `docs/指南/新增业务与页面.md` 第五节交付清单补齐测试与业务文档。
- 验收：`GET /api/review/collect-manifest?business_type=consistency` 返回 200；前端内置表由 fixture 等价测试锁定；启动期引用校验通过。
- **这是唯一有回归风险的一步**（一致性审核从"降级路径"切到"已配置"），所以单独一期、单独评审。

### P1 · 漂移体检器（无模型）

- 新增 `app/businesses/drift.py`：`inspect(pack_manifest, page_snapshot) -> DriftReport`，纯函数。
- 快照需要补两个字段（**唯一要动采集器的地方**）：控件的文档顺序序号、是否带必填标记。先验证 `controls`/`imageSlots` 数组是否已按 DOM 顺序输出，已有序则只补必填标记。
- 新增只读入口 `POST /api/review/drift-inspection`：接收快照 + 业务/地区，返回报告。不建任务、不落库、不进审核队列。
- 前端：体检按钮 + 报告展示（精确到声明条目 + 证据 + 置信）。
- 验收：`insufficient` 与 `removed` 能区分（区域未展开绝不报成"字段删除"）；`appeared` 只对"审核区内 + 必填 + 无声明覆盖"升级，其余进忽略清单，不刷屏。

### P2 · 变异夹具评测集（判卷人）

- 新增 `tests/test_page_drift.py`：一份真实脱敏快照 fixture + 四类注入变异（改名、删除、新增必填控件、交换材料图顺序），断言报告**恰好**命中注入项、无误报。
- 脱敏约束：夹具只保留标签与结构，清除字段值。**这同时是设计约束——体检器只依赖标签和结构，不读业务值**，隐私要求和架构要求同向。
- 验收：CI 绿；把 P1 的实现故意改坏（例如去掉位置判定），必须有测试失败。

### P3 · 数据化 override 层

- 新增 `packs/overrides/` + 加载期合并 + 上述允许/禁止清单的强校验（越界直接拒绝加载并说明为什么必须走代码）。
- 验收：改一条别名不需要动任何 Python、不需要重新构建前端；`build_collect_manifest` 下发结果含该别名；等价测试通过。

### P4 · 修复提案 Agent（薄循环）

- 新增 `app/services/drift_agent.py`：循环、预算、升级阶梯，**约 200 行以内，不引入运行时框架**。
- 工具四个：`read_declaration` / `propose_patch`（合入草稿 → 重跑 P1 体检 → 返回真实残差）/ `verify_evidence`（对当前案例跑一次现有材料提取，回答"这份材料里有没有这个值、对不对得上"）/ `ask_user`。
- 产出：一份 override 草稿 + 每条的证据与置信，**人确认后由程序写入 git**。
- 预算：≤6 次模型调用、≤2 轮修复、实证提取单次体检最多 N=3 个提案（成本上限）。超限输出"已解决 / 待人工 / 判不动"三清单。
- 多地区硬约束：同一变更必须在**所有已配置地区**分别复检；只有一个地区通过标为"部分通过"，不允许静默合入。

## 八、关键风险与对策

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| **误报** | 报三次"字段删除"实际是没展开，审核员再也不看这个工具 | `insufficient` 独立成类，证据不足**绝不**报成结构变更；P2 用注入测试把误报率变成 CI 指标 |
| override 长成第二套配置系统 | 无测试、口径漂移 | 严格限制只改页面适配，业务口径一律走 Python；合并结果过启动期校验 |
| 单地区验证通过就合入 | 把另一地区改坏 | P4 强制多地区复检，部分通过不合入 |
| 实证提取成本 | 慢、费 token | 只对疑似新增审核字段跑，单次上限 3 个，超出排队 |
| P0 让一致性审核从降级路径切到已配置 | 影响现网行为 | 单独一期、单独评审、保留降级开关 |
| 采集器改动引入回归 | 影响主链路采集 | 只加两个只读字段，不改现有匹配逻辑；有 `collect-manifest.test.mjs` 等既有测试兜底 |

## 九、明确不做

- 不做"全自动发现新业务/新页面配置"（上次失败的原因：没有判卷人）。
- 不驱动浏览器（审核员自己点到页面，只读采集）。
- 不引入 agent 运行时框架，不新建数据库，不改 `app/workflow/graph.py` 生命周期。
- 不让模型直接写任何配置文件。
- 不改审核判定口径、不改权威链、不改材料白名单。

## 十、从 pico-harness 借鉴什么（重写，不搬代码）

只借三个**观念**，按本系统形态自己实现：

1. **固定任务 + 验证器 + 重复运行比较** → P2 的变异夹具评测集。这是让"能不能收敛"变成分数的唯一办法，也是上次最缺的东西。
2. **权限靠运行时强制** → 模型工具面无"写配置"，只有"提交提案"。
3. **执行记录可回放** → 每轮提案、校验结果、证据命中与否留痕，能复盘"它当时为什么这么选"。

**明确不借**：agent 循环、上下文预算、trace 查看器、会话调度。本功能 90% 是确定性程序，模型只在两个点上出场（分数咬平时的二选一、配规则提案）。为它引入运行时是把简单问题复杂化——上次已经为此付过学费。

## 十一、可量化目标

- 一次页面文案变更：人工改动 Python 文件数 **1 → 0**（改为一处 override）。
- 漂移检出率 100%、误报率 <5%（P2 评测集在 CI 持续把关）。
- 新增字段导致的静默漏审：**归零**（含 `review_declared_fields_only=True` 的过户、车源）。
- 单次体检模型调用 ≤6 次，无模型时（P1 单独使用）0 次。

## 十二、待确认

1. **P0 是否现在就做**：一致性审核补扩展包是所有后续工作的前提，但它改变现网行为（从降级路径切到已配置）。要不要先只做 P1-P2（不碰一致性审核，只对已有包的三个业务做体检）？
2. **`review_declared_fields_only=True` 的两个业务**：体检要不要复用"未认领控件"这条通道，还是走独立入口？我倾向独立入口——避免把审核工作台的噪音策略搅动。
3. **必填标记的判据**：页面上是统一的 ant-design `*` 吗？如果各页面不一样，需要给我一个真实页面让我确认选择器。
4. **override 的评审人**：进 git 意味着走代码评审流程。你们能接受配置变更走 MR，还是希望有一个业务人员可操作的界面？
