# 数据库设计与数据字典

本项目使用 PostgreSQL，当前应用结构版本为 **7**，完整结构共 **28 张表**。审核服务按实际消费检查 **10 张表**，配置服务检查 **22 张运行表**；双方都验证完整迁移历史和摘要。本文说明表的用途、关系与维护规则；全部字段、类型、默认值、约束和索引见[数据库字段字典](数据库字段字典.md)。

## 配置与数据边界

| 类型 | 数量 | 表 |
| --- | ---: | --- |
| 正式配置主干 | 7 | cfg_page、cfg_page_version、cfg_page_field、cfg_page_material、cfg_release、cfg_release_item、cfg_head |
| 完成验证 | 1 | cfg_validation_run |
| 聊天配置工作流 | 8 | cfg_capture、cfg_task、cfg_task_capture、cfg_task_requirement、cfg_task_run、cfg_task_event、cfg_task_interaction、cfg_idempotency |
| 排放参考数据 | 1 | ref_engine_emission |
| 已停用车型参考数据（历史保留） | 2 | ref_vehicle_model_key、ref_dataset_import |
| 应用迁移 | 1 | sys_schema_migration |
| LangGraph 官方存储 | 4 | checkpoints、checkpoint_blobs、checkpoint_writes、checkpoint_migrations |
| 受保护业务副本（历史保留） | 4 | forj_vehicle_brand、forj_vehicle_series、forj_vehicle_model、forj_vehicle_model_config |

本机 local 与线上 public 是同一数据库内相互独立的 Schema。连接只设置目标 search_path，不回退 public，不跨 Schema 建外键。两个空间分别维护，不自动同步。四张 forj_ 表按受保护源数据使用，配置维护不修改其结构、数据或既有引用。

车型运行查询使用业务接口，不读取本地四张 `forj_`、`ref_vehicle_model_key` 或导入台账；排放查询仍读取 `ref_engine_emission`，运行就绪检查要求该表存在。仍严格检查运行表及不可变迁移版本/摘要；没有删除、重建或改写既有表。备份与历史迁移保护继续覆盖已有历史数据。

## 存储方式

页面稳定身份在 cfg_page，地区、启停、名称随不可变版本存放。每个字段、材料独立成行；页、字段、材料的嵌套选项用显式契约验证的 JSONB 保存，不存文件集合、SQL 或脚本。上传要求只由 material_policy 维护，不重复存放材料 required/minimum_count。

验证完成后独立写 cfg_validation_run，绑定候选、草稿修订、有效需求版本/摘要、现场、基线和内核。新报告的 verification_context 保存版本化需求、能力与样例摘要及检查覆盖；publish_valid_until 限定发布证据期限，expires_at 负责清理。旧报告按 legacy 上下文保留旧期限语义，不伪造历史需求。cfg_release 记录确认并引用验证，cfg_release_item 记录完整页面版本选择，cfg_head 原子指向当前目标发布。正式历史不可覆盖，已提交版本也不能追加子项。

一次 task 对应一个已有页面的修改任务。新任务必须关联已保存的真实采集目录，基线取创建时的活动正式配置，历史采集不回退正式版本。cfg_capture 分列保存页面来源、记录身份、字段原值、HTTP(S)图片地址与原始标签/分区/定位；目录不可改写，不保存图片字节、base64或伪造内容摘要。模型分析按需直接使用URL，观察结果带采集、样本、地址摘要及观察时间；URL变更不证明图片内容相同。

cfg_task 独占草稿与当前引用，cfg_task_capture 保存所有使用过的现场与已确认语义映射。cfg_task_requirement 独立保存目标、消息来源、修订、依赖、调查与验收条件，一句消息可以有多个目标。cfg_task_run 保存一次执行的输入版本、模型、预算、消耗和退出状态；澄清继续原轮预算，新消息或显式恢复创建新轮。cfg_task_interaction 保存版本绑定的澄清、浏览器取证或发布确认，原交互失效后不得复用。

cfg_task_event 追加保存消息、工具结果、交互答复和本地交付事实，已写事件禁止修改。context 仅保存有类型约束的小型工作上下文、映射决定与可重建展示投影，不另存整份消息、目标、运行或交付报告。候选preview只是缓存，发布、审核进程加载及浏览器采用分别记录；本地补丁报告不构成配置发布证明。正式完成报告独立保存，清理聊天不删除发布和凭据。普通幂等回执保存必要资源引用，永久发布operation_id仍在cfg_release。

不新增日常审核任务、识别结果或审核员操作历史表。审核作业和结果短期保存在内存，排障摘要写脱敏轮转日志。固定样例仍由人工维护文件，不建设通用样例或模型管理平台。

## 表关系与版本标识

| 对象 | 关系与用途 |
| --- | --- |
| cfg_page → cfg_page_version | 同一稳定页面有多个不可变版本，地区和启停随版本保存 |
| cfg_page_version → cfg_page_field / cfg_page_material | 字段、材料归属于唯一版本，不直接覆盖历史行 |
| cfg_release → cfg_release_item | 一次发布保存全部页面的版本选择，未修改页面引用原版本 |
| cfg_release → cfg_validation_run | 发布关联已完成验证，证据不依赖永久保留聊天 |
| cfg_head → cfg_release | 单行当前目标发布指针，revision 用于并发控制 |
| cfg_task_capture → cfg_task / cfg_capture | 保留任务使用过的全部现场与映射；仍被引用的采集不能删除，禁止关联其他页面 |
| cfg_task → capture / run / validation / release | 当前引用必须归属本任务；草稿只保存一份，正式发布独立保留 |
| cfg_task_requirement → cfg_task_event | 每项业务目标追溯原始消息及最近更正，依赖由应用验证 |
| cfg_task_run / cfg_task_interaction → cfg_task | 执行轮次和交互归属同一任务；事件、验证、响应通过组合外键限制归属 |
| ref_vehicle_model_key → forj_vehicle_model | 派生查询键引用既有车型，不改造源业务表 |

`sys_schema_migration.version` 是数据库结构版本；`schema_version` 是配置契约版本；`version_no` 是页面业务版本；`digest_version` 是摘要算法契约；`release_id` 是发布批次；`cfg_head.revision` 是全局发布并发号。任务的 `row_version` 是保存并发号，`draft_revision` 是草稿修订，`intent_revision` 是目标修订，`evidence_revision` 是现场与映射修订。这些值不能互相替代。最低框架语义版本门槛在 `minimum_kernel_version`，精确源码标识用于绑定验证与加载。

## 嵌套选项与代码边界

| 存储位置 | 保存内容 | 不保存内容 |
| --- | --- | --- |
| cfg_page_version.page_options | 路径、页签、分区、身份锚点、材料政策、地区政策、规则绑定、展示与已实现动作映射 | 字段和材料列表、已分列身份属性、文件集合、脚本、模型密钥与连接信息 |
| cfg_page_field.options | 别名、定位、证据路由、权威链、已有比较与任务投影选项 | 已分列键名、标签、审核/必填/可写权限的重复值 |
| cfg_page_material.options | 图片提示、分区、显式提取输入、上传槽位及分区覆盖 | 已分列名称与 guidance、独立的 required/minimum_count 上传要求 |

这些对象通过版本化类型模型验证，未知属性拒绝。`settings` 是完整逻辑声明的组织方式，入库时转换成明确的页级选项，不另存同一属性副本。完整配置示例和维护命令见[审核配置开发](../开发/审核配置开发.md)。

上传存在性由 `material_policy.presence_groups` 表达：组间 AND、同组方案 OR、方案内材料 AND；材料质量与页码由对应策略检查，OCR 失败不等于未上传。字段的 evidence 生成提取白名单和比较路由，不在多处手工复制。

`rule_bindings` 只引用代码登记的能力；当前 `inputs/parameters` 必须为空，不能存入尚未实现消费的参数。已有专用政策按对应类型执行。`actions` 只能引用已登记的处理器、来源属性、转换器和缺值策略；新增映射不自动授予目标字段写回权限。新算法、新控件和新接口仍由开发者扩展代码。

## 不可变历史与验证保护

正式页面版本、字段、材料、发布清单及完成报告不可修改，已保存父项也不能追加子项。修改配置创建新版本，回滚创建新发布。数据库通过唯一键、同页组合外键和触发器保护结构，应用进一步校验能力、候选与内核。

验证绑定当前候选、草稿修订、现场、基线发布与清单摘要；草稿或现场变化会使旧证明失效。发布只能关联用途、基线和清单相符、通过且未过期的验证。报告保留紧凑检查、试采集和回放证据，不复制全量草稿、现场、图片、模型响应或识别原文。开发 IMPORT 只证明编译检查，不能当成日常 PUBLISH/ROLLBACK 的业务验收。

普通幂等回执短期保留资源编号、修订和状态；同编号不同请求内容返回冲突。资源已清理时返回过期，不重新执行旧写入。发布 `operation_id` 永久保存在 cfg_release，不随普通幂等过期。消息和工具事件增量写入 cfg_task_event，按 seq 分页读取，不另存消息数组。超出单消息上限的工具结果复用同表 TOOL_RESULT_CHUNK，消息保存数量/摘要引用；原子写入和完整性核对避免大配置丢失，模型按需分页取证。

## 访问、发布与回滚

两个 FastAPI 后端共享 SQLAlchemy 2.x 映射与事务层，正常业务使用 AsyncSession。每次操作使用独立 Session，多次关联读使用一致快照；模型调用、浏览器等待、人工确认不占事务。CLI 同步维护复用 ORM；发布事务和就绪检查通过标准 AsyncSession.run_sync 与同步维护共用，删除自制生成器驱动；DDL、COPY 和官方检查点协议保留适合它们的专用方式。

服务启动只读检查表、迁移版本和脚本摘要，不调用 create_all、不播种页面。代码资源见 [schema.sql](../../src/forj_review_database/schema.sql)、[models.py](../../src/forj_review_database/models.py)。

发布后审核服务约每 2 秒探测 head，完整编译成功后切换服务快照；失败保留旧快照，正在执行的审核继续持有原版本。数据库提交状态 PUBLISHED 和进程实际加载状态分开。只改业务配置无需重启；改框架代码仍需更新并重启。

单页与整批回滚都创建新发布，不覆盖旧版本。日常发布、回滚必须试采集与固定回放；开发 import 只提供编译验证，不能冒充业务验收。配置回滚不恢复源表、参考数据或已完成页面写入。

## 维护与迁移

结构变更必须先备份，再通过显式迁移执行。迁移只操作明确的自有表白名单，保留 ref_vehicle_model_key 既有外键，前后检查四张业务表摘要及触发器；不能删除整个 Schema 后重建。备份放 `.review-config/backups/` 或服务器专用备份目录，不进入 Git 或发行包。

当前不可变基线为v4，目标为v7；显式迁移器保留3 → 4转换，再按顺序应用005、006、007。005/006历史脚本和摘要不重写。007先拒绝已确认待对账的旧发布，再替换旧聊天表、删除图片字节表，清理配置Agent独占的幂等与检查点工作数据，保留checkpoint_migrations、全部正式配置、发布、验证和保护表。正式验证的历史session_id/source_session_id列名继续保留，含义为来源任务，避免改写不可变历史。

迁移前停止旧写入服务，完整备份并在隔离库恢复、试迁移，核对正式/保护表及当前head；完成后验证两个服务重启及正式配置实际加载。跨实例逐行摘要核对应统一时间等会话表示参数。启动不自动升级；public默认拒绝迁移，本机不使用额外授权参数。审核服务不依赖聊天表与检查点是否存在，但仍要求当前受管理迁移完整。命令与适用条件见[审核配置开发](../开发/审核配置开发.md)。

临时数据每小时按引用清理：无引用现场 7 天、普通幂等 30 天、闭合任务结束后 30 天、未发布且不再使用的验证 30 天。闲置未发布任务 30 天后归档，草稿、需求与现场目录及观察保留到归档后 30 天；恢复时可以继续调查，发布前重新验证。已确认待对账任务不自动归档。被任一保留任务引用过的采集目录保留以支持恢复，试采集证明仍只有 15 分钟有效期；正式发布及其验证不自动删除。
