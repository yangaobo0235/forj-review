# 业务底座改造与遗留审计

## 结构结论

现有 `contracts / businesses / capabilities / runtime / integrations / presentation / interfaces` 分层和前端 `platform / features / shared / app` 结构可以保留。整体移动目录不能解决业务清单重复、静态枚举或目录与执行来源不一致的问题，本轮做职责内的局部改造。

新增 `businesses/configuration/`：

| 文件 | 职责 |
| --- | --- |
| `schema.py` | 严格的页面配置契约、可接受参数及结构校验 |
| `compiler.py` | 继承、字段变更、自动生成提取与路由、领域引用校验 |
| `loader.py` | JSON 读取、模板依赖排序、活动版本及启动快照 |

`businesses/rules/catalog.py` 负责内置业务处理器、输入字段、输出检查项与默认阶段；主图只依赖此装配入口。`review-pages/` 是业务配置交付目录，前端不加载可执行规则文件。

## 已处理问题

- 普通新业务不再要求扩展前后端固定业务枚举；已知枚举仍保留原实例语义。
- 所有原生业务包的地区声明自动生成 Profile，新增包无需再手工补活动 Profile 列表。
- 页面目录、采集清单、路由校验和审核运行使用同一服务注册表，支持独立实例和版本隔离。
- 字段新增只声明一次来源，编译产生提取白名单与路由，减少多表同步。
- 同业务多页面按 `page_id` 精确匹配；不明确的清单查询拒绝执行。
- 前端下拉原先过滤版本 `1.0` 的动态页面，现改为使用整个后端目录。
- 新材料类型通过清单识别，不需要追加前端物理材料枚举。
- 当前业务上下文路由失败时，不再意外退回报废置换业务包。

## 清理依据

对源码、测试和工具做了符号引用扫描、静态检查，并运行现有行为测试。静态扫描只用于提出候选，不能证明所有运行时路径都不存在。

| 对象 | 结论与处理 |
| --- | --- |
| `TRANSFER_LEGACY` | 不在运行时注册表，无迁移工具引用，唯一消费者是规则去重测试。移除旧“已停用”座位，测试改用实际存在的未配置 Profile |
| 前端旧四段 `config:` 解析 | 当前代码无生成者，也没有持久化读入路径；移除可能生成 undefined 身份的分支，无效标识明确报错 |
| 主图中的处理器导入与注册清单 | 迁入规则目录，不再要求新增后端业务处理器时编辑通用主图 |
| 静态目录接口的数据源 | 改为当前应用实例的注册表，消除与实际审核配置不一致的平行来源 |
| `PAGE_IDENTITIES / _pack_identities` | 生产路径已经使用活动 Profile，旧静态投影只被测试引用。删除平行目录，测试改验实际活动目录 |

## 仍需保留的兼容代码

- `BusinessProfile.external_checks / rule_groups / page_actions`：仍是测试和集成构造 Profile 的已支持边界，内部统一转换为能力绑定；没有向新 JSON 契约暴露它们。
- 旧字段别名、旧材料类型与二维码回退：仍处理受支持的采集请求，不能仅因名称含 legacy 就删除。
- 前端内置页面适配器、字段名与材料名：保留服务目录不可用时的历史识别或展示用途。已配置页面拿不到精确清单时阻止审核，避免将回退表当业务真相。
- `ContextMapping / ContextSequence`：当前确实被字段、材料及组合字段投影使用，同时保障并发页面隔离，不属于死代码。
- 证据差异展示、状态标签、DOM 控件校验：属于前端展示或页面执行，不负责决定审核通过与否。

## 后续扩展边界

普通业务接入修改页面配置；新算法修改后端处理器和规则目录；超出现有采集能力的控件由开发人员扩展浏览器平台。Agent 将来只需消费配置 Schema、规则目录和校验入口，本轮未增加 Agent 代码。
