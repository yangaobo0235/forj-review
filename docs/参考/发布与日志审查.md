# 发布与日志审查

本次检查范围包括根目录入口、`scripts/release`、Dockerfile/Compose、Ubuntu 启停与恢复脚本、服务启动、HTTP、任务调度、模型、二维码、LangGraph、能力、结论以及浏览器采集/回填诊断。业务规则和主图拓扑保持原有职责。

| 发现 | 处理结果 |
| --- | --- |
| 重构后打包实现迁到子目录，旧根命令失效 | 恢复两个根 CMD 委托入口，支持插件 `-Local` 参数 |
| 后端只交付镜像/Compose，容易继续使用旧部署脚本 | 同包交付启停、回滚、公共脚本、说明、发布身份和 SHA256SUMS |
| Windows 可选 PowerShell 模块不可用、中文 manifest 默认解码错误 | SHA256/ZIP 使用 .NET，JSON 明确使用 UTF-8；真实运行两个入口验证 |
| 重复启动覆盖真正的回滚版本；Compose 未随镜像备份 | 记录健康版本，保留镜像与 Compose 配对；失败后重试仍使用上一健康版 |
| 日志目录权限过宽、运行目录前置条件不清晰 | 固定新镜像 UID，按实际镜像用户准备日志属主/组权限，完善首次安装步骤 |
| Compose 固定并发导致服务端 .env 修改不生效 | 改为显式变量插值，保留 16/8/2 默认值 |
| 模块日志分散、部分 INFO 在生产没有处理器 | 应用命名空间和 Uvicorn 错误日志统一接入文件与控制台 |
| 仅按日期轮转，日内增长无上限；文件日志失败可被忽略 | 按天/大小轮转与归档数量限制，生产强制持久日志可写 |
| 异步队列、线程间缺少关联信息 | 每个提交项复制独立上下文，关联 request/trace/job/image 与业务版本 |
| 取消没有终态耗时，汇总排队混入执行耗时 | 每个终态仅记录一次，区分识别等待、识别过程、汇总等待与汇总执行 |
| 语义重试重置单图总计时起点 | 保留原起点，重试单独计时并记录结果 |
| 节点异常日志仍可能表现为完成成功 | 显式记录成功、失败、取消及异常类型 |
| QR 来源、解码失败与官网访问失败难以区分 | 解码与访问分阶段日志，保留来源、错误码、TLS/HTTP/重试信息 |
| 默认异常文本、浏览器 URL/标签/页面诊断对象可能携带业务数据 | 后端安全格式化与堆栈位置；前端技术字段白名单，去掉自由文本和完整链接 |
| 部署、日志文档描述旧上传流程和旧节点数 | 重写操作指南、日志事件表和排查路径，更新 README / 环境变量示例 |

验证覆盖 Python/扩展全量回归、架构边界、lint/build、真实 Windows 打包、生产 Docker 容器启动及日志、Shell 语法，以及模拟主机的升级/重复执行/失败重试/校验拒绝/启停/回滚。CI 增加生产镜像构建与容器验证，部署脚本回归随 pytest 自动执行。模拟主机测试不会接触线上服务，Windows 下仅用替身处理 Git Bash 缺失的 flock；Linux CI 使用真实 flock。

当前边界：未部署远程服务器；真实模型配额、外部官网可用性和业务页面写回仍需部署后用非敏感样例确认。应用日志是运行诊断，不替代完整审计数据库；浏览器日志仅在本地 Console。当前单进程文件轮转适用于现有部署，多实例需要独立文件或集中收集。详细操作见[部署指南](../指南/部署.md)和[日志与排查](日志与排查.md)。
