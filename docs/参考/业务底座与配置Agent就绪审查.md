## 结论

项目已经具备作为业务底座的主要结构：普通页面可以用声明式 JSON 接入，字段的采集、提取、证据路由和比较策略由同一条字段声明派生；页面共用审核主图和结果工作台。现有目录及主图可以保留，不需要再做一轮整体重构。

但还不宜直接让 Agent 自动修改并发布生产配置。当前主要缺口在配置变更后的语义校验、继承清理和版本发布边界。本次实际复现了三类校验通过但有效配置不完整或残留旧内容的情况。

这里的“前端不改”适用于现有采集器和控件执行器支持的页面。新的控件类型、跨 iframe 采集等浏览器能力，仍应由开发人员扩展平台层。

## 已经成立的架构边界

| 位置 | 当前职责及判断 |
| --- | --- |
| `businesses/configuration/` | 严格 Schema、JSON 编译、模板继承、启动快照；适合作为未来 Agent 的配置契约 |
| `businesses/packs/`、`businesses/rules/` | 不可变业务声明与专用算法；普通配置和算法扩展已有分界 |
| `runtime/workflow/`、`capabilities/` | 统一审核生命周期与能力调度；不同页面不需要复制 LangGraph |
| `evidence/` | 汇总证据、归一化及确定性比较，不依赖 HTTP 响应呈现 |
| `presentation/` | 生成任务、建议和响应；仍有少量既有业务的特殊任务投影 |
| 前端 `platform/browser/` | DOM 采集、图片分组、身份校验和受控回填 |
| 前端 `features/review/` | 展示后端任务与证据、收集操作，不负责材料完整性或最终审核裁决 |

已确认以下链路：

- JSON 不接受可执行脚本、导入路径或未知属性；字段、材料可使用新的稳定标识。
- 字段声明生成采集清单、模型提取白名单、证据映射和比较策略，避免手工维护多张平行表。
- 页面目录、精确采集清单和实际审核使用同一服务注册表；页面和版本不明确时拒绝猜测。
- 浏览器使用动态目录和清单，普通新页面不要求新增前端 Adapter；已配置页面拿不到精确清单时阻止继续审核。
- 业务上下文隔离不同页面的同名字段和材料，已有并发隔离测试。
- 审核主图保持 19 个正常节点及输入错误分支；页面差异来自 Profile、材料要求、字段策略和能力绑定。
- 结果工作台按任务协议复用；写回继续受字段、控件类型、记录身份和回读检查约束。

## 已复现的问题

### P2：只配置定位 ID 的必审字段不会进入采集清单

位置：`businesses/configuration/schema.py` 的 `FieldConfig`、`businesses/configuration/compiler.py` 的最终校验、`businesses/packs/model.py` 的 `build_collect_manifest`，以及前端 `page-field-collector.ts` 的别名匹配。

复现：新字段声明 `key=permit.name`、`label=Name`、`locator_id=person-name`，提供合法材料和 evidence，省略 aliases。编译和 `ReviewService` 装配均通过，`required_fields` 包含该字段，但 `manifest.fields` 是空列表。

原因：Schema 允许 aliases 为空，清单只收录 aliases 非空的字段；前端定位 ID 目前也是别名匹配的附加条件，并非独立采集入口。

影响：Agent 可能以为 ID 已足够定位，实际浏览器无法按该声明采集页面值，必审字段长期进入证据不足或人工处理。

建议：明确区分页面字段、材料内部字段和规则输入。要求页面取值的字段在编译期校验可采集绑定。若要支持仅 ID/name 定位，必须同时扩展清单和采集器；仅放宽清单过滤条件不够。材料内部字段不应被一概要求配置别名。

### P2：停用继承规则后，没有校验遗留检查绑定的生产者

位置：`businesses/configuration/compiler.py` 中 `disable_rules`、`declared_checks` 和必审字段校验；`businesses/packs/model.py` 中 `validate_pack_references`。

复现一：继承 `vehicle_source:default/1.0` 并停用 `vehicle_model_consistency`，编译和服务装配通过；能力只剩材料完整性，但 `VEHICLE-MODEL-POWER/CODE/EMISSION → vehicle.model` 三条检查绑定仍保留。

复现二：先新增一个 `required=true`、`mode=None`、绑定 `VEHICLE-MODEL-POWER` 的字段 `vehicle.model_assessment`，再在下一版本停用车型规则。新版本仍被接受，字段唯一声明的规则生产者已不存在。

原因：检查项生产者校验只遍历本次显式声明的字段，没有覆盖继承后的全部绑定；最终必审字段校验只检查绑定是否存在，没有确认绑定是否有效。

影响：配置依赖已断开，仍能通过“完整校验”。任务组装会跳过不存在的检查结果，可能回落为普通比较或人工复核。本次没有证明现有生产业务因此错误放行，不能把遗留绑定直接等同于误判通过。

建议：对编译后的完整配置校验检查项生产者。停用规则时报告受影响字段；必须明确删除绑定、补充替代证据或调整字段用途，不能仅因还留着一条字符串绑定就视为满足审核依赖。

### P2：继承删除字段或改来源后，提取白名单不断累积

位置：`businesses/configuration/compiler.py` 中材料合并及提取白名单生成。

复现：纯 JSON 基础版本声明两个字段，分别读取 `printed.name`、`printed.number`。子版本删除号码字段，把名称来源改为 `new.name`。有效字段和路由已正确清理，但材料提取白名单仍是：

```text
printed.name, printed.number, new.name
```

原因：继承的材料 `fields/scoped_fields` 已包含上一次自动派生结果，本次再次与新路由取并集，无法区分显式保留的规则输入与已经废弃的自动字段。

影响：字段删除不等于停止提取，旧字段持续进入模型提示词和返回契约，增加提取成本及干扰。本次复现的最终路由没有把旧值继续用于已删除字段，不能表述为必然比较错误。

建议：分别保留原生或显式提取字段、`extra_fields` 和由当前路由派生的字段，每次从最终有效声明重新计算。需要保留处理器专用输入，不能简单删除所有未出现在路由中的字段。

## 配置操作覆盖范围

| 变更 | 目前通常需要修改什么 | 边界 |
| --- | --- | --- |
| 新增普通页面 | 一个页面 JSON、对应验证样例 | 已支持的 DOM 结构及控件范围内，前端和主图无需改动 |
| 新增普通审核字段 | JSON 中一条字段声明 | 同时声明页面绑定和材料来源；上述可采集校验需要补齐 |
| 修改标签、来源、时效或归一化 | 对应字段配置 | 改来源后的提取白名单有上述残留问题 |
| 删除普通字段 | `remove_fields`，必要时显式更新依赖 | 身份锚点、组合字段及规则依赖不能随意删除 |
| 调整必传材料、数量或页码 | JSON 的材料声明 | 新材料名称、关键词、指引可声明；完整删除继承材料尚无 `remove_materials` |
| 启停已注册业务规则 | JSON 的规则开关、字段检查绑定 | 规则要求现有固定语义字段；不能自动把任意字段映射到任意算法参数 |
| 新增算法、外部核验或特殊派生逻辑 | 后端处理器、目录登记、配置及测试 | JSON 契约没有完整暴露原生业务包的所有能力 |
| 新增浏览器控件能力 | 前端浏览器平台适配及测试 | 适配完成后，各页面继续通过配置复用 |

原生业务包仍主要由 Python 声明，外部 JSON 是其上的受限编写入口。`review-pages/` 当前只有说明文件，示例在 `docs/示例/页面配置/`，需要部署时显式启用配置目录。本次没有读取真实 `.env`，不判断当前机器是否已启用该目录。

“一个页面一个文件”建议理解为一个页面版本的声明集中在一个 JSON 文件中。更新时新建版本并保留旧版本；使用继承时还需要保留精确模板及其依赖，不能只交付增量文件。

## 接入 Agent 前建议补齐的基础能力

以下是能力缺口与后续设计建议，不是已经复现的生产故障，也不要求现在实现聊天 Agent。

1. **先补有效配置校验和变更测试。** 修复上述三个问题，覆盖新增、修改、删除、规则停用、连续继承；验证编译后的完整结果，而不仅是输入 JSON 的格式。
2. **提供可读的有效配置及差异。** 现有 Schema、规则目录、页面目录和采集清单可复用；再提供继承展开结果、字段来源、依赖影响和结构化诊断，便于 Agent 在修改前后确认实际变化。可先做本地 CLI，不必立即增加在线写接口。
3. **强化版本不可变和发布边界。** 当前同一启动快照内拒绝重复身份，但外部文件被原地修改后，以同版本重启仍会接受；没有跨重启的内容校验与历史约束。建议保存源配置及有效配置的摘要、发布清单和历史，日志记录精确摘要。草稿校验、审批与整批切换分开，回退使用已验证的旧发布快照；多人修改增加基于旧摘要的冲突检查。
4. **增加离线回放和页面绑定验证。** 为每个页面准备脱敏 DOM、图片清单及固定识别输出，验证页面识别、采集覆盖、匹配/冲突/缺证据、任务及写回授权。配置变更应显示新增或消失的检查，避免“格式正确，但审核少了一项”。
5. **按实际需要补声明能力。** 优先补材料移除及影响诊断；有真实复用需求时再把专用规则的参数与输入绑定做成受限契约。不要为了覆盖任意业务而开放任意脚本。

将来的配置 Agent 可以独立承担“探查 → 澄清 → 草稿 → 校验 → 差异/回放 → 发布”的流程，输出页面声明。当前审核主图继续承担固定版本的审核执行。对话状态持久化及人工暂停恢复应放在配置流程，不能依靠现有内存审核作业代替。
