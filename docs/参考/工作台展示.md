# 审核工作台前端展示规范

`Workbench`（审核工作台）是展示任务和证据的界面；`Renderer`（渲染器）把 `ReviewTask`（审核任务）转换为组件；`PageAction`（页面动作）是经过授权的页面写回操作。本文只规定如何展示和操作，不重新计算后端规则。

本文档规定后端审核结果如何在浏览器扩展中展示、筛选、定位和执行页面动作。它是前端的展示契约，不是第二套审核规则。前端可以决定布局、标签、颜色、折叠状态和交互方式，但不得改变后端的状态、理由、证据或建议。

## 1. 展示目标

审核员打开工作台后，应能在很短时间内回答五个问题：

1. 当前审核是否可以继续，以及页面是否仍然是提交审核时的页面。
2. 哪些字段已经一致，哪些字段冲突，哪些字段证据不足。
3. 每个结论来自哪张材料、哪一页、哪个字段或哪个外部核验。
4. 当前还需要审核员处理什么，处理后会影响什么。
5. 哪些动作可以安全回填，回填是否成功并已回读确认。

任何只显示“通过/失败”而隐藏来源、理由、缺失和降级信息的页面都不符合本规范。

## 2. 页面整体结构

字段优先 Profile 使用统一工作台，推荐顺序如下：

1. **顶部摘要**：显示自动通过数量、已人工处理数量、待处理数量和当前页面状态；不展示“Agent 最终审核建议 / 建议人工复核”的大卡片。
2. **视图标签**：固定显示“待处理、全部字段、页面外核验”三个分类，数量为 0 时仍保留页签。材料完整性不生成展示任务、页签或卡片，也不参与任何展示计数；每个数量必须与对应分类的实际可见任务数量一致。
3. **任务索引**：按后端 `sequence` 或稳定任务 ID 排序，显示字段名称和状态。
4. **任务详情**：显示页面原始值、材料提取值、证据来源、理由、差异、高亮和动作。
5. **底部消息区**：显示回填、回读、回滚、重新采集和错误信息。

所有包含正式 `review_tasks` 的响应共用 `EvidenceReviewWorkbench`，不再按业务、地区或 Profile 版本登记不同组件。人工配置和生成配置都显示完整页面值、材料证据、规则依据、原图和受控动作。缺少任务协议的旧响应暂由 LegacyReviewResults 兼容。

任务可见性由后端 `TaskPresentation` 声明和 `ReviewTask.visible` 下发。材料完整性检查仅保留在后端报告和审核判定中，不生成展示任务；旧响应中的 MATERIAL 任务及 BUSINESS-MATERIAL-COMPLETENESS 在统计、筛选和选中任务之前统一排除。已退役的挂靠交互在置换定义中隐藏。机器结论和整单建议不因展示调整改变。

桌面宽度不小于 680px 时，索引约占 28%，证据详情紧邻索引，间距 10px；窄侧栏改为上下排列，索引限高滚动，详情保持可阅读。人工核对、页面回填和重新审核通过分别反馈；切换任务清除前一个字段的操作消息。

字段条目的分类标题按 `category` 取词（`CATEGORY_LABELS`）：`FIELD` → 页面字段、`BUSINESS_RULE` → 业务规则、`EXTERNAL` → 页面外核验。不要按业务名称写死。

## 3. 状态和视觉语义

| 后端状态 | 中文显示 | 视觉语义 | 是否允许自动通过 |
| --- | --- | --- | --- |
| `MATCH` | 一致/满足/通过 | 绿色文字或边框、成功图标 | 仅在所有阻断条件满足时允许 |
| `CONFLICT` | 冲突/不一致/不满足 | 红色文字、红色边框或左侧标记 | 不允许 |
| `INSUFFICIENT` | 待复核/无法校验/证据不足 | 橙色文字、警告标记 | 不允许 |
| `REVIEW_REQUIRED` | 待复核 | 橙色或中性色警告 | 不允许 |
| `MISSING` | 缺少材料 | 红色或橙色缺失标记 | 不允许 |
| `UNCERTAIN` | 识别不确定 | 橙色不确定标记 | 不允许 |

颜色不能是唯一信息。每个状态必须同时显示文字、图标或可访问标签；冲突不能只用浅红背景表示。建议区域还要显示“审核建议：通过”或“审核建议：需要人工复核”。

`MATCH` 只表示该项证据一致，不表示整单已经通过。顶部的整体建议必须由后端 `recommendation` 决定，前端不得通过统计绿色行自行计算。

## 4. 字段比较展示

字段任务至少展示：字段标题、页面原始值、材料提取值、来源名称、任务状态和后端理由。

- 页面值缺失显示“未采集”，不能显示为空白让审核员误以为没有该字段。
- 材料值缺失显示“未识别”或“没有可靠证据”，并解释是缺图片、读取失败、识别失败还是字段未提取。
- 两边值相同显示“字段一致”，保留可展开的证据来源。
- 两边值不同显示“字段冲突”，页面值和材料值同时保留，不能覆盖其中一个。
- 日期、车架号、车牌号等字段可以使用后端提供的规范化比较和差异范围；前端只能渲染差异，不能自己归一化后改变结论。

**每条材料候选值自带比对结果和比对说明**，与结论值同处一个候选框内，审核员不必读到字段底部的理由才知道是哪一条对不上：

| 显示内容 | 数据来源 | 空缺时 |
| --- | --- | --- |
| 结论值 | `CheckResultValue.value` | 不显示该候选 |
| 与页面是否一致 | `CheckResultValue.conflicting`：`true` → 「· 与页面不一致」，`false` → 「· 与页面一致」 | `null`/`undefined` 表示没有比对过，什么都不显示 |
| 比对说明 | `CheckResultValue.check_reason` | 为空表示该字段的结论不来自规则投影，不显示这一段 |
| 原图定位 | `image_id` / `image_index` | 没有可定位的图片时不显示按钮 |

`check_reason` 是产出该值的检查自己写的理由（“页面车型马力 430 与材料推导值 473、480 不一致”），由后端在投影时填好。**前端不得自己拼这句话**，也不得从字段理由里切分出来——字段理由用「；」拼接是展示格式，不是可解析的协议。同一个检查下的多条候选共用一句说明，不按候选拆句。

**已经被字段条目吸收的规则结论不再单出一张卡片。** 后端在投影成功时不把该检查的独立任务放进 `review_tasks`（依据是字段条目真的发出来了，不是声明里写过绑定），前端因此看不到重复条目，工作台也不为此再过滤一次。字段条目本身要完整承担展示责任：页面侧、材料侧、逐条说明、原图定位缺一不可，否则删掉卡片等于删掉结论。

**理由已经逐条搬进候选框时，底部整段理由不再显示。** 后端在投影时把 `details.reason_distributed` 置为 `true`；理由里多出检查没写过的一句（页面字段缺失或存在歧义）时置为 `false`，整段必须留着，否则那句话就没有别的地方可看。这个判断由后端给，前端不解析理由文本。

**「不一致」三个字标红。** 这是纯粹的呈现：把后端给的整句切分后给「不一致」加样式，不改字、不加字、不删字，也不因为染色改变任何状态；「一致」不标。标红不能只靠颜色——状态文字本身已经写明一致与否，颜色只是加速扫读。

`conflicting` 由后端逐条判定，前端只做映射，不得通过比较两侧字符串自行推断；后端给 `null` 时也不能显示成“一致”。这几项都是字段条目的通用规则，不按业务分支——没有投影来源的字段永远是 `null`、不显示说明、整段理由照旧，展示不变。

字段列表中的状态颜色、详情卡片中的状态和异常筛选必须来自同一个 `result_status`。禁止列表显示“通过”而详情显示“待复核”。

规则结论（`BUSINESS_RULE`）默认只有「材料提取值」区块。**规则自己带了页面侧取值时**（`ReviewTask.page_values`，如新旧车所有人一致性的两个页面所有人），卡片要先摆「页面原始值」再摆材料——审核员得先看到页面比出了什么。没有页面侧取值的规则结论**不显示这一块**，不能凭空渲染一行“未采集”。

规则通过检查结果 `details["page_values"]` 把页面侧取值交给任务装配（`_business_step` 取出后转成 `ReviewTask.page_values`，不再留在 `details` 里）。这样页面值不会混进「材料提取值」列表，而材料列表的过滤规则（丢掉 `申请页面字段`）保持不变。

**「页面原始值」区块下面可以有一句话**（`details.page_value_note`），由规则给出，用在页面上的几个值互相对不上时——此时没有候选值可以标红，不说明就只剩一个状态徽标。前端只渲染这句话，不自己拼。区块里没有这一项时不占位置。

## 5. 不一致和证据高亮

证据高亮由 `EvidenceFact.conflicting`、`differences` 和后端任务状态驱动：

- 有明确多数基准值时，只标出与基准不一致的证据片段，并标注“与基准值不一致”。
- 只有两条互相冲突的证据时，两边都要显示对方值，不能擅自选择一边作为正确值。
- 三条及以上全部冲突且没有多数值时，整条证据标记为冲突，提示“未形成多数值”。
- 没有差异位置时只显示值级别的冲突，不伪造字符级高亮。

高亮必须保留原文和来源。不能把高亮后的文本提交给后端，也不能把视觉上的多数值变成自动采用值。

## 6. 证据来源和原图定位

证据来源应使用稳定的中文标签：申请页面、机动车销售发票、机动车登记证书、行驶证、报废机动车回收证明、营业执照、身份证、二维码官网或图片证据。来源标签来自 `EvidenceFact` 的来源和文档类型映射，不根据图片文件名猜测。

每条图片证据在有 `image_id` 时提供“查看原图”。点击后应：

1. 在当前审核页面或受控预览中定位对应图片；
2. 尽可能滚动到原图并添加短暂高亮；高亮同时覆盖图片和它的可见容器——缩略图可能只有一百来像素宽，只给 `<img>` 描边在长列表里等于没定位；容器是 `body` 级别时只描图片，避免整页蓝框；
3. 显示材料类型、业务范围、分组顺序和来源；
4. 如果图片已经失效，显示“原图不可用”，保留后端证据文字，不伪造定位成功。

**定位结果必须回到审核员当前看的那张卡片旁**，不能只写进面板顶部的提示条：字段卡片通常在长列表的中间，顶部提示在视野之外，表现就是“点了没反应”。定位失败还要区分原因——页面身份失效、图片节点被框架重渲染后按地址找不到、消息发不到页面（标签页已关闭、内容脚本未注入），三者给不同的提示。

框架重渲染会换掉 `<img>` 节点（上传组件刷新、缩略图重新挂载）。节点的 `src` 没变就还是同一张图，按采集时记录的地址在页面上重新找一次，不要直接判成“原图已变化”。

原图定位只改变浏览器视图，不改变审核状态。图片二进制不能写入日志或公开错误消息。

## 7. 材料完整性诊断

后端继续返回 material_completeness 报告、原始检查和最终建议，用于缺料检查及审核判定；展示路由不再从这些诊断生成材料汇总或材料异常任务。所有业务（含生成配置）共用此契约。前端不展示材料完整性字段、卡片或页签，旧结果界面的材料汇总组件也已移除。

缺失证据仍通过受影响的字段显示 INSUFFICIENT；独立业务规则及外部核验异常仍按原状态展示。“展示项目已处理”只表示可见任务处理完毕，不能把它当成整单审核通过。

## 8. 二维码和外部核验展示

二维码任务显示解析状态、二维码来源、官网字段、域名校验、访问状态和失败原因。外部服务超时、不可访问或不确定必须显示降级提示，并进入人工复核。前端不得把“网页打开成功”显示成“业务核验通过”，只有后端 `CheckResult` 为 `MATCH` 才能显示满足。

## 9. 主体关系展示

后端继续计算主体关系；置换定义以 TaskPresentation 声明隐藏已退役交互，任务投影下发 visible=false。前端不自行维护业务专用排除名单。

后端主体关系规则和 `page_fill_intent` 保留为兼容契约；当前扩展不执行挂靠提议。无调用的旧挂靠写入器、消息协议、客户端和 hook 入口已删除。主体关系异常仍影响后端最终建议。

写入器保留页面身份校验、唯一性检查、原值校验、回读和回滚保护。写入失败会把整个会话置为 `STALE_PAGE`（页面已失效）并禁用全部回填按钮，因此改变这段行为前必须先确认页面控件仍然存在。

**「车辆所有人一致性」是另一条独立结论，不在排除名单里**：它判断的是新旧车所有人**是不是同一个主体**（`owner_consistency`），审核员要看，所以在「页面外核验」里正常显示。不要因为名字相近就把它当主体关系任务一起过滤掉。

## 10. 回填和页面定位

普通字段回填流程：

1. 审核员在任务中选择某条材料值，或手工输入候选值。只要任务绑定了 `page_target_field`（页面定位字段），即使任务在侧边栏以 `ASSISTANT`（助手任务）展示，也必须提供人工输入框；输入框初始值为页面原值，允许审核员修正页面值和材料值都不可信的情况。
2. “回填此值”按钮只在存在可写候选、任务状态不是 `MATCH` 且 `writable`（允许写回）为真时出现。按钮和人工输入框都调用同一个受控写回链路，不能各自实现一套 DOM 操作。

`writable` 由后端按三层判定，任何一层不满足都不显示按钮：**业务**注册了页面写回动作（`page_action_ids`）、**控件**本身可写（`ReviewFieldSnapshot.editable`）、**控件类型**在该业务的 `writable_control_kinds` 里。没声明控件类型的业务不限制（历史口径）；声明过的业务只放开列出的类型——写回器对下拉、日期这类复合控件的验证程度和文本框不同，没验证过的一律交人工填写。前端不得用 `control_type` 自行推断能不能写回。

浏览器侧还有同一份边界的**硬副本**：允许写回的字段与控件类型由采集清单下发（`writable_fields` / `writable_control_kinds`），清单之外一律拒绝写入。清单不可用时退回内置表。`writable_fields` 在后端单独成表，不能从清单的 `fields` 里筛——那张表只收录有中文别名的采集字段，挂靠这类只用于操作的字段同样允许写回。

3. 前端显示即将写入的字段和目标控件。
4. 写入前重新检查页面实例、采集批次、控件唯一性和原值。
5. 写入后回读页面字段，成功时显示“已回填并回读，已定位到页面字段”。
6. 页面目标应滚动到可视区域、获得焦点并短暂高亮约 4 秒，帮助审核员确认实际写入位置。
7. 回读不一致时显示失败原因并回滚，回滚后再次回读原值；恢复失败或页面失效必须提示人工核对，不能显示成功。自定义下拉只查该控件关联的选项列表，选项有歧义时停止。

前端按稳定 `action_id` 找执行器。**后端下发了前端没有注册执行器的动作时，必须给出可见提示**（面板提示「页面动作「X」尚未在前端注册，已跳过」），不得静默跳过：静默跳过会让「后端加了动作、前端没跟上」表现为「页面上什么都没发生」，这正是「新增业务前端零改动」最直接的破口。

发票代码/号码任务和新车车架号任务是组合字段任务。后端必须先比较页面两个原始值，再比较材料值；前端显示两个页面原始值。点击“回填此值”时，两个页面字段必须在同一授权动作中完成唯一控件校验、原值校验、写入、回读和失败回滚，不能只写入其中一个字段。

同一采集批次内，单字段和组合字段连续回填统一保留第一次回填前的身份锚点值，只更新最新已回读值。查看原图和后续页面动作仍据此验证原始页面指纹，不能把第二次回填前的值覆盖成身份基准。重新采集时清空回填记录并建立新基准；未经过受控回填的锚点变化仍判为页面变化。

开票金额回填使用字段级金额回读：`423000.00`、`￥423,000.00` 等等价格式在页面写回确认阶段视为同值；只有货币符号没有数字时按空金额采集。该规范化只用于 DOM 写回确认，不改变后端字段比较结论。回读失败仍必须回滚。

回填不调用模型或服务端。初次审核仍完整采集表单；回填守卫只实时采集业务清单的身份锚点，同一次校验复用同一份采集结果，不重复构建审核字段目录或匹配所有字段。字段别名索引随清单替换重新生成，只缓存定义，不缓存 DOM 值或唯一性判定；重复目标、页面身份、控件原值、回读和回滚检查继续执行。框架更新后的短暂等待保留，真实页面耗时需现场验证。

## 11. 页面失效和操作禁用

检测到页面刷新、标签页切换、业务身份变化、采集批次过期、目标控件变化或页面指纹不匹配时，工作台显示“页面操作已停止”，禁用所有回填按钮，并提供“重新采集并复核”。旧任务可以继续阅读，但不能继续写页面。

**页面指纹的锚点由业务声明**（采集清单的 `identity_anchors`），不能写死在浏览器里。指纹只收有值的锚点，并且至少具有 record_identity_fields 明确声明的记录编号；只有兼容旧清单时使用原有 VIN/申请编号规则，否则返回空串。空指纹会让**所有**页面写回和原图定位在客户端就被拒绝——这类"字段名对不上"的失效不会报错，只会表现为"点了没反应"，因此新增业务时必须核对锚点字段在该页面上真实存在。

**业务识别同样由声明驱动**（页面识别清单 `GET /api/review/page-catalog`）：地址唯一时按地址判定，地址被多个业务共用时（一致性审核与过户审核都走 `/consistency-*`）按页面特征文案在候选里筛，给不出唯一答案就**不猜**，提示"无法识别当前审核业务，请人工选择"。

- 侧边栏的业务下拉必须列出共用地址的**每一个**业务，否则人工没有退路。
- **自动识别认不出来时，人工选择生效**；只有自动识别唯一且与人工矛盾时才拒绝（防止用长春的规则审青岛的单子）。共用地址的两个业务自动识别本来就给不出答案，此时若还按"页面说了算"拒绝人工，审核员永远选不进去。
- 面板显示"当前：xxx · 人工选择／自动识别"时必须能区分这两个来源，方便判断是不是识别错了。识别不到时按钮禁用，不能带着空业务发起审核。

网络错误、协议错误和服务端失败要区分显示。网络错误提示可以重试；协议错误提示版本不兼容；业务失败提示人工复核。不能把三类错误统一显示为“审核不通过”。

## 12. 人工处理状态

前端可以记录审核员对任务的“已处理”或“标记人工复核”操作，但不能篡改后端原始 `MATCH`、`CONFLICT` 或 `INSUFFICIENT`。人工处理状态只用于工作台进度显示；最终建议仍以服务端结果和产品规定的人工确认流程为准。

## 13. 可访问性和一致性

状态不能只依赖颜色；按钮需要明确文字和禁用原因；原图按钮需要可访问名称；高亮文本不能依赖颜色区分。所有 Profile 使用同一套状态标签、证据标签、回填成功/失败文案和页面失效文案，地区差异只出现在业务名称、政策理由和材料要求中。

## 14. 变更要求

新增任务类型时，先确认统一 EvidenceReviewWorkbench 能否展示；不能展示时扩展按任务类型分派的详情组件，并记录输入字段、状态映射、证据展示、操作权限和空状态。不得在 `ReviewResults.tsx` 或地区组件中增加业务判断来修补后端结果。修改颜色、状态文案、筛选逻辑、证据高亮、原图定位或回填反馈时，必须补充对应前端测试和截图/交互验收说明。
