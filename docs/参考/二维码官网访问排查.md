# 二维码官网访问排查

## 已确认的问题

二维码识别、官网网络访问、官网字段解析是三个独立步骤。出现官网链接只说明获得了允许域名的网址，不代表官网已返回有效证明数据。

2026-10-15 排查中的审核样本由 ZXing 解码，官网域名有效；原审核访问失败，只执行了 1 次、约 2 秒。随后访问同一链接可返回 HTTP 200，并提取到 `certificate_no`、`vin`，因此不能把本样本的失败归因于模型编造链接或字段解析器必然不兼容。

网络对照出现过：默认 TLS 直连连接失败、代理访问成功、TLS 1.2 直连成功；后续默认 TLS 也能成功。这证明访问存在间歇性及路径差异，但不足以证明所有失败均由 TLS 1.3 引起，也不要求系统必须配置代理。

旧客户端只把 429/500/502/503/504 标记为可重试；连接异常、连接重置和超时直接结束。虽然业务配置允许重试 1 次，这些最需要重试的失败实际只请求 1 次。与此同时，异常类型被丢弃，最终统一展示“二维码网页无法完成核验”，历史日志无法进一步区分具体网络故障。

## 当前实现

`integrations/qr/web_verifier.py` 保留正常 TLS 协商和证书校验。暂时性网络异常、超时和上述 HTTP 状态最多再试一次，间隔 250ms。连接异常后的重试使用独立的 TLS 1.2 兼容客户端；HTTP 错误与超时重试继续复用原客户端。默认单次请求总时限仍为 8 秒，最多 2 次，不无限等待。

证书校验失败不重试、不关闭证书校验；非法网址、越界跳转、超大响应、缺少官网关键字段不通过重复请求伪装为成功。取消仍直接向上传播。

每次实际官网请求记录 `review qr web completed`，包含图片索引、官网主机、TLS 策略、尝试次数、失败类型、HTTP 状态及耗时。不记录完整二维码网址、加密令牌、网页正文或异常原文。重试摘要的 `reason_code` 记录当前尝试的实际失败原因，`strategy` 区分 `official_page` 与 `official_page_tls12`；这不改变公开协议形状或审核判定标准。

运行时通过已有 `QrCheck.message` 输出明确原因。连接失败、访问超时、HTTP 错误、证书错误、响应拒绝及访问成功但字段缺失各有说明；前端只展示结果，不承担访问或审核判断。官网返回 200 也必须提取完整编号和 VIN 才能成为官网读取成功，业务字段一致性仍另行比较。

## 再次失败时查看什么

查看后端 `logs/review-agent.log` 中的 `review qr web completed`：

| `error_code` | 含义及处理 |
| --- | --- |
| `connection_error` | 建连或传输失败；查看兼容重试是否成功，并在后端所在机器检查网络出口 |
| `timeout` | 请求超过时限；查看第二次结果及官网响应速度 |
| `http_status` | 官网已响应错误状态；按具体状态区分限流、拒绝和服务异常 |
| `tls_certificate_error` | 证书校验失败；检查运行环境的时间、证书链和网络代理，不关闭校验 |
| `redirect_rejected` / `response_too_large` / `response_rejected` | 响应不满足访问边界；人工核验后调整适配，不能跳过保护 |
| `fields_missing` | 网络已访问成功，但页面缺关键字段；区分错误页、页面结构变化与无效证明 |

旧任务结果不会因修复自动改写；后端重新加载新代码后，需要重新发起审核。新增回归使用合成网址和 MockTransport，覆盖暂时连接故障后恢复、超时重试、重试上限、证书失败、HTTP 分类、字段缺失及日志脱敏。
