# 日志与排查

当前日志分为后端应用日志、部署日志和浏览器本地诊断。后端负责识别、证据、规则、外部核验及任务生命周期；浏览器负责 DOM 采集与受控回填。浏览器诊断不会自动上传，服务器不能凭后端日志确认页面控件已写入成功。

## 文件与保留

| 日志 | 位置 | 保留方式 |
| --- | --- | --- |
| 生产应用 | `/home/ubuntu/review-agent-deploy/logs/review-agent.log` | 午夜或大小触发轮转，默认 10 MiB / 30 份归档 |
| 容器控制台 | `docker compose logs review-agent` | Docker json-file，10 MB × 3 |
| 部署操作 | `/home/ubuntu/review-agent-deploy/deploy.log` | 下一次操作发现超过 5 MiB 时轮转，保留 `.1` |
| 本地后端 | `.env` 中 `REVIEW_LOG_DIR`，通常为仓库 `logs/` | 同应用轮转策略 |
| 浏览器扩展 | 审核页与侧边栏各自的 DevTools Console，前缀 `[ReviewAgent]` | 浏览器会话控制台，不持久上传 |

归档按数量封顶，**不是保证保留 30 天**。繁忙时一天可能产生多份；应用文件通常约占 310 MiB 上限，单条超大事件、文件头及其他日志有少量额外占用。应用日志归档名带日期、时间和微秒，避免同日大小轮转覆盖。时区跟随进程，生产为 `Asia/Shanghai`。

所有应用模块统一使用 `logging.getLogger(__name__)`，由应用生命周期将 `forj_review_assistant` 和 `uvicorn.error` 接到相同控制台/文件处理器，防止主图与能力 INFO 丢失。正常健康检查和成功任务轮询不记录逐条访问日志；错误请求仍记录。不要重新启用包含原始 URL/query 的 Uvicorn 访问日志。

## 配置

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `REVIEW_LOG_DIR` | 未指定则仅控制台 | 文件目录；生产 Compose 固定 `/logs` 挂载 |
| `REVIEW_LOG_REQUIRED` | false | 生产固定 true，文件不可写时启动失败 |
| `REVIEW_LOG_LEVEL` | INFO | DEBUG / INFO / WARNING / ERROR |
| `REVIEW_LOG_MAX_MB` | 10 | 1–100 MiB，单文件轮转阈值 |
| `REVIEW_LOG_BACKUP_COUNT` | 30 | 1–365，归档数量上限 |

生产 `.env` 可覆盖级别和轮转数量，重新执行启动脚本生效。日常保留 INFO，改成 WARNING 会失去成功任务的追踪信息。本地文件不可写时会告警并保留控制台输出；生产不会静默降级。不要让多个服务进程共同写同一个日志文件，当前部署为单 Uvicorn worker；扩容需独立文件卷或集中日志平台。

## 关联一次审核

- `request_id`：每个 HTTP 请求生成，定位提交、拒绝与 HTTP 耗时。
- `trace_id`：一次审核链路，服务端为缺失值生成；关联图片、主图、能力、结论。
- `job_id`：异步任务 ID，前端 `job.created` 与后端 `review job created` 共用，作为人工排查入口。
- `image_id` / `image_index`：材料标识与序号，定位模型、重试、二维码来源。
- `business` / `region` / `profile`：本次实际执行的业务与版本。
- `collectionId`：浏览器采集批次，用于本地串联采集与回填，通过 `job.created` 对应后端任务。

跨线程、异步队列与 `asyncio.to_thread` 传播上下文；不同作业隔离，排队后不会借用上一作业的 trace。ID 只允许有界的字母、数字及部分分隔符，异常 ID 记录为 `invalid-id`。不要把用户姓名或业务原值当作 ID。

```bash
cd /home/ubuntu/review-agent-deploy
# 用浏览器 Console 中 job.created 的 job_id 查后端链路
grep -F 'job_id=替换任务ID' logs/review-agent.log*
# 从创建事件取得 trace_id，再定位整个审核
grep -F 'trace_id=替换追踪ID' logs/review-agent.log*
grep -E 'review qr|review qwen|review job timing' logs/review-agent.log | tail -100
```

单次只读 `/api/review/assist` 没有 job_id，用 trace_id 查询。上下文字段和少数事件正文可能同时包含 ID；以同一 ID 关联，不要依赖固定字段排列顺序。

## 应记录的事件

| 环节 / 事件关键词 | 记录内容 | 解决的问题 |
| --- | --- | --- |
| `review service started/stopped` | 发布 ID、活动 Profile 数、模型是否配置、三项并发 | 是否跑了正确镜像及配置 |
| `review http completed` | 方法、路由模板、状态、耗时、request_id | 请求没进入任务、422、404、500；不记录 query 或请求体 |
| `review job created` | job/trace、图片数、采集失败数 | 审核是否真的创建 |
| `review qwen call completed` | 分类/提取阶段、模型、图片、耗时、tokens、限流、调用结果 | 慢在模型、网络还是限流；429 轻量重试用 rate_limited 表示 |
| `review image retry` | 重试原因码、次数、结果、耗时，时间不足时 skipped | 为什么重读、重读是否有效 |
| `Agent image completed/failed/timed out` | 采用的类型、页面类型提示、接受字段键、不确定字段键、解析错误码、总耗时 | 材料路由错误、缺失字段、结构解析与单图超时 |
| `review qr decode` | 模型或本地解码来源、码数量、下载/解码错误码、耗时 | 没读到码还是图片没取到 |
| `review qr web completed` | 白名单域名、图片序号、TLS 模式、尝试次数、可访问性、HTTP 状态、错误码、耗时 | 链接有了但官网失败，参见二维码专项排查 |
| `review node completed` | 主图节点、SUCCEEDED/FAILED/CANCELLED、耗时、异常类型 | 19 个正常节点中卡在哪个阶段 |
| `review capability ...` | 能力 ID、状态、尝试次数、检查数、错误码、耗时；取消单独记 | 某业务启用的能力是否执行、被阻塞或降级 |
| `review evidence quality` | 材料完整性与质量统计 | 有上传但证据不足 |
| `review decision` | 建议、风险、每个字段的状态、证据类型、不确定来源 | 为什么提示冲突或人工复核，未配置与正常审核分开 |
| `review job timing` | 唯一终态、数量、重试数、排队/执行耗时、进程峰值内存 | 整单耗时、部分成功、失败和取消 |
| `URL ... failed` | 异常类型和安全堆栈位置 | 未预期异常；不写异常正文 |
| 浏览器 `collect.*` / `panel.collected` | 批次、业务、控件/图片数量、溢出、匹配/歧义数量 | 采集未命中、超出材料数量、页面识别失败 |
| 浏览器 `job.created/completed/failed` | 批次、任务 ID、状态 | 串联浏览器与服务器 |
| 浏览器 `write.complete` / `write.group.*` | 字段键或数量、批次、成功状态、错误码、耗时 | 回填被身份/白名单/控件/回读检查拒绝；失败提示仍显示在面板 |

成功轮询与 `/health` 不刷屏；失败轮询记录 WARNING。预期识别失败、图节点失败及能力尝试失败为 WARNING；未预期任务异常为 ERROR。模型调用的失败结果仍有 INFO 汇总，需结合图、图片及终态事件判断，不能只查 ERROR。

`review job timing` 对成功、部分成功、失败和取消各只写一次：`recognize_wait_ms` 是创建到首次获得识别槽位，`recognize_ms` 是首次识别开始到最后图片返回（包含后续图片排队，并非纯模型耗时）；`finalize_wait_ms` 是汇总排队，`finalize_ms` 是实际汇总；`total_ms` 到终态。尚未发生的阶段为 -1，避免把取消前未执行的阶段伪造为 0。`peak_rss_mb` 为整个服务进程生命周期峰值，不是某一任务独占内存。单图耗时包含该批次内部排队及语义重试，模型耗时查看 qwen 事件。

## 内容边界

允许记录：受控标识、字段键、材料类型、规则/能力 ID、状态、稳定错误码、数量、耗时、token 用量、发布信息。禁止记录：姓名、证件号、VIN、车牌、字段原值、图片/二维码完整链接与签名、页面正文/标题、提示词、模型原始响应、Cookie、密钥、请求/响应 body。

后端格式化层额外隐藏 URL、常见凭据及证件模式，转义换行并限制消息长度。异常仅记录类型和文件/行号/函数堆栈，不记录异常文本、源码行和局部变量。此层是兜底，不能代替调用点白名单；增加日志时仍应只选择明确的技术字段。前端共享诊断工具过滤自由文本与对象，不上传材料或日志，不能用 Console 打印整个 PageData、action 或响应对象。

日志不是完整审核档案：这里不保存原始证据，异步快照仍是内存与 TTL 生命周期，重启会丢失。若将来需要人工结论留痕、审计回放或长期统计，应另建带访问控制、留存政策和业务事件契约的持久化审计模块，不向运行日志填充真实证件数据。

## 常见故障排查

1. 没有文件日志：查 `deploy.log`、容器启动日志、日志目录权限；生产无法写文件会启动失败。启动脚本自动准备权限。
2. 审核没有创建：先看浏览器 `collect.*`、请求 HTTP 状态、`job.created`。422 通常是输入或 Profile 路由校验，HTTP 500 查安全异常堆栈。
3. 模型很慢：按 job_id 对比 recognize_wait、qwen duration、rate_limited 与总耗时。降低并发前先判断排队还是配额；不要仅按整单耗时归因模型。
4. 有二维码但官网失败：对比 decode 来源与 `qr web` 的 DNS/连接/TLS/HTTP/页面结构错误，见[二维码官网访问排查](二维码官网访问排查.md)。日志只保留域名，不拿链接签名做搜索。
5. 下拉/日期回填失败：查看审核页 Console 的 `write.complete` 错误码、对应采集批次及面板提示，见[页面控件回填排查](页面控件回填排查.md)。后端成功不代表 DOM 操作成功。
6. 新增能力看不到日志：检查是否使用应用命名空间、INFO 级别，确认启动发布 ID 与上传包一致，再查能力绑定与节点。不要临时恢复 uvicorn.error 散落调用。


## 本地配置版本对账

审核主图的 `review configuration` 日志记录 `page_id`、`profile` 和 `configuration_sha256`。该摘要与 `--inspect-pages` 中对应页面的 fingerprint、`--replay-pages` 用例报告一致，用来区分相同版本文本背后的实际配置。日志只记录配置标识与摘要，不记录页面字段值或材料内容。本地快照还会限制已记录版本被原地修改，详见[本地页面配置工作流](../指南/本地页面配置工作流.md)。
