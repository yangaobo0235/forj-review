# 长春报废置换审核规则（`scrap_replacement | changchun | 1.0`）

本文档是长春 Profile 的业务基线。代码实现分别位于后端 `src/forj_review_service/businesses/profiles.py`、`src/forj_review_service/businesses/replacement_policies.py`、`src/forj_review_service/businesses/rules/replacement_policy.py`、`src/forj_review_service/businesses/completeness.py`、`src/forj_review_service/businesses/rules/affiliation.py`，以及前端 `apps/review-extension/src/platform/browser/adapters`、`apps/review-extension/src/platform/browser`、`apps/review-extension/src/features/review/ui` 和 `apps/review-extension/src/platform/extension`。长春与青岛共用审核流程和材料策略，但政策窗口、产地范围和能力 ID 必须保持地区一致。旧车 VIN、发票/新车 VIN 组合核验、手机号和材料展示遵循通用字段协议：二维码官网 VIN 为最高标准，行驶证/登记证只核对后 8 位；发票代码/号码、新车 VIN/OCR VIN 先校验页面双值一致再比材料；手机号只认页面值；材料任务只显示是否齐全。

`Profile`（业务配置档案）定义长春这一业务版本；`Registry`（注册表）按 ID 查找实现；`Capability`（审核能力）由 `Handler`（处理器）或 `Subgraph`（子图）执行；`Renderer`（渲染器）负责前端工作台展示。本文中的代码 ID 保持英文以便与实现对应，后文首次出现的专业术语均按此含义理解。

## 1. Profile 身份和启用范围

| 项目 | 配置 |
| --- | --- |
| `business_type` | `scrap_replacement` |
| `region` | `changchun` |
| `version` | `1.0` |
| `rules_configured` | `true` |
| 页面路径识别 | URL 包含 `/scrap-replace-changchun` |
| 前端工作台 | `FIELD_WORKBENCH` |
| 页面动作 | `fill_review_fields`（人工回填）、`verify_invoice`（自动验真）、`set_affiliation`（按单一主体材料自动设置新旧车挂靠） |
| 失败默认策略 | `MANUAL_REVIEW` |

地区、版本和页面指纹必须同时匹配。不能因为页面字段结构与青岛相同，就把青岛 Profile 或政策替换给长春；后端启动时会校验 Profile、政策地区、版本和规则 ID 的一致性。

## 2. 必审字段

长春使用与青岛相同的标准字段集合：

- 旧车：`old_vehicle.type`、`old_vehicle.recycle_date`、`scrap_certificate.certificate_no`、`old_vehicle.vin`、`old_vehicle.plate_no`、`old_vehicle.owner`、`old_vehicle.engine_model`、`old_vehicle.emission_standard`、`old_vehicle.fuel_type`、`old_vehicle.is_jiefang`。

排放标准优先读取旧车机动车登记证书的明确值；证书没有明确值时，按完整发动机型号精确查询 `engine_emission_standards`，与页面排放标准核对。对应表仅收录车型目录中唯一对应一个国三至国六值的型号。精确命中直接使用；未命中时按已维护的 玉柴、潍柴、锡柴、大柴、上柴、江铃、扬柴、联合动力、康明斯的限定系列规则推导，并保留命中标记及规则来源。统一型号的空白、大小写、全角格式和前置品牌文字，保留完整后缀。两层均无法确定、识别不确定或参考表不可用时转人工复核；多个材料型号查表或推导的排放值不一致时提示冲突，不取多数。规则结果不自动写回精确表；明确非柴油或燃料识别不确定时不使用柴油系列规则，NG/CNG/LNG 型号也不推导。登记证车辆品牌只用于“是否解放牌”等整车品牌核验，不作为发动机厂家的限制条件。维护方式见 [发动机排放对应表](../发动机排放对应表.md)。
- 新车和发票：`new_vehicle.fuel_type`、`invoice.code`、`invoice.invoice_no`、`invoice.amount`、`invoice.invoice_date`、`new_vehicle.vin`、`new_vehicle.plate_no`、`new_vehicle.owner`、`new_vehicle.registration_date`、`application.terminal_certificate_no`、`application.customer_name`、`application.terminal_phone`。

页面附加字段 `application.owner_type`、`application.dealer_name`、`application.submitted_at` 和 `page_ocr.new_vehicle_vin` 只用于展示、主体类型声明或组合字段核验，不能被前端转化为资格结论。

## 3. 材料清单和页码

长春 Profile 使用 `SCRAP_REPLACEMENT_MATERIAL_POLICY`，模式为 `enforce`。必须采集旧车行驶证、旧车登记证第 1、2 页、报废证明、新车行驶证、新车登记证第 1、2 页和新车发票。采集阶段与识别阶段分别校验图片读取、材料类型和页码。

缺少图片为 `MISSING_MATERIAL`；图片存在但读取失败或识别不确定为 `UNCERTAIN_MATERIAL`；登记证必需页未确认时为 `MISSING_REGISTRATION_PAGES` 并进入人工复核。材料覆盖不足不会阻止不依赖该材料的能力运行，但最终建议必须保留缺失信息。

### 上传完整性展示

2026-10-16 上传完整性展示与青岛共用 `MaterialPolicy.presence_groups`：旧车行驶证、登记证、报废证明三类必传；新车行驶证、登记证、发票三类必传；主体资料满足“营业执照”或“身份证正面与反面均上传”任一方案即可，也可同时提供。不根据个人/企业类型强制选择某一方案。

页面标题保留旧车/新车分区，单图有明确标签时记录标签；无标签时先按内容分类，去掉固定图片顺序兜底。重复同类图片不能补足另一类，旧车图片不补新车缺项。上传状态独立于 OCR 字段和页码核验：已确认类型的材料不会因字段识别失败或超时变成缺失；未分类、面别不明、采集截断等情况保留待确认。登记证第 1、2 页继续参与原有证据质量检查。

`material_completeness.presence` 驱动进度下方、字段核对上方的 `MaterialPresence.vue` 折叠区。齐全默认收起，缺失/待确认默认展开；支持按图片 ID 定位原图并沿用采集身份保护。已满足主体资料的一种方案时，另一方案的缺项标为可选。该区不替代字段审核，不新增页面写回。协议兼容和回滚见[改造说明](../审核执行原理.md)。

## 4. 后端能力绑定

| 能力 ID | 类型/阶段 | 是否必需 | 产出 | 失败行为 |
| --- | --- | --- | --- | --- |
| `material_completeness` | MATERIAL / `EVIDENCE_VALIDATION` | 是 | `material.coverage` | 人工复核 |
| `scrap_certificate_qr` | EXTERNAL / `EVIDENCE` | 是 | `qr.valid`、`scrap_certificate.verified` | 人工复核 |
| `changchun_replacement_policy` | RULE / `POST_COMPARE` | 是 | `replacement.eligible` | 人工复核 |
| `verify_invoice` | RULE / `POST_COMPARE` | 否 | `invoice.verification` | 安全降级 |
| `affiliation_subject` | RULE / `FINAL_REVIEW` | 是 | `subject.relation` | 人工复核 |
| `owner_consistency` | RULE / `POST_COMPARE` | 是 | `owner.consistency` | 人工复核 |
| `vehicle_type_light_duty` | RULE / `POST_COMPARE` | 是 | `vehicle.type.light_duty` | 人工复核 |

二维码内容优先复用同一次 URL 模型提取的 `qr_codes`；模型没有可靠结果时，后端只对报废证明候选图片 URL 在内存中使用 ZXing、失败后使用 OpenCV 解码，再做官网域名、HTTPS、访问及字段核验。每次结果记录二维码来源和失败阶段，未可靠识别或官网不可用时明确转人工复核。

官网访问由 `integrations/qr/web_verifier.py` 执行：暂时性连接异常、超时及 429/部分 5xx 最多重试一次，连接异常重试使用校验证书的 TLS 1.2 兼容客户端。后端日志保留脱敏失败类型及耗时，现有二维码任务展示具体连接、HTTP 或字段解析失败原因；主图、能力 ID、业务判定和前端职责不变。详见[二维码官网访问排查](../部署运维.md)。

`verify_invoice` 在 `invoice.invoice_no` 与页面值 `MATCH` 时提出 `verify_invoice`（一键验真）页面动作，只提议不执行。它**不产出任何检查项**，因此不会进入工作台的待处理计数；非必需且失败降级为 `SKIPPED`，避免页面动作提议失败被误报成人工复核任务。

`vehicle_type_light_duty`（报废车辆类型档位）与地区政策字段 `vehicle_type_review_keywords` 配套：命中关键词的材料车辆类型会让「报废车辆类型」字段转待复核。**长春未配置关键词，因此这条能力在长春永远不产出检查项，行为与加它之前完全一致**——能力是青岛、长春共用的，差异只在政策数据里声明。青岛口径见[报废置换-青岛](报废置换-青岛.md) 5.1 节。

## 5. 长春地区政策规则

政策 ID 为 `scrap_replacement_changchun`，版本 `1.0`。三项政策检查读取与青岛相同的指定图片字段。**2026-09-21 起两个日期的窗口与青岛统一为 2026 全年**；**2026-09-21 起发票产地也改为同口径的关键词匹配**。两地现在只在关键词上不同（本地地名），规则形状完全一致：

1. **新车发票日期**：`invoice.invoice_date` 必须在 **2026-01-01 至 2026-12-31（含边界）**。缺失、格式无效、多个冲突值或 OCR 不确定为 `INSUFFICIENT`。
2. **回收证明交车日期**：`old_vehicle.recycle_date` 必须在 **2026-01-01 至 2026-12-31（含边界）**。缺失、格式无效或证据不唯一为 `INSUFFICIENT`。

**超出政策窗口交给人工复核，不自动判不通过**。窗口边上的一天之差（材料出具时间、节假日顺延）要靠人工判断，自动否决会误伤，因此超范围与"读不到日期"同样是 `INSUFFICIENT`，理由里写清超出的是哪个范围。
3. **新车发票产地**：`new_vehicle.origin` 必须规范化后包含“长春”关键词，允许“长春”“长春市”“吉林省长春市”等包含该关键词的值。无法取得唯一值为 `INSUFFICIENT`，明确不包含关键词为 `CONFLICT`。青岛自 2026-09-21 起也是这个口径（关键词换成“青岛”），两地的宽松程度必须保持一致——`tests/unit/businesses/test_replacement_policy_checks.py::test_origin_matches_by_keyword_in_every_region` 锁住这一点。

检查 ID 仍为 `POLICY-INVOICE-DATE`、`POLICY-DISPOSAL-DEADLINE` 和 `POLICY-NEW-ORIGIN`，但解释文本必须引用长春政策范围。展示层会把发票日期和报废交车日期政策结果合并到对应字段卡片，不再单独显示页面外日期核验；不能仅通过检查 ID 判断地区，响应中的 Profile 和政策版本也必须保留。

## 6. 新旧车所有人一致性

能力 `owner_consistency`（RULE / `POST_COMPARE`，必需，失败人工复核）产出检查 `OWNER-CONSISTENCY-001`，审核员在**页面外核验**里看到一条「车辆所有人一致性」。

业务只关心一件事：页面上的「报废车辆所有人」和「新车所有人」是不是同一个主体，材料只是佐证。所以**先比页面、再比材料**：

1. 两个页面原值按 `party_name` 归一化后比对。不一致直接 `CONFLICT`——材料再一致也改变不了"页面填了两个不同的人"这个事实。
2. 页面一致时再看材料。每份读到的所有人名称都要与页面值一致，有一份对不上就是 `CONFLICT`（那正是审核员必须亲眼看的场景）。
3. 任一页面值为空、或某一侧没有任何可读材料可佐证 → `INSUFFICIENT`。

**证据只认四份材料**：`old_vehicle.owner`（行驶证、回收证明）和 `new_vehicle.owner`（行驶证、发票）两组，别的证件不参与。每位所有人**每份材料一条**，重复上传和正反面合并成一条（`deduplicate_sources`），所以最多四张图。读不出名字的材料（「无法识别」）不参与比对——否则会被当成一个真实的名字，凭空造出冲突。

卡片上先摆「页面原始值」（旧车所有人、新车所有人），再摆「材料提取值」和原图。证据标签带新旧车前缀（旧车行驶证 / 新车行驶证）：同一份行驶证在两侧都会出现，只写「行驶证」在两边不一致时反而分不清是哪一边的。

**冲突就地表达，不写成一句话**：

| 情况 | 界面上怎么表达 |
| --- | --- |
| 材料值与页面值不同 | 那条材料值逐字标红（`CheckResultValue.differences`），并标「与页面不一致」 |
| 两个页面值不同 | 「页面原始值」区块下面一句 `page_value_note`：新旧车页面所有人不一致 |
| 证据不足（页面值缺失、某一侧没有可读材料） | **整段理由照旧显示** |

前两种情况下理由整段收起（`reason_distributed`）：界面上已经用标红和提示表达了同一件事，再念一遍两边写了什么只是噪音。第三种必须留——页面上没有任何东西能说明为什么判待复核，藏掉理由等于让审核员对着一个橙色标记猜。

**这条结论没有页面写回目标**：它不是一个页面控件，只是对两组既有字段的判断，所以卡片上只有「查看原图」，没有人工输入框和回填按钮。

它和 `affiliation_subject`（主体关系）是两件事：后者判断的是**主体类型**（个人/公司），用于生成后端主体类型提议，在报废置换工作台里不展示；这条判断的是**是不是同一个主体**，审核员要看。

## 7. 主体关系和挂靠规则

长春复用统一的 `affiliation_subject` 规则：识别个人或公司主体，验证个人身份证正反面、公司营业执照和法定代表人，再比较旧车与新车主体关系。个人同名、同公司名称且营业执照确认、两家公司法人相同、公司法人等于个人姓名时可以 `MATCH`；姓名或法人不同为 `CONFLICT`；材料缺失、多份冲突或主体类型无法可靠判断为 `INSUFFICIENT`。

主体关系为 `MATCH` 且主体类型明确时，后端保留主体关系结果；审核完成后由 `set_affiliation` 页面动作按上传材料设置旧车和新车挂靠：只有营业执照时填“公司”，只有身份证时填“个人”，两类材料同时存在或材料类型不明确时不自动回填。前端执行会校验页面身份、采集批次、控件唯一性并在失败时回滚。主体证据缺失或冲突仍影响后端最终建议。

## 8. 前端行为

前端业务选择显示为“长春报废置换审核”，自动识别路径为 `/scrap-replace-changchun`，手动选择产生 `scrap_replacement / changchun / 1.0`。长春、青岛及生成配置共享 `EvidenceReviewWorkbench`，按任务契约呈现，不能在组件中写地区判断来替代后端规则。

工作台展示字段比较、二维码结果、政策检查和降级原因。材料完整性在进度下方的独立折叠区展示；旧 MATERIAL 诊断任务不进入字段工作台，不展示顶部最终建议大卡片，通过后端 TaskPresentation 声明过滤主体关系诊断；日期范围、产地关键词、材料是否足够、主体关系及最终建议仍由后端决定。

后端返回的 `set_affiliation` 在审核完成后由工作台触发，把旧车和新车挂靠统一设置为动作指定的“公司”或“个人”；两类主体材料同时存在时不返回该动作。动作失败时提示人工处理，不点击页面原生“立即提交”。通用字段回填仍校验页面实例和原值，写入后回读并在失败时回滚。

长春页面遵守统一的[审核工作台前端展示规范](../审核执行原理.md)：日期或产地冲突显示红色并同时显示页面/材料值，二维码不可用和政策无法校验显示橙色待复核状态；发票日期和报废交车日期政策直接显示在字段卡片。材料完整性在进度下方的独立折叠区展示；旧 MATERIAL 诊断任务不进入字段工作台，不展示顶部最终建议大卡片，通过后端 TaskPresentation 声明过滤主体关系诊断，页签数量以过滤后的任务为准。组合字段显示两个页面原始值，点击回填时两个页面字段必须原子写入、回读和失败回滚。开票金额回读允许货币符号、千分位和小数尾零的等价格式，只有 `￥` 时按空值采集。带 `page_target_field` 的冲突任务显示默认页面原值的人工输入框和“回填此值”，成功后定位并高亮页面控件约 4 秒，回读失败则显示错误并回滚。页面失效时所有回填按钮立即禁用。

## 9. 配置维护

业务字段、材料、能力和动作声明集中在 `businesses/packs/scrap_replacement.py`，地区政策由 `replacement_policies.py` 提供。所有业务共用审核主图，普通规则直接调用注册处理函数；识别和二维码核验分别维护多步骤工作流。

自定义页面配置的动作启用、字段权限、材料要求和版本发布方式见[审核配置开发](../审核配置开发.md)。修改政策窗口、来源范围或页面动作时，同时更新业务声明、本文和边界测试；不在前端重写审核逻辑。
