# 过户审核规则（`transfer | default | 1.0`）

本文档是过户审核 Profile 的业务基线。代码实现位于后端
`app/businesses/packs/transfer.py`（字段、材料、路由、组合字段）、
`app/businesses/rules/transfer_invoice_date.py`（开票日期规则）、
`app/businesses/page_catalog.py`（页面识别），以及前端
`src/components/workbenchRenderers.tsx`、`src/browser`。修改其中任意一处，
都必须同时核对本文档和测试。

术语口径沿用 `docs/参考/术语表.md`：`Profile`（业务配置档案）定义本业务版本；
`Capability`（审核能力）由 `Handler`（处理器）执行；`Renderer`（渲染器）负责
工作台展示；`page_anchors`（页面特征文案）用于把本页面和同址的一致性审核页面
区分开。

## 1. 业务身份

| 项 | 值 |
| --- | --- |
| `business_type` | `transfer` |
| `region` | `default`（**不分地区**） |
| `profile_version` | `1.0` |
| 前端显示名 | 过户审核 |
| 页面地址 | `/consistency-qingdao`、`/consistency-changchun`（**与一致性审核完全重合**） |
| 页面特征 | `审核过户凭证`、`过户发票买家名称`、`转入地车管所`（三个全部命中才算本页面） |
| `rules_configured` | `true` |

**为什么不分地区**：青岛和长春两套页面用的是同一套规则，所以和车源审核一样取
`Region.DEFAULT`，两个地址挂在同一条 `RegionDeclaration` 上。按地址拆成两个地区
声明会让同一套规则出现两份 Profile，改一处漏一处会静默地只对某个地址生效。

**为什么地址会重合**：后台是列表页不卸载、详情叠上去的结构，同一个菜单下的详情
页共用一个 URL，靠列表页的状态筛选进到各自的页面（「待过户审核」和
「待一致性审核」）。识别因此不能看地址，只能看页面特征——判定顺序和踩过的坑见
`docs/指南/新增业务与页面.md` 第八节。

## 2. 核对字段和材料

14 个字段全部进入必审清单：

| 页面字段 | 材料来源 | 证据模式 |
| --- | --- | --- |
| 开票日期 | 二手车发票 | `SINGLE_SOURCE` |
| 车牌号 | 登记证书第 1、2 页 ＋ 二手车发票 | `PARALLEL` |
| 识别车架号 | 登记证书第 1、2 页 ＋ 二手车发票 | `PARALLEL` |
| 过户发票买家名称 | 登记证书第 3、4 页 ＋ 二手车发票，**两边都要有** | `PARALLEL` |
| 证件号 | 登记证书第 3、4 页 ＋ 二手车发票，**两边都要有** | `PARALLEL` |
| 发票代码 | 二手车发票（由票面数电号码派生，见 §4） | `SINGLE_SOURCE` |
| 发票号码 | 二手车发票 | `SINGLE_SOURCE` |
| 开票金额(含税) | 二手车发票 | `SINGLE_SOURCE` |
| 卖方名称 | 二手车发票 | `SINGLE_SOURCE` |
| 卖方证件号 | 二手车发票 | `SINGLE_SOURCE` |
| 厂牌型号 | 二手车发票 | `SINGLE_SOURCE` |
| 转入地车管所 | 二手车发票 | `SINGLE_SOURCE` |
| 二手车市场 | 二手车发票 | `SINGLE_SOURCE` |
| 纳税人识别号 | 二手车发票 | `SINGLE_SOURCE` |

页面上的**经销商、车源编号、车源名称、车源发布时间、主机厂**是只读信息，不是
核对字段。审核目录只收录声明的 14 个字段（`review_declared_fields_only=True`）。

**车源发布时间**（`application.source_published_at`）是唯一一个"采集但不核对"的
字段：`reviewable=False`，不进审核目录，只给 §4 的开票日期规则读。

### 材料（3 项，`enforce`）

| 业务分区 | 材料 | 要求 |
| --- | --- | --- |
| `transfer` | 机动车登记证书 | **第 1、2、3、4 页全齐** |
| `transfer` | 二手车销售统一发票 | 至少 1 张 |

登记证书是一份材料的两段（第 1、2 页是摘要和车辆信息栏，第 3、4 页是登记栏），
页码按图片页脚实际印刷的 `registration.covered_pages` 统计，不按上传顺序推测。
**只传了第 1、2 页时要明确报出缺第 3、4 页**——买家的名称和证件号只在这两页上，
缺了就没有证据来源。

页面上的身份证正反面和营业执照槽位归到 `other`，**不采集、不识别、不参与审核**
（业务口径已确认：过户只要求登记证书和二手车发票）。前端按 `page_groups` 把它们
淘汰在选图阶段，后端不会收到这两类图片。

**材料类型只在本业务声明的集合里选。** 上传位小标题「二手车发票」含"发票"二字，
前端关键词会把它判成 `invoice`，而跨业务合并的政策表里 `invoice` 是报废置换的
机动车销售发票——直接套用会拿错字段白名单。后端 `_expected_document_type` 的
候选已限制为 `transfer` 包声明的 `{registration_certificate, used_car_invoice}`，
判不中时改走"先分类、再按 `used_car_invoice` 提取"，不会借用别的业务的政策。

## 3. 业务例外

### 登记证书上有多条历史登记，一律取最近一次

一本登记证书上有多个历史记录，取错一条不会报错，只会把买家的名字判成别人的：

| 位置 | 有几条 | 取哪一条 |
| --- | --- | --- |
| 第 1 页「注册登记摘要信息栏」第 4 项 | 第一次上牌时的机动车登记编号 | **不取** |
| 第 1 页「转移登记摘要信息栏」 | 最近一次转移登记后的号牌 | **取这条**（车牌号） |
| 第 1 页「机动车所有人」 | 上一手车主 | **不取**（不是买家） |
| 第 3 页「登记栏」的转让登记 | 本次交易的**卖方** | **不取** |
| 第 4 页「登记栏」的转让登记 | 本次交易的**买方** | **取转让登记日期最晚的那条** |

这条约束写在材料的读取指引里（模型层面），不是事后挑选——让模型把两条都读出来
再选，它会输出两个值，然后被当成"材料内部冲突"。

### 买家名称和证件号必须两边都有

这两个字段声明了 `allow_single_evidence=False`：**登记证书第 3、4 页的转让登记和
二手车发票必须互相印证**。

| 材料情况 | 结论 |
| --- | --- |
| 两边都有且一致 | `MATCH` |
| 两边都有但不一致 | `CONFLICT`「多个来源存在不同值」 |
| 只来了一边，即使页面值相同 | 字段比较为 `REVIEW_REQUIRED`，工作台为 `INSUFFICIENT`；页面填写值不能替代另一份材料 |

只来了一边就判「一致」，等于**登记证书第 3、4 页没上传时也照样通过**——而买家是
谁恰恰只能从这两处确认。车牌号和识别车架号同样来自这两份材料，但业务没有提出
同样的要求，目前仍然允许单一来源成立；需要收紧的话改这两个字段的
`allow_single_evidence` 即可。

2026-10-13 复盘修正：多材料来源设为 `allow_single_evidence=False` 时，聚合器检查所有声明材料类型均提供有效证据，不再用“页面值 + 一份材料”满足互证要求。

### 发票代码来自票面数电号码

二手车销售统一发票（电子）票面**只有一个数电号码，没有「发票代码」这一栏**，
但审核页面上有两个控件。处理方式与报废置换的机动车销售发票一致：

- 材料声明 `derived_field=("transfer.invoice_no", "transfer.invoice_code")`，
  **模型只提取号码一次**，发票代码由确定性兼容层派生。让模型分别生成两个值，
  它会给出两个互相冲突的答案，而冲突是它自己造的。
- 工作台的字段理由上会写明「发票代码由票面数电号码适配」——不说明，审核员会
  照着这一栏去原图上找，找不到。

## 4. 能力和规则

| 能力 | 类型 / 阶段 | 必需 | 产出 | 失败策略 |
| --- | --- | --- | --- | --- |
| `material_completeness` | MATERIAL / `INPUT_COVERAGE` | 是 | `material.coverage` | 人工复核 |
| `transfer_invoice_date` | RULE / `POST_COMPARE` | 是 | `transfer.invoice_date_valid` | 人工复核 |
| `verify_invoice` | RULE / `POST_COMPARE` | 否 | `invoice.verification` | 安全降级 |

`transfer_invoice_date`（检查项 `TRANSFER-INVOICE-DATE`）判定：

- **开票日期必须晚于车源发布时间**。两边都**只比到天**：车源发布时间带时分秒
  （`2026-09-08 13:04:54`），开票日期只到天；一天之内先发布后开票是常事，比到秒
  会让同一天的两条记录随机判成不通过。
- 相等算不满足（"晚于"是严格晚于）。
- 读不到任何一个日期都判 `INSUFFICIENT`（人工复核），**不判不通过**：时间戳缺
  `2026-13-45` 这种"看着像日期"的值也不算读到了。
- **用页面上的开票日期，不是发票材料上的那个**。页面值是审核员在审的记录本身；
  材料侧读出来的值由字段比对单独负责。两个值不一致时字段比分会标成冲突，两条
  结论各说各的事，不互相覆盖。
- **结论并进「开票日期」字段行**，不再单独出一张卡片。合并关系由
  `field_check_bindings` 声明（`("TRANSFER-INVOICE-DATE", "transfer.invoice_date")`），
  后端 `prepare_display_tasks` 按声明合并——写死一张表时，每来一个带日期类规则的
  业务都要回引擎里补一行，漏了不报错，只是审核员在字段下面找不到这条结论。

### 发票代码/号码是组合字段

`page_field_composites` 声明 `FIELD-TRANSFER-INVOICE-CODE-NO`：页面上的发票代码
与发票号码先互校，一致后再与材料比对。页面自己填岔了就判 `CONFLICT`，理由写明
「页面两个字段原始值不一致」。

组合字段通过后，`verify_invoice` 提出点击页面「一键验真」按钮的请求。**触发字段
由声明给出**（`invoice_verification_field="transfer.invoice_no"`）——写死一个业务的
字段名会让另一个业务永远不验真，而且不报错，只是那个按钮从来不亮。

验真动作显式声明 `requires_authorization=False`，按现有产品约定自动执行。执行前必须验证页面身份、本次采集的发票号码控件及原值，只点击该控件所在表单项里唯一可用的验真按钮；失败显示提示，不覆盖已完成的审核结果。

## 5. 前端规则

- **页面识别**：`transfer` 与 `consistency` 共用两个地址，识别靠页面特征文案，
  由后端页面识别清单下发（`GET /api/review/page-catalog`）。给不出唯一答案时
  **不猜**，交审核员在下拉里选。**自动识别认不出来时人工选择生效**。
- **工作台**：正式 review_tasks 使用统一 EvidenceReviewWorkbench，与报废置换及生成配置共用组件。固定显示待处理、全部字段、页面外核验三个分类，不展示材料完整性任务或顶部最终建议大卡片；后端材料检查、诊断报告和最终建议保留。规则结论已投影到字段行，无独立外部任务时页面外核验显示 0。
- **回填**：只放开文本框（`writable_control_kinds=("text", "textarea", "number")`）。
  **开票日期是日期控件，不回填**——写回器对日期控件的验证程度和文本框不同，
  没验证过的一律交人工填写。声明为可写的字段渲染成日期控件时，条目上不会出现
  回填按钮。
- **页面指纹锚点**：`identity_anchors=("transfer.vin", "transfer.plate_no")`。
  `transfer.vin` 是强锚点，没有它指纹恒为空串，页面写回和原图定位会被全部拒绝。
  **证件号是个人隐私，不放进指纹。**
- **车源发布时间靠 label→文本那条采集路径**：它在页面上是纯文本，不是输入框。
  采集器的 `structuredCandidates` / `adjacentCandidates` 能读这种"标签 + 后继文字"，
  但**以 `isKnownLabel` 为闸门**——别名没进采集清单就一个值都采不到，而规则只会
  一直报「待复核」，不报错。`tests/transfer-manifest.test.mjs` 锁住了这个别名。

## 7. 待确认点

上线前必须核对生产页面：

1. **图片上传区域的实际分组标题**。这里按页面区块名称声明 `过户资料` / `过户凭证`；
   生产页面用的是别的写法时，图片会落到 `unknown` 分区，字段一律不路由并提示
   人工复核。
2. **14 个字段在页面 DOM 中的分区标识**。当前统一声明 `page_section="unknown"`
   （不做区域限制）。
3. **「车源发布时间」在页面上的实际结构**。采集器能读「标签 + 后继文字」和
   `dl`/`tr`/描述列表两种写法；如果页面把它塞在别的结构里，值采不到，规则会一直
   报「待复核」。
4. **登记证书第 3、4 页的转让登记条数上限**。当前约束是"取转让登记日期最晚的
   那一条"；一辆车过户多次时，这个约束是否仍然成立需要业务确认。
