# 车源审核

车源审核使用当前材料和字段声明，与过户审核分别维护。过户的现行配置见[过户审核](过户审核.md)。

页面入口为青岛、长春的一致性审核路径，必须同时检测到激活的“车源审核”页签及其关联可见面板。路径本身不能确定当前步骤。字段只从当前面板采集，切换步骤、车辆或采集批次后，旧查询和回填权限失效。

## 材料完整性

- 必须上传行驶证正面。
- 登记证书第 1、2 页与铭牌，至少上传一种，也可同时上传。
- 行驶证反面、登记证书第 3、4 页不用于本次核对；按单图标题排除。车况资料与附件区域也不进入材料识别。
- 上传完整性只看必传图片是否存在，不以字段识别成功、读值正确或页码识别成功作为“已上传”的条件。登记证页码是否可确认属于识别质量，单独反馈。
- 图片按所属区域和单图标题区分，不按第几张猜材料类型。没有可靠标签时保留待确认状态。

## 行驶证信息

| 页面字段 | 核对依据 |
| --- | --- |
| 车牌号码 | 行驶证号牌号码，忽略空白和大小写 |
| VIN | 行驶证完整 VIN，不使用后 8 位匹配 |
| 发动机号 | 行驶证发动机号码，不能用发动机型号代替 |
| 行驶证车辆类型 | 行驶证完整文字，不折叠为“牵引车”等大类 |
| 注册日期、发证日期 | 各自对应的行驶证日期，按日期值比较 |
| 所有人 | 行驶证所有人，使用名称规范化比较 |
| 品牌型号 | 行驶证品牌文字与辅助资料中的完整整车型号组合 |

使用性质、地址不进入核对范围。登记证和铭牌中的 VIN 只用于检查辅助材料是否与行驶证属于同一辆车，不替代行驶证 VIN。

品牌型号只允许前缀兼容的补全。例如行驶证为 `解放牌CA4255P25K2T1E6A`，登记证或铭牌为 `CA4255P25K2T1E6A80`，完整值为 `解放牌CA4255P25K2T1E6A80`。两边完整型号相同也视为一致。互相矛盾、不确定或 VIN 不一致时，不自动生成补全值，保留原图证据供人工处理。只有可靠的完整组合值提供一键回填；原始截断值和不带品牌的型号仅作为证据展示。

## 车型与规格参数

规格参数只生成一个“车型”审核项，其余参数用于回填和回读，不再逐项从图片推断。

1. 默认读取登记证或铭牌上的整车型号、发动机型号。辅助材料没有整车型号时可使用行驶证的品牌型号读值；冲突或不确定的读值不自动填入搜索框。
2. 操作人员可以编辑两个型号搜索。保留型号后缀，只统一空白、大小写和全角字符；发动机型号可去除前置中文品牌文字。不用发动机号码、马力反推或模糊相似值替代。
3. 限定页面当前品牌、车系和车辆类型，再同时精确匹配两个型号，只查询未删除、已启用的车型。缺少范围信息时要求重新读取，无匹配时不扩大范围。候选直接展示车型库的完整名称，有可用值时补充变速箱和换挡方式；车型 ID 用于后台验证和回填。即使只有一个结果也不自动选中。
4. 操作人员选择后，预览原值与将回填的值，再点击“回填整个规格参数”。按品牌→车系→车型→参数的顺序操作下拉框和输入框；父级联动重建控件时重新定位子控件。
5. 本版截图中的整块范围为品牌、车系、车型、驱动形式、燃料种类、排放标准、最大马力、发动机品牌、发动机型号，以及有有效目录值的货箱长度。库中没有货箱长度时保留原值，避免车型联动清空。缺少其他必需配置时阻止整块回填。
6. 同名车型保留为不同记录，展示车型编号、变速箱及后桥速比，操作人员选择后按具体 ID 回填。目录名称和配置存在矛盾时显示警告，不静默修正。
7. 回填前重新查询配置，配置有变化则要求重新搜索、核对预览。回填中保持步骤与车辆身份检查，完成后逐项读回。部分失败明确提示未完整回填，侧栏同步实际读回值。

具体销售版本仍由操作人员判断，所以重新审核后“车型”保持人工确认项；页面名称相同不等于已证明该版本正确。回填不点击提交或下一步。

### 车型字段交互

车型沿用统一字段卡片：顶部保留页面原始的完整车型名称；材料依据合并为可展开区域，逐值保留型号、材料来源和识别不确定提示，同一张材料的原图入口只展示一次。候选搜索与选择嵌入该字段下方，不再重复通用的材料大卡片和搜索说明。两个型号只是查询条件，不能作为车型名称直接回填；该字段不提供普通文本回填入口，其他字段保持原有交互。

搜索状态归工作台持有。页面查询范围与材料型号齐全且审核可操作时自动查询，不依赖是否已打开车型字段；识别进行中暂不可操作时，在恢复可操作后启动查询。字段切换保留候选、选择及手动搜索条件，同一条件不随组件重建或状态更新重复查询。手动修改条件立即清除旧候选与选择，不被后续识别覆盖，可明确恢复材料条件。切换车辆、步骤、采集批次或查询范围时清空旧状态，并丢弃迟到的查询结果。

搜索条件始终显示为两行：第一行整车型号输入框，第二行发动机型号输入框，右侧共用一个普通高度的“搜索车型”按钮，垂直居中。可点击按钮或按回车搜索，手动输入时提供“恢复材料条件”。

候选采用紧凑列表，每页 5 条。完整名称自然换行，不截断，不再重复名称中已有的马力、驱动和排放信息，也不显示“变速箱未提供”等占位文字。同名记录显示编号和配置差异。与页面名称完全相同时仅标注“名称与页面一致”，不以名称证明具体 ID 相同。超过 5 条才显示总数、当前范围和分页；分页只切换已经取回的完整结果，不重复请求车型库。翻页保留已选 ID，并在列表下持续显示所选完整名称、编号和配置差异；所选项不在当前页时提供“回到所选页”。修改条件或重新搜索会清除旧选择并回到第一页，列表不设置内部滚动区。

选中后展示可见字段的回填变化数量，可展开逐字段预览。“回填整个规格参数”始终可见，查询中、未选择或配置缺失时置灰并明确原因；同名记录不因此置灰。执行后展示回填和回读结果。

查询中、无匹配和通信失败分别展示。扩展接收端失效转换为中文连接提示，保留条件并提供重新查询入口；不会把连接失败当作无匹配，也不会因切换字段自动重试。查询只通过审核助手自己的服务，运行时不访问业务系统接口、生产库或测试库。

只读搜索由侧栏直接发送给扩展后台，再访问审核助手，搜索不经过业务页 content script。后台校验侧栏发送方及采集身份，为每个源标签页保存最新查询会话和可信候选到 `chrome.storage.session`，后台 worker 休眠后仍能恢复。新查询立即使旧会话失效，迟到响应不能覆盖最新候选。回填仍发送到原业务页；业务页先检查当前步骤和车辆，再向后台用查询 ID、车型 ID 取回可信配置，校验发送页、标签页、页面实例、记录指纹和采集批次，随后重新查询车型库比对配置并联动写入、逐项回读。侧栏消息不接受任意自带配置作为回填依据。

会话身份逐字段比较，候选配置递归比较键和值，不比较对象属性的排列顺序。Chrome storage 序列化或 worker 重启不会因此造成“刚搜出就失效”。确实被新查询取代或目录配置更新时，清除旧候选和选择并提示重新搜索；页面采集变化时要求重新读取。

Ant 自定义下拉框不保证将 ID 放在 DOM 上，不能仅凭名称或可见顺序点击。扩展后台通过 `chrome.scripting` 的 MAIN world 适配器只读当前 Vue 生产根节点 `_vnode`，定位采集控件对应的 ASelect，并读取实时 options、fieldNames、选中值以及虚拟列表过滤后的 ID/key 映射。调用组件公开的 scrollTo 让目标选项进入视口，标记其真实 DOM 元素，再由受页面身份守卫约束的 content script 正常点击。它不修改组件数据，不调用业务接口，不依赖开发模式专有 DOM 属性。品牌、车系、车型均核验真实 ID；名称相同但 ID 不同时仍选择目标记录。页面未加载目标 ID、控件结构无法核验或读回 ID 不一致时明确失败，不退回同名首项。最终整块规格逐项回读，车型 ID 也再次核验。

## PostgreSQL 车型查询与数据存放

审核服务只读查询自身 PostgreSQL 中的车型目录。扩展仍调用 `POST /api/review/vehicle-models/search`；自动搜索、手动搜索和回填前复核使用同一实现。连接配置见 [PostgreSQL 运行配置](../部署运维.md)。不连接原业务系统数据库，也不调用业务接口。

| 表 | 内容 |
| --- | --- |
| `forj_vehicle_brand` | 416 条品牌及原始 ID、有效标记 |
| `forj_vehicle_series` | 4,199 条车系，保留内部 ID 和外部 `series_id` |
| `forj_vehicle_model` | 148,082 条车型，保留完整名称、整车型号及关联 ID |
| `forj_vehicle_model_config` | 148,084 条车型完整规格参数，包含全部导出的配置字段 |
| `catalog_keys` | 147,270 条有效车型的规范化整车型号、发动机型号及联合查询索引 |
| `catalog_metadata` | 格式版本、源数据导出时间、表数量和缺项统计 |

四张源目录表保留原始有效状态及缺失值，仅排除 `create_by`、`update_by` 操作账号列。运行查询条件仍为 `del_flag=0 AND operate=1`；配置通过 `model_id` 关联，车系名称通过 `forj_vehicle_series.id = forj_vehicle_model.s_id` 关联，回填使用外部 `series_id`。查询首先限定页面当前品牌、车系和车辆类型：页面采集选中项文字，离线目录唯一解析出品牌 ID 与业务车系 ID（不是车系表内部主键），再叠加车辆类型、两个完整型号的精确筛选。缺少页面范围时提示先选择完整并重新读取；名称对应多个 ID 时明确报错，不猜测 ID，也不回退全库查询。保留发动机品牌前缀规范化和后缀精确比较，不做模糊搜索。超过 2,000 个匹配结果或当前页面范围内所查整车型号存在缺少配置的记录时返回明确错误，避免展示不完整的列表。

每次查询使用有连接配额和超时的只读、可重复读事务，结束后关闭连接。车型数据已经迁入 统一的 `forj_review.public`；应用不再安装或读取本地数据库文件。原始缺项继续保留，不推断补齐。


当前页面范围查询已用真实离线数据验证：东风商用车 / 东风天龙 / 牵引车下，`DFH4250A4 + DCI450-51` 为 14 条，`DFH4250A4 + DCI420-51` 为 11 条。原全库查询的 34 条由东风天龙 14 条和东风天龙VL 20 条组成，现在不再跨页面车系混查；同名不同 ID 的配置记录继续分别保留。真实页面下拉联动仍需在线核对；有匹配记录不等于无需人工选择销售版本。

## 实现与验证

自动识别约定不随审核字段配置变化：青岛和长春报废置换按路径，车源、过户、一致性按审核表单的激活页签与可见关联面板。扩展内置目录通过 `scripts/dev/export_page_catalog.py` 从同一后端声明生成，服务目录可用时优先使用服务版本。服务不可达时仍识别页面身份，单独提示服务未连接并阻止创建审核任务；恢复连接后点击“重新读取页面”更新目录和采集清单。一致性保留未配置的人工复核入口。

页面步骤与字段采集范围分别处理。业务系统 MyForm 的 `a-tab-pane` 是空容器，字段在同一表单内的后续行中。激活页签及关联面板用于确认当前步骤；空面板布局从所属审核表单读取可见字段，普通面板内有字段的布局仍限制在该面板内。标题与字段为兄弟列时，按最近的前置分区标题定位行驶证信息和规格参数。字段、身份回读和规格参数回填重新定位共用这一采集范围，切换步骤后旧采集和旧回填仍失效。

回归验证从扩展消息入口应用真实业务清单，通过与 MyForm 相同的空面板及兄弟字段结构采集 19 个字段（增加查询范围所用车辆类型）、生成 9 个可核对字段，并覆盖普通字段实际回填、回读、隐藏旧面板及外部筛选框隔离、切换步骤拒绝旧回填。该结构回归不能替代在线页面联调。

声明入口为 `businesses/packs/vehicle_source.py`；材料补全和搜索条件规则为 `businesses/rules/vehicle_source_model.py`；独立查询为 `integrations/vehicle_models.py`；扩展选择界面为 `VehicleModelPicker.vue`。工作台由 `use-vehicle-model-search.ts` 管理搜索与候选，`use-vehicle-model-review.ts` 管理预览及回填操作，纯型号和规格规则位于 `shared/vehicle-model.ts`。

后端测试覆盖材料存在、来源隔离、型号冲突、品牌补全、PostgreSQL 只读查询、范围限制及连接释放和完整主图；扩展测试覆盖候选及参数映射、页面身份、父子控件重建、部分失败与最终回读。自动化测试使用隔离的本机 PostgreSQL 和合成数据，不访问业务数据库。

生效需要重启审核后端，重新加载 `apps/review-extension/dist` 中的扩展，并刷新业务页面后重新采集。

车型回填的页面通信校验：后台不再把 `MessageSender.url` 或 `sender.tab.url` 当成当前路由。SPA 切换可能保留旧入口地址；发送方 URL/origin 只用来核验同一业务站点，当前路由改为按原请求的标签页 ID 调用 `chrome.tabs.get`，与采集地址精确比较。会话解析、离线配置复核和 MAIN world 选项检查共用该校验；消息必须来自本扩展及主 frame，原有步骤、页面实例、记录指纹、采集批次和候选 ID 校验保持生效。MAIN world 优先按发送方 documentId 执行，兼容无 documentId 时只限定主 frame，防止文档刷新后旧请求进入新文档。缺少标签页、来源站点不符、主页面标识缺失或实际导航发生时返回具体原因，不再显示笼统的“当前页面不支持车型回填”。

车型卡片显示“查询范围：品牌 / 车系 / 车辆类型”。手动修改两个型号仍沿用此范围；范围更新会清除旧候选和旧选择并重新搜索。回填前实时重读三个范围字段，发生变化则要求重新读取、搜索，不使用旧候选写入。

采集和写回统一读取下拉的选中名称，内部 ID 由选项适配单独校验；品牌使用实际的 `brandName/id` 映射。后端改动后重启审核服务，扩展改动后重新构建并加载扩展、刷新业务页。
