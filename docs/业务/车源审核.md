# 车源审核规则（`vehicle_source | default | 1.0`）

本文档记录车源审核 Profile 的完整业务契约：规则实现、前端行为、测试和文档都以同一个 Profile ID 和版本关联。声明位于 `src/forj_review_assistant/businesses/packs/vehicle_source.py`。

## 1. 业务身份

| 项目 | 配置 |
| --- | --- |
| 业务类型 | `vehicle_source` |
| 地区/租户 | `default`（车源审核不分地区） |
| Profile ID | `vehicle_source`（`BusinessProfile(business_type=VEHICLE_SOURCE, region=DEFAULT, version="1.0")`） |
| 版本 | `1.0` |
| 页面路径和指纹 | 路径 `/vehicle-source`（覆盖 `/vehicle-source/approval?...`）；指纹兜底：页面同时出现“车源审核”和“行驶证信息” |
| 规则配置状态 | `rules_configured=true`，`page_interaction=true` |
| 自动建议范围 | 13 个字段的页面值与材料比对 + 车型三项规则结论；材料不齐、基准缺失或证据不确定一律人工复核 |
| 人工复核入口 | 工作台任务列表；`INSUFFICIENT` 与 `CONFLICT` 任务都需要审核员处理 |

页面识别看**地址**：命中后返回 `vehicle_source / default`。地址来自声明里的 `admin_paths=("/vehicle-source",)`，随页面识别清单（`GET /api/review/page-catalog`）下发给浏览器。页面地址改版时按声明里的 `page_anchors=("车源审核", "行驶证信息")` 兜底——取审核页自身的标题和区块名，不要用某个字段名，字段会改版。

请求的业务与地区由 `validate_request_route` 按同一份声明推导出的路由表校验：请求若声明了别的业务或地区，直接拒绝，不会用错 Profile。

`Region.DEFAULT` 没有地区政策，因此该 Profile **不声明 `replacement_policy`**，也不产生 `{region}_replacement_policy` 能力。`src/forj_review_assistant/contracts/review.py` 的 `Region` 枚举没有车源变体，这是刻意保留的：车源不需要地区维度。

## 2. 前端规则

- **Adapter**：`VehicleSourcePageAdapter`（`apps/extension/src/platform/browser/adapters/vehicle-source-adapter.ts`）只保留页面身份，不维护可写控件表——采集、写回和页面指纹的字段范围都由后端下发的采集清单决定，见 §9。地址改版的兜底文案也从这里搬进了声明（`page_anchors`），见 §1。
- **页面识别**：清单可用时只认清单（`apps/extension/src/platform/browser/catalog/page-catalog.ts`），内置适配器表只在清单拉不到时兜底。车源的地址唯一，因此按地址命中即可，不参与按内容判定——后台的侧边栏和跨业务公共区块会被 `document.body.innerText` 一起收进来，按内容判定容易被带偏。
- **页面指纹锚点**：`identity_anchors=("vehicle.vin", "vehicle.plate_no", "vehicle.owner")`。浏览器用有值的锚点拼出页面指纹，页面写回和原图定位都以它为前提；**至少要有 `vehicle.vin` 这个强锚点**，否则指纹为空串、这些操作一律拒绝执行。锚点必须按业务声明——写死成报废置换的 `old_vehicle.*` 时，车源页面一个都匹配不上，指纹恒为空，表现就是"点回填和查看原图都没反应"。
- **字段与分区**：13 个字段的别名、页面区域和材料分组全部由后端采集清单下发（`GET /api/review/collect-manifest?business_type=vehicle_source`），前端不维护第二份表。fixture 见 `apps/extension/tests/fixtures/collect-manifest-vehicle-source.json`，一致性由 `apps/extension/tests/vehicle-source-manifest.test.mjs` 锁定。
- **页面区域（图片分组）**：**「证件照」是唯一的上传区域**，行驶证正反面、登记证书第 1、2 页和第 3、4 页、以及车辆铭牌都在这一组里；上传的材料数量由审核员按业务要求决定（行驶证必须有，登记证书与铭牌二选一）。「车况承诺书」和「车况照片」归到 `other` 分区，前端选图时直接排除，不会上传。`page_groups` 同时保留了按材料名分组的写法，兼容页面改版。
- **图片类型**：分组标题只决定业务分区，具体是哪份材料由**图片下方的小标题**决定——`classifyImage` 按它识别 `vehicle_license`（行驶证正面/反面）、`registration_certificate`（登记证书1、2页 / 3、4页）、`vehicle_nameplate`（铭牌）。铭牌分支必须排在登记证书之前——“登记证书和铭牌二选一”这类说明会把两个词写在同一句里。小标题认不出来的图片会落到模型分类，代价是多一次识别调用。
- **不声明上传槽位**：车源页面上的图片数量和顺序不固定，按次序兜底会把铭牌误判成登记证书，所以槽位留空，类型由页面文案和模型识别共同确定。
- **任务展示**：正式 review_tasks 使用统一 EvidenceReviewWorkbench，与报废置换及生成配置共用组件。不展示材料完整性任务或顶部最终建议大卡片，计数以可见任务为准；后端材料检查、诊断报告和最终建议保留。
  - **统一三个视图**：固定显示 **待处理 / 全部字段 / 页面外核验**，无独立外部任务时页面外核验显示 0。车型三条规则结论投影成功后不再下发独立规则任务，车型冲突由字段行表示。
- **审核目录只含声明字段**：`review_declared_fields_only=True`。页面上的售价、底价、是否带挂、主机厂、发布人等控件**不进入审核目录**，不会产生“请人工核对”条目——车源审核的字段就是声明的 13 个。
- **车型的条目来源**：`vehicle.model` 不参与常规字段比对，它的字段条目由 `field_check_bindings` 把三条规则结论投影而来（按最坏状态合并理由），审核员在「全部字段」里看到一行「车型」。三条结论各自成框，每条检查自己的理由写在该框里（`check_reason`），不用去读底部拼起来的长理由。**投影成功的结论不再各自出一张卡片**：字段条目已经完整展示了页面侧、材料侧、逐条说明和原图定位，再出一张「业务规则」卡片就是让审核员在「待处理」里把同一条结论看两遍。抑制的依据是“字段条目真的发出来了”，不是“声明里写过绑定”——字段控件不在页面上时条目出不来，那几条结论就只剩卡片可看。
- **一票否决**：`page_interaction=true` 使 `uncertain_requires_review` 生效——模型自报不确定的字段直接 `REVIEW_REQUIRED`，不被“看起来一致”的其它来源覆盖。

## 3. 后端字段和材料

### 3.1 必审字段（12 个进入比对）

| 字段键 | 页面名称 | 材料来源 | 证据模式 | 归一化 | 缺失/冲突语义 |
| --- | --- | --- | --- | --- | --- |
| `vehicle.type` | 车辆类型 | 行驶证、登记证书 | `PARALLEL` | `vehicle_type` | 材料值折叠为业务大类（载货汽车/牵引车）后比对，见 §5 |
| `vehicle.plate_no` | 车牌号码 | 行驶证 | `SINGLE_SOURCE` | `plate` | 无行驶证值 → `REVIEW_REQUIRED` |
| `vehicle.vin` | VIN | 行驶证（基准）、登记证书、铭牌 | `PARALLEL` + 权威链 | `vin` | 行驶证缺失 → 人工复核；辅助材料按后 8 位比对 |
| `vehicle.engine_no` | 发动机号 | 行驶证 | `SINGLE_SOURCE` | `identifier` | 行驶证上叫“发动机号码” |
| `vehicle.license_vehicle_type` | 行驶证车辆类型 | 行驶证（票面原文） | `SINGLE_SOURCE` | `text` | 保留票面完整原文，不做业务归类 |
| `vehicle.brand_model` | 品牌型号 | 行驶证（基准）、登记证书、铭牌 | `PARALLEL` + 权威链 | `identifier` | 复合字段，见 §5；辅助材料不一致 → `CONFLICT` |
| `vehicle.usage_nature` | 使用性质 | 行驶证 | `SINGLE_SOURCE` | `text` | |
| `vehicle.registration_date` | 注册日期 | 行驶证 | `SINGLE_SOURCE` | `date` | 只读“注册日期”，不得用发证日期或检验有效期代替 |
| `vehicle.issue_date` | 发证日期 | 行驶证 | `SINGLE_SOURCE` | `date` | **时效：必须在审核日往前推 90 天内**，见 §5 |
| `vehicle.owner` | 所有人 | 行驶证 | `SINGLE_SOURCE` | `party_name` | |
| `vehicle.fuel_type` | 燃料种类 | 行驶证、登记证书 | `PARALLEL` | `fuel_type` | 与车型排放标准是两件事，见 §4 |
| `vehicle.engine_model` | 发动机型号 | 登记证书或铭牌（基准） | `PARALLEL` + 权威链 | `engine_model` | **行驶证不在来源里**，见下 |

**行驶证上只有“发动机号码”，没有“发动机型号”，也没有独立的“车辆型号”。** 因此：

- `vehicle.engine_model` 的权威链首是**登记证书或车辆铭牌**，行驶证不参与。把行驶证当基准会让每次审核都卡在“未取得行驶证值”，而材料里其实有型号。比对只看型号本身，中文品牌前缀（`潍柴WP10.5H430E62`）不参与，见 §5。
- `vehicle.brand_model` 在行驶证上是一个独立栏目，正常读取；在登记证书上**没有这个栏目**，必须由「车辆品牌」栏接上「车辆型号」栏组成（`解放牌` + `CA4250P66M25T1A1E6` → `解放牌CA4250P66M25T1A1E6`）。
- 行驶证也不提供 `vehicle.model_code`（整车型号），该项只从登记证书或车辆铭牌读取。

### 3.1.1 一份材料的多张图片

行驶证正反面、登记证书第 1、2 页与第 3、4 页、以及页面重复提供的同一张图，按材料身份和规范化值去重。相同值只显示一次；不同值全部保留并参与冲突裁决。

合并发生在两处，缺一不可：

1. **字段比较**：`src/forj_review_assistant/evidence/comparison/aggregate.py` 的 `deduplicate_sources`。只合并相同值，保留最高置信度的原图引用及合并后的不确定性；不能根据页面值选择材料读值。
2. **车型规则**：`src/forj_review_assistant/businesses/rules/vehicle_model.py` 的 `_readable_values`，规则读的是原始观察，不走字段比较。这里同样调用 `deduplicate_sources`，否则马力会推成「488、488」、型号会列出两条一模一样的字符串。

材料之间的比较仍然发生在不同材料类型之间（行驶证与登记证书），那才是真正的两个来源。

车型规则的每条结论都带来源说明和原图定位：结论值自己写成「488 马力（由发动机功率推导）」，把推导途径和值放在一起；算它用的那个原文（`12520 ml / 359 kw`）留在 `detail` 里，供需要时追查。**证件上直接印着排放标准时不出推导说明**——材料和值都说“材料上读到的”，不能一个说读到的、另一个说推出来的。

### 3.3 材料

| 材料类型 | 显示名 | 分区 | 必需 | 页面提示词 |
| --- | --- | --- | --- | --- |
| `vehicle_license` | 机动车行驶证 | `vehicle` | 是 | 行驶证、行驶证正面、行驶证反面、证件照、车源资料、车辆资料 |
| `registration_certificate` | 机动车登记证书第 1、2 页 | `vehicle` | 与铭牌二选一 | 登记证书、机动车登记证、登记证、证件照、车源资料、车辆资料 |
| `vehicle_nameplate` | 车辆铭牌 | `vehicle` | 与登记证书二选一 | 车辆铭牌、铭牌、证件照、车源资料、车辆资料 |

三类材料都上传在页面的**「证件照」分组**里，业务分区相同，材料类型由图片下方的小标题区分（见 §2 的“图片类型”）。因此这三条 `hints` 只用于判断“这张图是否属于审核材料”，不用于区分具体是哪一份。

**材料标准**：行驶证必须有；登记证书第 1、2 页与车辆铭牌**上传其一即可**。这条“二选一”由 `MaterialRequirement.alternative_group` 表达（`src/forj_review_assistant/businesses/material_policies.py`），组名 `vehicle_supplement`，在 `evaluate_collected` 和 `evaluate_extracted` 两处都生效：

- 组内任一材料满足要求时，其余成员的检查项状态为 `PRESENT`，理由写明“已提供同组替代材料：X”，且**不产生** `MISSING_MATERIAL` / `MISSING_REGISTRATION_PAGES`；
- 组内没有任何材料满足时，两个成员各报一条缺失；
- 替代关系**只作用于同组材料**：行驶证缺失照常报缺失。

材料字段白名单按业务分区叠加：同一份行驶证同时被报废置换和车源审核声明，各业务只看到自己分区（`old_vehicle` / `new_vehicle` / `vehicle`）的白名单。`vehicle.engine_model` 在**未声明分区的兜底白名单**里只允许登记证书——这是报废置换的历史口径，行驶证和铭牌只在车源分区下才允许读它。

## 4. 能力和规则

| 能力 ID | 类型 | 阶段 | 输出事实 | 失败策略 |
| --- | --- | --- | --- | --- |
| `material_completeness` | `MATERIAL` | `EVIDENCE_VALIDATION` | `material.coverage` | `MANUAL_REVIEW` |
| `vehicle_model_consistency` | `RULE` | `POST_COMPARE` | `vehicle.model_power`、`vehicle.model_code`、`vehicle.emission_standard` | `MANUAL_REVIEW` |

### `vehicle_model_consistency`（车型一致性）

实现：`src/forj_review_assistant/businesses/rules/vehicle_model.py`，在 `src/forj_review_assistant/runtime/workflow/graph.py` 的 `builtin_rules` 注册为 `vehicle_model_consistency`。

页面车型是下拉值，格式为
`一汽解放 J6L 中卡 220马力 4X2 6.75米仓栅式载货车(CA5180CCYP62K1L4E5)(国五)`。
解析**全部由固定正则完成**，不交给模型——模型只负责从图片里读出原文。规则产出三条独立结论，加上字段 `vehicle.fuel_type` 的比对，构成审核员看到的四条结论（马力、燃料、整车型号、排放标准）。**驱动形式不核验。**

| 检查 ID | 标签 | 页面值来源 | 材料值来源 | `MATCH` 条件 |
| --- | --- | --- | --- | --- |
| `VEHICLE-MODEL-POWER` | 车型马力 | `(\d{2,4})\s*马力` | ① 发动机型号里的 `-(\d{2,3})E\d`（两位数表示马力/10）② 发动机功率 kW × 1.36 | 每个候选值均满足 \|差\| ≤ 10 马力或 ≤ 5%；任一来源不确定则人工复核 |
| `VEHICLE-MODEL-CODE` | 车型整车型号 | 括号内的字母数字串（长度 ≥ 5，自动排除 `(国五)`、`4X2`） | `vehicle.model_code` | 归一化后相等，或短串（≥ 8 字符）是长串的子串 |
| `VEHICLE-MODEL-EMISSION` | 车型排放标准 | `国` + 中文数字或罗马数字 | `vehicle.emission_standard`，否则由发动机型号里的 `E4/E5/E6` 推导 | 归一化到“国四/国五/国六”后相等 |

判定语义：

- **`MATCH`**：页面基准值解析成功，且材料给了可比对的值并一致。
- **`CONFLICT`**：材料给了值但与页面不一致；或**材料之间互相不一致**（多条证据归一出多个不同值）——后者必须交人工，不允许挑一个当结论。
- **`INSUFFICIENT`**：页面解析不出基准值；材料没有可读取的相关字段；或**读不出马力/型号/排放标准**。永远不会因为“没有证据”而判通过。
- 低质量材料（“看不清”“无法识别”）不参与规则判断，只能得到 `INSUFFICIENT`。

两处取值细节：

- **登记证书的“排量/功率”是同一栏**（`12520 ml / 359 kw`），所以功率优先取带 `kw`／千瓦单位的数，取不到才退回整串里的最后一个数（排量总在功率前面）。
- **排放后缀不总是收尾**：`CA4DK1-22E5`（国五）、`CA6SM6-A48E6N`（国六）、`WP12.430E50`（国五）都合法，因此取最后一个 `E4/E5/E6` 记号，不锚定在结尾。

规则的 `details` 记录推导路径（`page_power` / `material_powers` / `derivation` / `material_model_codes` / `material_emissions`），保证每条自动结论都能追溯到至少一个事实。


（「与页面**不一致**」「…与材料推导值 488 **不一致**」里的「不一致」三个字标红；「一致」不标。）

一条检查用 `PAGE_VALUE_SOURCE`（`申请页面字段`）标出自己的页面侧取值；字段装配按这个标记把两侧分开，展示名改用检查自己的标签。规则因此不必知道字段视图长什么样，字段视图也不必知道每条规则在比什么。

**字段理由里的每一句话都搬进了它自己的候选框。** 车型一个条目下挂着五六条候选值，写着它们的其实是字段底部那段用「；」拼起来的长理由；读完才知道哪一条对不上，框和理由之间要来回对照。字段装配把每条检查自己的 `reason` 写到它的候选值上（`CheckResultValue.check_reason`），工作台放进框里：

| 内容 | 来源 | 说明 |
| --- | --- | --- |
| 结论值 | `CheckResultValue.value` | 含推导途径的括号说明 |
| 与页面是否一致 | `CheckResultValue.conflicting` | `true` / `false` / `null`（页面侧没解析出值，不做判断） |
| 比对说明 | `CheckResultValue.check_reason` | 该检查的理由原文，一条检查下的多条候选共用一句 |
| 原图定位 | `image_id` / `image_index` / `document_type` | 「查看原图」 |

**只有声明了 `field_check_bindings` 的字段才有 `check_reason`**——也就是结论由规则投影而来的那些字段（车源的车型、报废置换的客户名称）。普通字段的候选值没有这一段，框里不会凭空多出一句说明。

**理由搬进候选框之后，底部那一段就不再重复显示**：字段装配在候选值上写了 `check_reason` 时，把 `details.reason_distributed` 置为 `true`，工作台据此收起段落。理由里只要多出检查没写过的一句（页面字段缺失或存在歧义，见 `MISSING_PAGE_FIELD_REASON`），那一句没有别的地方可看，`reason_distributed` 就是 `false`，整段留着。段落收起是**展示层**的决定，`ReviewTask.reason` 仍然完整，列表和别处照旧可用。

`conflicting` 和 `check_reason` 都由后端给出，工作台只负责显示，不自己比较取值、也不自己拼句子；「不一致」标红是把后端给的整句切分后染色，不改字、不加字、不据此改状态。页面侧没解析出值时 `conflicting` 给 `null` 而不是 `false`——把“没比过”显示成“一致”比不显示更危险。

另外两条细节：

- **同一结论只出一行。** 220 马力既可能来自发动机型号的尾部数字，也可能来自发动机功率的换算；两种途径合并成「220 马力（由发动机型号、发动机功率推导）」，否则审核员会看到两行一模一样的值，以为材料在重复。理由里的材料值也用合并后的结果，不出现「220、220」。
- **比对基准是页面侧解析出的那一项**（马力对马力、型号对型号、排放对排放），不是整个车型字符串。

### 字段比对与材料比对的分工

- **行驶证是唯一基准材料**：`vehicle.vin`、`vehicle.brand_model`、`vehicle.engine_model` 声明权威链，链首是行驶证图片；行驶证缺失时降级人工复核，不让位给登记证书或铭牌。
- **辅助材料只做辅助比对**：登记证书/铭牌与行驶证不一致产生 `CONFLICT`（需要审核员看一眼），**绝不自动否决**。VIN 一类容易打刻不清的字段按后 8 位比对。
- **登记证书与铭牌必须有一个**：由材料策略保证，缺失情况保留在后端材料诊断和审核判定中，不生成材料展示任务。

## 5. 业务例外

- **车辆类型的模糊归一**：行驶证写“重型仓栅式货车”，页面写“载货货车”，两者语义同属载货汽车，`normalizer="vehicle_type"` 会折叠成同一大类，判为一致。牵引车单独成类，不参与折叠。
- **行驶证车辆类型不做折叠**：它要保留票面原文（`normalizer="text"`），审核员看到的就是证件上写的字。
- **发动机型号只比型号本身**：证件写「潍柴WP10.5H430E62」，页面可能只写型号，两者是不同来源对同一台发动机的两种写法。`normalizer="engine_model"` 会去掉中文品牌再比较；**高亮也跟着去掉品牌**，否则审核员会在材料值前看到「缺少 潍柴」这种与结论无关的标记（`src/forj_review_assistant/evidence/fields/normalize.py` 的 `comparison_view` 负责裁剪，`src/forj_review_assistant/evidence/fields/differences.py` 把裁剪掉的字数加回坐标）。型号本身不同仍然是冲突，品牌不掩盖真实差异。
- **重复材料的相同读值合并**：见 §3.1.1。材料要求按材料类型计数，不按图片张数；不同读值保留，不能掩盖冲突。
- **图片分区无法确定**：图片没有落在任何声明的区块标题下时，`route_fields` 拒绝路由并提示“图片业务归属无法确定，请人工复核”，该图片的字段全部丢弃，不会冒充领域字段。
- **车型下拉值为空或格式变化**：三条车型结论全部 `INSUFFICIENT`，交人工，不影响 12 个字段的比对。
- **发证日期的时效窗口**：`max_age_days=90`，页面日期必须落在「审核日往前推 90 天」到今天之间（含两端，按本地时区的当天算）。超出**不自动判不通过**，而是把该字段降为待复核并在理由里写明窗口——时效是政策口径，边上的一天之差要靠人判断。注册日期不受时效限制，业务只要求发证日期。这条结论**随审核日期变化**：同一份材料今天审通过、三个月后审就不通过，这是政策本身的性质。
- **重复请求**：扩展通过运行锁防止同一时刻重复提交；每次服务端创建仍产生新任务，`trace_id` 只用于追踪，尚无跨请求幂等保证。

## 8. 待确认点

上线前必须核对生产页面并回填以下内容，**在此之前不要把本文档当作已验收**：

1. **13 个字段在页面 DOM 中的分区标识**。当前统一声明 `page_section="unknown"`（不做区域限制）。`page-field-collector` 的 `findSection` 只识别报废置换的旧车/新车文案，对车源页面恒返回 `unknown`，因此当前配置可用；将来若给它加上车源分区识别，必须同步回填 `page_section`。
2. **13 个字段的页面别名是否与实际控件文案一致**。别名决定前端能否把控件映射到字段键；映射不上的字段会退化成“未配置核验来源”而不进审核目录（车源声明了 `review_declared_fields_only`）。
3. **「车况承诺书」「车况照片」的分组标题必须能被前端识别为 `other`**。只有识别到才能把这两组图片排除在上传之外；识别不到时它们的分区是 `unknown`，会被图片尺寸兜底（面积 ≥ 4 万像素即入选）重新拉进上传列表，表现为“上传了车况照片、识别失败若干张”。页面改版后要重新确认这几个标题。
4. **车辆铭牌图片的小标题必须能被识别为铭牌**。铭牌和行驶证、登记证书同属「证件照」分组，业务分区一致，因此**只能靠图片下方的小标题区分材料类型**。小标题里要出现“铭牌”两个字；认不出来时图片类型交给模型分类（多一次识别调用），但**材料完整性报告在识别前按小标题统计**，会出现“已上传铭牌却提示缺少车辆铭牌”。页面改版后要重新确认这个小标题。

另外属于已知缺口，不是待确认：

- **下拉和日期控件暂不支持回填**：`writable_control_kinds=("text", "textarea", "number")`，车辆类型、使用性质、车型、燃料种类（下拉）和注册日期、发证日期（日期）的字段条目上不出现回填按钮，交人工填写。放开某一种控件之前，必须先在真实页面上验证该控件的写入与回读。
- **页面写回只在浏览器完成**：后端只声明“允许提出写回请求”（`fill_review_fields`），不代理写入；身份校验、字段白名单、控件类型白名单、原值校验、回读与回滚都在 `page-field-writer` 里，见 `docs/参考/工作台展示.md` §10。
- **`docs/指南/新增业务与页面.md` 的交付清单历史写作 `docs/business-rules/<业务>.md`**，实际目录是 `docs/业务/`；该手册已改正。本文档按实际目录放置。

## 9. 字段回填

审核员可以把材料提取值写回页面控件，写入过程全部在浏览器里完成，后端只声明"这个业务允许提出写回请求"。

三层闸门都在字段条目的 `writable` 上体现，任何一层不满足都不显示回填按钮：

| 层 | 依据 | 车源的取值 |
| --- | --- | --- |
| 业务 | `page_action_ids` 非空且动作已注册 | `("fill_review_fields",)` |
| 控件 | `ReviewFieldSnapshot.editable` | 页面控件本身可写 |
| 类型 | `writable_control_kinds` | `text` / `textarea` / `number`，下拉与日期不放开 |

字段级的可写范围来自**扩展包的字段声明**（`FieldDeclaration.writable`），由采集清单下发给浏览器：

```json
{ "writable_fields": ["vehicle.type", "vehicle.plate_no", "..."],
  "writable_control_kinds": ["text", "textarea", "number"] }
```

浏览器以这份清单为硬边界，清单之外的字段一律拒绝写入。`writable_fields` 单独成表，**不能从清单的 `fields` 里筛**：那张表只收录有中文别名的采集字段，而挂靠这类只用于操作、没有别名的字段同样允许写回，按它过滤会静默丢掉。

写入流程与报废置换完全共用（`apps/extension/src/platform/browser/actions/page-field-writer.ts`）：身份校验 → 控件唯一 → 原值校验 → 写入 → 回读 → 失败回滚。车源只是把控件类型收窄到文本框，没有第二套写回实现。
