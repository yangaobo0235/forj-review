# 青岛报废置换审核规则（`scrap_replacement | qingdao | 1.0`）

本文档是青岛 Profile 的业务基线。代码实现分别位于后端 `src/forj_review_service/businesses/profiles.py`、`src/forj_review_service/businesses/replacement_policies.py`、`src/forj_review_service/businesses/rules/replacement_policy.py`、`src/forj_review_service/businesses/completeness.py`、`src/forj_review_service/businesses/rules/affiliation.py`，以及前端 `apps/review-extension/src/platform/browser/adapters`、`apps/review-extension/src/platform/browser`、`apps/review-extension/src/features/review/ui` 和 `apps/review-extension/src/platform/extension`。修改其中任意一处规则，都必须同时核对本文档和测试。

`Profile`（业务配置档案）定义青岛这一业务版本；`Registry`（注册表）按 ID 查找实现；`Capability`（审核能力）由 `Handler`（处理器）或 `Subgraph`（子图）执行；`Renderer`（渲染器）负责前端工作台展示。本文中的代码 ID 保持英文以便与实现对应，后文首次出现的专业术语均按此含义理解。

## 1. Profile 身份和启用范围

| 项目 | 配置 |
| --- | --- |
| `business_type` | `scrap_replacement` |
| `region` | `qingdao` |
| `version` | `1.0` |
| `rules_configured` | `true` |
| 页面路径识别 | URL 包含 `/scrap-replace-qingdao` |
| 前端工作台 | `FIELD_WORKBENCH` |
| 页面动作 | `fill_review_fields`（人工回填）、`verify_invoice`（自动验真）、`set_affiliation`（按单一主体材料自动设置新旧车挂靠） |
| 失败默认策略 | `MANUAL_REVIEW` |

只有页面身份、地区和版本同时匹配时，才能选择本 Profile。页面 URL 命中但页面指纹、采集批次或请求地区不匹配时必须拒绝审核和写回。

## 2. 必审字段

### 旧车和报废证明

`old_vehicle.type`（报废车辆类型）、`old_vehicle.recycle_date`（报废交车日期）、`scrap_certificate.certificate_no`（报废证明编号）、`old_vehicle.vin`（报废车架号）、`old_vehicle.plate_no`（报废车牌号）、`old_vehicle.owner`（报废车所有人）、`old_vehicle.engine_model`（报废发动机型号）、`old_vehicle.emission_standard`（排放标准）、`old_vehicle.fuel_type`（燃料种类）、`old_vehicle.is_jiefang`（是否解放牌）。

排放标准优先读取旧车机动车登记证书的明确值；证书没有明确值时，按完整发动机型号精确查询 `engine_emission_standards`，与页面排放标准核对。对应表仅收录车型目录中唯一对应一个国三至国六值的型号。精确命中直接使用；未命中时按已维护的 玉柴、潍柴、锡柴、大柴、上柴、江铃、扬柴、联合动力、康明斯的限定系列规则推导，并保留命中标记及规则来源。统一型号的空白、大小写、全角格式和前置品牌文字，保留完整后缀。两层均无法确定、识别不确定或参考表不可用时转人工复核；多个材料型号查表或推导的排放值不一致时提示冲突，不取多数。规则结果不自动写回精确表；明确非柴油或燃料识别不确定时不使用柴油系列规则，NG/CNG/LNG 型号也不推导。登记证车辆品牌只用于“是否解放牌”等整车品牌核验，不作为发动机厂家的限制条件。维护方式见 [发动机排放对应表](../发动机排放对应表.md)。

### 新车和发票

`new_vehicle.fuel_type`（新车燃料类型）、`invoice.code`（发票代码）、`invoice.invoice_no`（发票号码）、`invoice.amount`（开票金额）、`invoice.invoice_date`（开票日期）、`new_vehicle.vin`（新车架号）、`new_vehicle.plate_no`（新车车牌号）、`new_vehicle.owner`（新车所有人）、`new_vehicle.registration_date`（注册日期）、`application.terminal_certificate_no`（终端证件号）、`application.customer_name`（客户名称）、`application.terminal_phone`（终端客户手机号）。

页面还可能采集 `application.submitted_at`、`application.owner_type`、`application.dealer_name` 和 `page_ocr.new_vehicle_vin`，这些字段用于展示、辅助主体判断或组合字段核验；它们不能被前端当作新的业务规则。

旧车 VIN 以二维码官网返回值为最高标准：页面 `old_vehicle.vin` 与官网值比较完整车架号，旧车行驶证和机动车登记证只比较车架号后 8 位，报废证明中的 OCR 车架号不参与该比较。二维码缺失或官网返回多个不同车架号时必须人工复核。

发票代码与发票号码合并为一个组合任务，先校验页面两个原始值一致，再与发票材料提取值比较；新车车架号与 `page_ocr.new_vehicle_vin` 同样合并，先校验页面原始值一致，再与材料值比较。终端客户手机号以页面填写值为准，不与发票材料比较。

## 3. 材料清单和页码

材料策略为 `enforce`，必须至少采集以下六类材料：

| 业务范围 | 材料 | 页码要求 |
| --- | --- | --- |
| `old_vehicle` | 旧车行驶证 | 至少 1 张 |
| `old_vehicle` | 旧车机动车登记证 | 第 1、2 页 |
| `old_vehicle` | 报废证明 | 至少 1 张 |
| `new_vehicle` | 新车行驶证 | 至少 1 张 |
| `new_vehicle` | 新车机动车登记证 | 第 1、2 页 |
| `new_vehicle` | 新车发票 | 至少 1 张 |

采集阶段检查图片是否存在、是否读取失败、候选是否超出上限；识别阶段再次确认材料类型和登记证页码。缺失、无法读取、无法识别或页码不足分别保留后端材料诊断信息，不能使用“有图片”替代“材料类型和页码已确认”。

### 上传完整性展示

上传完整性展示：旧车三类材料、新车三类材料分别必传；主体资料满足“营业执照”或“身份证正面与反面均上传”任一方案即可，也可同时提供。不根据申请主体类型改变这条二选一规则。

必传规则在共享 Pack 的 `MaterialPolicy.presence_groups` 声明，复用现有材料检查流程，通过 `material_completeness.presence` 返回。页面标题只决定旧车/新车分区，单图有明确标签时记录标签；无标签时按内容分类，不使用图片序号或张数推断材料类型。重复同类图片不能代替其他种类。

上传状态独立于字段 OCR、登记证页码核验和字段冲突。类型或面别确认后，字段提取失败、超时仍保留“已上传”；未分类、面别不明或采集截断时，对应未确认材料显示“待确认”。登记证第 1、2 页的证据质量检查继续保留，不作为上传展示的通过条件。

前端 `MaterialPresence.vue` 位于进度条下方、字段核对上方；齐全默认收起，缺失或待确认默认展开，显示类别、二选一方案和原图定位入口。已满足替代方案时，另一方案缺少的图片标为可选。定位沿用本次采集身份校验，不新增页面写回。原理见[审核执行原理](../审核执行原理.md)。

二维码内容优先复用同一次 URL 模型提取的 `qr_codes`；模型没有可靠结果时，后端只对报废证明候选图片 URL 在内存中使用 ZXing、失败后使用 OpenCV 解码，再做官网域名、HTTPS、访问及字段核验。每次结果记录二维码来源和失败阶段，未可靠识别或官网不可用时明确转人工复核。

`verify_invoice` 在 `invoice.invoice_no` 与页面值 `MATCH` 时提出 `verify_invoice`（一键验真）页面动作，只提议不执行。它**不产出任何检查项**，因此不会进入工作台的待处理计数；非必需且失败降级为 `SKIPPED`，避免页面动作提议失败被误报成人工复核任务。

## 5. 青岛地区政策规则

政策 ID 为 `scrap_replacement_qingdao`，版本 `1.0`。规则只读取指定材料的唯一、可读、非不确定字段：

1. **新车发票日期**：读取 `invoice.invoice_date`，来源必须是 `invoice / new_vehicle` 图片。日期必须在 **2026-01-01 至 2026-12-31（含边界）**。缺失、格式无效、多个冲突值或 OCR 不确定为 `INSUFFICIENT`。
2. **回收证明交车日期**：读取 `old_vehicle.recycle_date`，来源必须是 `scrap_certificate / old_vehicle` 图片。日期必须在 **2026-01-01 至 2026-12-31（含边界）**。缺失、格式无效或证据不唯一为 `INSUFFICIENT`。

**超出政策窗口交人工复核，不自动判不通过**。窗口边上的一天之差（材料出具时间、节假日顺延）要靠人工判断，自动否决会误伤，因此超范围与"读不到日期"同样是 `INSUFFICIENT`，理由里写清超出的是哪个范围。
3. **新车发票产地**：读取 `new_vehicle.origin`，来源必须是新车发票图片。规范化后**包含“青岛”关键词即通过**，因此“青岛”“青岛市”“山东省青岛市”“中国青岛”“产地：青岛”都算符合；明确不含关键词（如“长春”）为 `CONFLICT`，无法取得唯一值为 `INSUFFICIENT`。

   发票产地按地区关键词匹配，`allowed_origins` 保留规范写法清单，关键词命中优先。

三项政策检查仍由后端生成 `POLICY-INVOICE-DATE`、`POLICY-DISPOSAL-DEADLINE` 和 `POLICY-NEW-ORIGIN`，但展示层会把前两项分别合并到 `invoice.invoice_date` 和 `old_vehicle.recycle_date` 字段任务中。审核员在字段卡片即可看到“符合政策范围：2026-01-01 至 2026-12-31”，响应中不再残留独立的页面外日期核验任务。任一项为冲突或不足，建议不得自动通过。

### 5.1 报废车辆类型档位（`vehicle_type_light_duty`）

政策字段 `vehicle_type_review_keywords` 为 `("轻型",)`；长春未配置，同一条能力在长春不产出任何检查项。

`old_vehicle.type` 是**按大类比对**的：`normalizer="vehicle_type"` 把票面完整车型折叠成业务大类，「重型厢式货车」和「轻型厢式货车」都归入「载货汽车」，与页面的「载货车」一律判 `MATCH`。**档位因此根本不在比对范围内**——三份材料里一份写重型、一份写轻型，也照样判一致。

能力 `vehicle_type_light_duty`（RULE / `POST_COMPARE`，必需，失败人工复核）补这个盲区：任一材料的车辆类型**原文**含「轻型」时产出检查 `VEHICLE-TYPE-LIGHT-DUTY`（`INSUFFICIENT`），理由里点名是哪份材料、票面原文是什么。该检查按 `field_check_bindings` 并进「报废车辆类型」字段行，审核员在字段卡片上看到的是橙色**待复核**而不是绿色「一致」，响应里不再单出一张卡片。

- 材料侧每份材料一条（行驶证、登记证书、回收证明），重复上传与正反面按 `deduplicate_sources` 合并，同一份材料不会点名两遍；读不出来的值（「无法识别」等）不参与。
- **只看材料，不看页面值**：页面的报废车辆类型是粗分类下拉，从来不写档位。
- **未命中时不产出任何检查项**（与 `verify_invoice` 一样）：并进字段行的 MATCH 结论会把材料值再列一遍、理由多出一句废话，字段卡片保持原样才对。
- 命中判 `INSUFFICIENT` 而不是 `CONFLICT`：轻型车是否属于本次补贴范围由政策人工把握，机器只负责把它挑出来。

## 6. 新旧车所有人一致性

能力 `owner_consistency`（RULE / `POST_COMPARE`，必需，失败人工复核）产出检查 `OWNER-CONSISTENCY-001`，审核员在**页面外核验**里看到一条「车辆所有人一致性」。

业务只关心一件事：页面上的「报废车辆所有人」和「新车所有人」是不是同一个主体，材料只是佐证。所以**先比页面、再比材料**：

1. 两个页面原值按 `party_name` 归一化后比对。不一致直接 `CONFLICT`——材料再一致也改变不了"页面填了两个不同的人"这个事实。
2. 页面一致时再看材料。每份读到的所有人名称都要与页面值一致，有一份对不上就是 `CONFLICT`（那正是审核员必须亲眼看的场景）。
3. 任一页面值为空、或某一侧没有任何可读材料可佐证 → `INSUFFICIENT`。

**证据只认四份材料**：`old_vehicle.owner`（行驶证、回收证明）和 `new_vehicle.owner`（行驶证、发票）两组，别的证件不参与。每位所有人**每份材料一条**，重复上传和正反面合并成一条（`deduplicate_sources`），所以最多四张图。读不出名字的材料（「无法识别」）不参与比对——否则会被当成一个真实的名字，凭空造出冲突。

卡片上先摆「页面原始值」（旧车所有人、新车所有人），再摆「材料提取值」和原图。证据标签带新旧车前缀（旧车行驶证 / 新车行驶证）：同一份行驶证在两侧都会出现，只写「行驶证」在两边不一致时反而分不清是哪一边的。

**冲突就地表达，不写成一句话**：

| 情况 | 界面上怎么表达 |
| --- | --- |
| 材料值与页面值不同 | 那条材料值逐字标红（`CheckResultValue.differences`），并标「与页面不一致」 |
| 两个页面值不同 | 「页面原始值」区块下面一句 `page_value_note`：新旧车页面所有人不一致 |
| 证据不足（页面值缺失、某一侧没有可读材料） | **整段理由照旧显示** |

前两种情况下理由整段收起（`reason_distributed`）：界面上已经用标红和提示表达了同一件事，再念一遍两边写了什么只是噪音。第三种必须留——页面上没有任何东西能说明为什么判待复核，藏掉理由等于让审核员对着一个橙色标记猜。

**这条结论没有页面写回目标**：它不是一个页面控件，只是对两组既有字段的判断，所以卡片上只有「查看原图」，没有人工输入框和回填按钮。

它和 `affiliation_subject`（主体关系）是两件事：后者判断的是**主体类型**（个人/公司），用于生成后端主体类型提议，在报废置换工作台里不展示；这条判断的是**是不是同一个主体**，审核员要看。

## 7. 主体关系和挂靠规则

`affiliation_subject` 比较旧车所有人和新车所有人，先识别主体类型：个人需要姓名符合个人姓名格式；公司需要匹配营业执照或公司名称特征。页面 `application.owner_type` 的“个人”“公司/企业”可作为新车主体类型声明，但声明与材料推断冲突时必须人工复核。

- 个人与个人：姓名一致，且对应身份证正反面已确认，结果 `MATCH`；姓名不同，结果 `CONFLICT`。
- 同一公司：新旧车公司法定名称一致，且营业执照已确认，结果 `MATCH`。
- 两家公司：分别存在唯一营业执照且法定代表人均可确认；法人相同为 `MATCH`，不同为 `CONFLICT`。
- 公司与个人：公司营业执照法人与个人姓名相同为 `MATCH`，不同为 `CONFLICT`。
- 缺少营业执照、身份证、法人姓名，或存在多份/冲突证据，结果为 `INSUFFICIENT`。

主体关系为 `MATCH` 且主体类型明确时，后端保留主体关系结果；审核完成后由 `set_affiliation` 页面动作按上传材料设置旧车和新车挂靠：只有营业执照时填“公司”，只有身份证时填“个人”，两类材料同时存在或材料类型不明确时不自动回填。前端执行会校验页面身份、采集批次、控件唯一性并在失败时回滚。主体证据缺失或冲突仍影响后端最终建议。

## 8. 前端行为

前端业务选择显示为“青岛报废置换审核”；手动选择会产生 `scrap_replacement / qingdao / 1.0`。字段优先工作台按后端 `ReviewTask` 展示页面原值、材料值、差异位置、证据图片和处理状态。前端只负责标签、排序、人工选择和调用写回动作，不重新计算日期、产地或主体关系。

后端通过 `set_affiliation` 返回无授权页面动作；审核完成后前端按动作值把两个挂靠下拉统一选为“公司”或“个人”。两类主体材料同时存在时后端不返回该动作。通用字段回填和挂靠动作都执行页面身份、采集 ID、唯一控件、原值、回读和回滚校验。

青岛页面必须遵守统一的[审核工作台前端展示规范](../审核执行原理.md)：`CONFLICT` 字段和政策结果使用红色冲突标记，`INSUFFICIENT` 和外部降级使用橙色待复核标记；页面值、材料值和证据来源同时展示。日期政策直接显示在对应字段卡片，不重复显示页面外核验。当前统一证据工作台固定显示待处理、全部字段、页面外核验三个分类，不展示材料完整性任务或顶部最终建议大卡片；后端不再生成材料展示任务，旧响应的材料任务不参与展示计数。主体关系诊断通过后端 TaskPresentation 声明隐藏；后端材料检查、规则和最终建议保持不变。组合字段任务显示两个页面原始值；点击回填时两个页面字段必须原子写入、回读并在失败时回滚。开票金额回读允许货币符号、千分位和小数尾零的等价格式，只有 `￥` 时按空值采集。带 `page_target_field`（页面定位字段）的冲突任务必须显示默认填入页面原值的人工输入框和“回填此值”按钮；写回成功后定位控件并高亮约 4 秒，回读成功才显示成功。

## 9. 配置维护

业务字段、材料、能力和动作声明集中在 `businesses/packs/scrap_replacement.py`，地区政策由 `replacement_policies.py` 提供。所有业务共用审核主图，普通规则直接调用注册处理函数；识别和二维码核验分别维护多步骤工作流。

自定义页面配置的动作启用、字段权限、材料要求和版本发布方式见[审核配置开发](../审核配置开发.md)。修改政策窗口、来源范围或页面动作时，同时更新业务声明、本文和边界测试；不在前端重写审核逻辑。
